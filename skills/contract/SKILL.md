# Contract：契约落地与冻结

**角色**：落地（查签名）可派执行者，机械；拍板归协调者 + 用户。

## 两段

**1. 落地（机械，可派）**：把 spec 的契约语义翻译成精确签名/端点/类型。每个签名都要对着现状代码查证——它们是代码事实，不是设计发挥。产出：契约增量文档，精确到可编译。

**2. 冻结（提交，不可逆性在此）**：

- 有目标图的项目：契约条目（允许的依赖方向、入口、预算）写进 `codegraph/target.json`，**冻结即提交该文件**。此后对照闸门按它执法。
- 骨架先行（Ticket 0）：接口/类型/事件的空壳落码，**编译必须通过**——契约错配要在编译期暴露，不留给集成阶段。
- 无图项目：契约增量文档即冻结物，review 节点按它人工对账。

## 拍板记录：三重闸门

契约决定写成拍板记录（一段即可），但**只记同时满足三条的**：

1. **难逆转**——回头要动多个域；
2. **无上下文会惊讶**——后人看到会想「修掉」这个故意为之的设计；
3. **真取舍**——存在被否掉的像样方案。

少一条就不写（防拍板记录变成会话日记）。被否掉的方案与显式的「不做」一并记录。

## 纪律

- 契约变更 = 重新走本节点 + 审核，没有「顺手改一下接口」。
- 落地阶段发现 spec 的语义定不下去（两个域对同一规则的归属有分歧）→ 退回 spec，不许自选。
- 交棒：breakdown。
