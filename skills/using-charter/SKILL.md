# Using Charter

你装载了 charter 套件：以用户故事验证结果、按子系统保持代码责任、让 Agent 的自主决定对人可见。流程中的每个节点是一个 skill。

## 规则

**动手前先定位节点。**任何开发请求——新功能、修 bug、重构、评审——先判断它处于流程的哪个节点，调用对应 skill，再开始工作。哪怕只有 1% 的可能某个节点 skill 适用，也必须先调用确认。

## 节点地图

五个节点、两部法，入口只有两条：

```
bug/测试失败/诡异行为 → implement（排查节：无根因不许修）→ review → finish
需求/想法 → spec（收尾定级）
   ├─ L1 微改（plan 增量为零 + 验收一眼可核）→ implement → review → finish（spec 即 plan）
   ├─ L2 单子系统 → plan → implement → review → finish
   └─ L3 跨子系统 → plan（含拆分与接缝、需冻结的外部承诺）
        ├─ 未扇出：同 L2
        └─ 扇出：首故事子卡先走完一轮合入父卡分支 → 其余子卡分批同序列（一批 ≤ 2 张）
                 → 父卡 review（全部故事最终验收）→ 父卡 finish
```

横切（不占流程位）：`architecture-law`（架构法，spec 定边界、plan 拆责任、review 架构轴按它裁）、`defect-families`（缺陷族法，plan 与 review 引用）。契约冻结不是节点，是 plan 的条件节：只在本轮新增/变更独立工作单元共同依赖的接缝或对外兼容承诺时写。并行扇出是例外不是默认：只在既有边界上扇出，新缝一律先串行长出来。人工 move 可越列、`card dispatch --step` 不校验当前列，本图**不是机器保证**，协调者按 review/finish 的证据纪律把关。

**一律建卡**（2026-10-20 用户定，撤销 10-18「账本可选」）：进本流程的请求不论级别一律先建卡（`handoff card add`），L1 也不例外；「坐在旁边做的小活可无卡」已删——实测它会让一切滑成主会话自己做。finish 时残余一行落 `docs/roadmap.md`。

定级的判据在 spec 的「定级」节，判决写进 spec 头部；判错的纠偏是**跨流迁移**（带着已产出的东西显式迁移并留痕），不是推倒重建。

## 台账纪律

产出型节点（spec/plan/implement）**边干边落台账**：每确立一个事实就往台账文件追加一行——提交、跑过的命令与原始输出、放弃的尝试、做出的判断。不要攒到回合结束再写：回合可能不会有结束。台账是仓内文件，与本节点产出物同批提交；落点随项目约定，无约定时与产出物同目录。提交事实的记法：把提交当时的命令与原始输出追加进台账，随后只 amend 一次收进同批提交；amend 会换 hash，这是 git 的事实不是漏记，禁止把 amend 后的 HEAD 写回台账再追。收口判据是工作树干净。裁决与结论回写产出物正文，实验过程与原始读数只进台账，正文留一行指针。审查节点是只读回合，不建台账，过程记录写进裁决表。

## 红旗

| 念头 | 事实 |
|---|---|
| 「这个太简单，不用走节点」 | 简单需求的 spec 可以只有几句话；跳过的从来不是仪式，是判据。 |
| 「我记得那个 skill 说什么」 | skill 会演进，调用读当前版本。 |
| 「先探索一下代码再说」 | spec 的事实调查、排查的第 0 步正是探索——那是节点内的工作。 |
| 「用户催得急」 | 急 = 走轻档，不 = 跳节点。 |
| 「级别判错了，重新建卡吧」 | 跨流迁移带着产出走；重建丢事件流，审计链断裂。 |
| 「有规则不让我做 X」 | 引出那条规则的原文和出处；引不出，它就不存在。 |

用户显式指令永远优先于本套件。
