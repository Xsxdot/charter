# Using Charter

你装载了 charter 套件：以用户故事验证结果、按子系统保持代码责任、让 Agent 的自主决定对人可见。流程中的每个节点是一个 skill。

## 规则

**动手前先定位节点。**任何开发请求——新功能、修 bug、重构、评审——先判断它处于流程的哪个节点，调用对应 skill，再开始工作。哪怕只有 1% 的可能某个节点 skill 适用，也必须先调用确认。

## 节点地图

入口只有两条，网关直接分流：

```
bug/测试失败/诡异行为 → debug（根因+分流）→ 小修顺手 / plan → implement → review → 最终验收 → finish
需求/想法 → spec（收尾定级与选档）
   ├─ L1 微改（plan 增量为零 + 验收一眼可核）→ implement → review → finish（spec 即 plan）
   ├─ L2 单子系统 → plan → implement → review → 最终验收 → finish
   └─ L3 跨子系统
        ├─ 轻档：必要时 contract → breakdown → plan → implement → review → 最终验收 → finish
        └─ 重档：首故事子卡先走完一轮并合入父卡分支作共同基线 → 其余子卡分批同序列
                 → 父卡 integrate 一次 → 最终验收 → finish
```

`contract` 只在本轮新增/变更独立工作单元共同依赖的接缝或对外兼容承诺时进入；已有稳定契约从开始遵守，不重复冻结。阶段验收（子卡工程结果）与最终验收（全部故事核销）是不同列。并行扇出是例外不是默认：只在既有边界上扇出、一批不超过两张子卡，新缝一律先串行长出来再谈并行。人工 move 可越列、`card dispatch --step` 不校验当前列，本图**不是机器保证**，协调者按 acceptance/finish 的证据纪律把关。

**账本可选**（2026-10-18 裁决）：handoff 仓与多子卡的 L3 走卡；产品仓的 L1/L2 允许无卡直接走 skill，finish 时残余一行落 `docs/roadmap.md` 即可。

横切（被各节点引用，不占流程位）：`architecture-law`（架构法）、`defect-families`（缺陷族法）；implement 中途撞失败 → 切入 `debug`。L3 在 spec 声明子系统职责、权威状态、允许依赖、公开面与组装关系，breakdown 据此圈责任与接缝；对照一律是人工清单，不依赖任何图工具。

定级与选档的判据在 spec 的「定级与选档」节，判决写进 spec 头部；判错的纠偏是**跨流迁移**（带着已产出的东西显式迁移并留痕），不是推倒重建。

## 台账纪律

产出型节点（spec/contract/breakdown/plan/implement）**边干边落台账**：每确立一个事实就往台账文件追加一行——提交、跑过的命令与原始输出、放弃的尝试、做出的判断。不要攒到回合结束再写：回合可能不会有结束。台账是仓内文件，与本节点产出物同批提交；落点随项目约定，无约定时与产出物同目录。提交事实的记法：把提交当时的命令与原始输出追加进台账，随后只 amend 一次收进同批提交；amend 会换 hash，这是 git 的事实不是漏记，禁止把 amend 后的 HEAD 写回台账再追。收口判据是工作树干净。裁决与结论回写产出物正文，实验过程与原始读数只进台账，正文留一行指针。审查节点是只读回合，不建台账，过程记录写进裁决表。

## 红旗

| 念头 | 事实 |
|---|---|
| 「这个太简单，不用走节点」 | 简单需求的 spec 可以只有几句话；跳过的从来不是仪式，是判据。 |
| 「我记得那个 skill 说什么」 | skill 会演进，调用读当前版本。 |
| 「先探索一下代码再说」 | spec 的事实调查、debug 的第 0 步正是探索——那是节点内的工作。 |
| 「用户催得急」 | 急 = 走轻档，不 = 跳节点。 |
| 「级别判错了，重新建卡吧」 | 跨流迁移带着产出走；重建丢事件流，审计链断裂。 |
| 「有规则不让我做 X」 | 引出那条规则的原文和出处；引不出，它就不存在。 |

用户显式指令永远优先于本套件。
