# Implement：实现

## 测试纪律

测试只为两类对象写，**先红后绿**：

- **竖切**：本任务承诺的用户故事从真实入口到可观察结果的一条路径，优先经生产接缝或真实消费入口断言；
- **核心方法**：承重规则与不变式（状态机转移、金额/时间计算、权限判定、序列化边界）。

**只测当前组件。**邻居组件的行为靠既有测试与 review 的真机兜底，不在本任务里替它补测。没有可测的真实路径时先说明障碍并设计验证，不造只为测试而存在的假缝。日志、注释、纯映射不开独立红绿周期，但纯映射须被行为或 roundtrip 断言覆盖。

- **看到红才算测试存在**：确认失败原因是功能缺失而非 typo。新建缝符号的首红允许是编译红，空壳落地后必须再见一次断言红才进入实现；既有缝上的红必须直接是断言红。
- 绿灯只写最小代码（YAGNI）；重构不加行为。
- 测试有没有牙由 review 的变异复验核一次，实现侧不自验变异。

**首故事（L3）的实现边界**：沿 spec 声明的子系统职责、权威状态、允许依赖和组装点，从真实产品入口做到用户可观察结果。只建设所选故事触及的路径；不得为赶演示新增跨子系统穿透、临时万能协调对象、硬编码成功或测试专用入口。探索结果证伪目标边界时停下来修订 spec；通过审查的代码才可作为后续子卡共同基线。

## 测试三段律

**编译全量、测试局部、集成全量。**

- task 内循环：只跑**触及包**的测试（plan 里已声明范围）。
- 每个 task 收尾：全量**编译/类型检查**（最便宜的全仓检查）+ 触及子系统的测试。
- 全量测试**只出现在 review（父卡最终验收）与 finish**——它不是被省略，是被移位到唯一有意义的位置。跨包破坏由编译与契约闸兜底，漏网的由全量抓。

## 日志与注释（交付的一部分）

- 关键节点必打：入口带输入、外部调用前后、**每条错误分支带上下文与原因**、成功路径不静默（静默成功是「靠猜排障」的头号成因）。
- 结构化 logger，禁 print / fmt.Printf / console.log。
- 新文件头：职责 + 边界；导出函数：参数/返回/注意事项；非显然逻辑：写「为什么」不写「做了什么」——与代码重复的注释删掉。

## 修复熔断

**同一问题 3 次修复失败 = 架构问题。禁止第 4 次尝试**——停下，写清三次各改了什么、各怎么失败的，上报协调者。继续硬试烧的是轮次，掩的是结构性根因。

## 排查：修 bug，或中途撞失败

**无根因调查不许提修复。**没搞清为什么坏就改代码 = 修症状不修病根，补丁只会把缺陷换个位置复活。排查可派快执行者跑轮次；根因后的**分流决定归协调者**。

- **第 0 步：钉死被验对象身份**——哪个二进制、哪个分支、哪个提交、哪个进程。版本戳、构建缓存、linked worktree 都会说谎；身份没钉死之前一切观察都不可归因。
- **第 1 步：建红色反馈回路**（这一步就是排查的全部，其余是机械）。找到一条命令同时满足四项才算有回路，没有它不许进假设阶段：①能对这个 bug 变红；②确定性（偶发红先二分收敛成必现）；③快（秒级到分钟级）；④agent 可跑、不依赖人眼。
- **第 2 步：边界取证**（多组件系统）：在每个组件边界加统一前缀的诊断日志（如 `[DEBUG-xxxx]`），完整跑一遍，先定位断在哪一层，再进那一层查。不许在没有取证的层里凭感觉翻代码。
- **第 3 步：假设纪律**：列 3~5 个可证伪的假设并排序（只有一个假设 = 锚定了第一直觉）；一次实验只改一个变量；归属判据看失败原文——「不是我干的」≠「没有 bug」。
- **常见形状**：偶发红多半是判据取了中途副产物；环境假红有固定形状（负向权限断言在 root 下全红、路径长度上限、HOME 不可写），认不出就在环境内外对跑同一命令；测试全绿但功能不生效 = 夹具编码了错误假设，转真机。
- **出口**：修复必须先有复现该 bug 的失败测试；若代码里不存在能写这条回归测试的接缝——这本身就是发现，按架构债立卡，不硬塞测试。根因后分流：一两行小修顺手修掉；改变职责、权威状态或依赖方向回 spec 定性；命中新的共同依赖接缝或对外承诺进 plan 的「需冻结的外部承诺」节；不许在排查现场顺手动架构。收尾把诊断日志一把清干净，根因、证据、分流决定落卡。

## 结论纪律

- **边干边落台账**（纪律见网关「台账纪律」节；派发时作为附录随本块注入）。
- **交回物第一节固定为「偏离与自主决定」**：本节点的交回物（台账 / 报告 / 交棒声明）第一节标题固定为「偏离与自主决定」，逐条列出：①与已批准 plan 或 spec 不一致之处；②本节点执行者自行拍板的内容与理由；③每条是否落在 plan「决策权限」节的授权范围内。没有偏离时必须写「无」，不得省略该节。偏离只出现在正文编号列表里、没有进该节，视同未披露。
- **没跑到结果不许写结论。**测试没跑就写「预计通过」、命令失败就绕过去——都算谎报。跑不了就如实记「未验证」与原因。宁可交一个诚实的未验证，不交一个编造的绿。

## 收尾自审

- 每条错误分支有带上下文的日志？成功路径有出口日志？新文件有头注释、导出函数有文档注释？
- 触及包测试绿、全量编译过？
- 本轮故事/步骤、适用的既有或新冻结契约、触及的架构边界是否一致？未冻结的内部实现调整是否留有理由与验证结果？
- 交回物第一节是「偏离与自主决定」？每条自行拍板都对照了 plan 决策权限？无偏离写了「无」？
