# Acceptance：验收

## 顺序铁律

**复跑 → 变异复验 → 真机验收 → 才归档。**

任务挂在待审状态零成本；提前归档等于赌测试没有盲区，且会关掉续接通道（只能重派、丢执行者上下文）。

## 1. 复跑：新鲜证据

没有本轮跑出的证据不许声明通过——「早些时候绿过」不算，执行者自报的绿要用 diff 与复跑独立核验。任何暗示成功的措辞（「应该行了」）都触发本条。

## 2. 变异复验：测试有没有牙

把实现改坏一处，对应测试必须转红；还原必须回绿。两条规则：

- **变异必须编译得过。**删出一个编译错误不是证据——那证明的是代码被引用，不是行为被守护。用「条件永假化」这类保编译的变异。
- 变异点选**本次交付的承重行为**，不是随机行。多路径共用的实现，变异一处应使每条声称覆盖它的路径都红——只红一边说明另一边的覆盖是假的。

## 3. 真机验收：行为事实只能跑出来

**API 事实可以静态核验，行为事实不能。**

- API 事实（签名存在、哨兵存在、方法名对）——grep 可确认，「判据先在基线跑」罩得住。
- 行为事实（这个事件走不走那条通路、那个字段实际谁写入、某状态下真实响应）——**只有把系统跑起来才知道。夹具里每一个行为假设都是一次没人验证的断言**；夹具编码了错误的现实时，单测全绿、变异也红——它们忠实验证了一个不存在的世界。

处置：breakdown/plan 里标注「未验证，需真机」的每一条，在此逐条执行；边界域的行为验收全部走真机清单，不得用 mock 结果抵账。

## 4. 契约对照（有图项目）

分支视图对照闸门无 fail；接缝收窄了就提请调低预算（棘轮只减不增）。

## 红旗

| 念头 | 事实 |
|---|---|
| 「测试全绿，直接归档」 | 全绿只证明「写下的假设被满足」，不证明假设对。行为假设逐条真机。 |
| 「变异删掉整段实现，测试红了」 | 若红的是编译错误，证据无效，重做保编译的变异。 |
| 「真机麻烦，下次补」 | 事后补验 = 永不验。真机清单清空是归档的前置条件。 |
