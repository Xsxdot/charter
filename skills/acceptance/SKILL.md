# Acceptance：验收

## 顺序铁律

**复跑 → 承重变异复验 → 真机验收 → 阶段裁决；最终验收通过后才可归档。**

任务挂在待审状态零成本；提前归档等于赌测试没有盲区，且会关掉续接通道（只能重派、丢执行者上下文）。

**两种裁决，同一证据纪律**：Wave 0 只验选定故事与它触及的生产路径，留下可取得的被测提交、构建/环境、故事及原型版本、实际结果和独立 review 记录，作为后续共同基线；它不宣称整个需求完成，也不归档父卡。最终验收核销本轮全部必交故事、相关原型/流程图状态与关键反例；L3 重档在集成后逐项核 S1…Sn 及已有故事回归，L3 轻档/L2/bug 则从本轮 review 进入，不强求不存在的 integrate。子卡技术绿、Wave 0 旧绿或“已开修复卡”都不能抵账。

**入口先辨阶段**：Wave 0 核对 plan 头部的阶段、选定故事与版本，以及 review 的本轮交棒；L3 重档最终验收核对 integrate 交棒中的阶段、故事全集、下一去向和所引计划版本；L3 轻档/L2/bug 核对本轮 plan、review 与全部承诺。缺对应记录不猜作最终验收。Wave 0 通过后，协调者按 plan 的交棒区规则追加已验基线、分工草案与下一去向，保留本轮验收所引用的原计划版本；最终通过才交图对账/finish。

## 1. 复跑：新鲜证据

没有本轮跑出的证据不许声明通过——「早些时候绿过」不算，执行者自报的绿要用 diff 与复跑独立核验。任何暗示成功的措辞（「应该行了」）都触发本条。

## 2. 变异复验：测试有没有牙

把实现改坏一处，对应测试必须转红；还原必须回绿。两条规则：

- **变异必须编译得过、必须打中唯一**——两条的展开与手法见 implement 的「变异自验」段，此处不重复正文。协调者复验时按那一段执法：编译不过的那一发不算数，「变异后一切如常」先怀疑没打中。
- 变异点选**本次交付的承重行为**，不是随机行。多路径共用的实现，变异一处应使每条声称覆盖它的路径都红——只红一边说明另一边的覆盖是假的。转红者至少有一支穿过真实消费入口或所声称覆盖的生产接缝；只有内部锁转红，不得声称生产路径已有测试覆盖。没有预先声明的缝时不为过此维制造假缝。

## 3. 真机验收：行为事实只能跑出来

**API 事实可以静态核验，行为事实不能。**

- API 事实（签名存在、哨兵存在、方法名对）——grep 可确认，「判据先在基线跑」罩得住。
- 行为事实（这个事件走不走那条通路、那个字段实际谁写入、某状态下真实响应）——**只有把系统跑起来才知道。夹具里每一个行为假设都是一次没人验证的断言**；夹具编码了错误的现实时，单测全绿、变异也红——它们忠实验证了一个不存在的世界。

处置：当前阶段 breakdown/plan 里标注「未验证，需真机」的每一条，在指定环境逐条执行；边界型子系统的行为验收走真机清单，不得用 mock 结果抵账。受原型/流程约束的故事拿实际截图、输出或运行轨迹对照**指定版本与状态**，不能以摘要代替页面。Wave 0 同时核对真实组装、权威状态和生产消费者是否落在 spec 已批准的边界上；新增路径穿透他方内部即使演示成功也不通过。把 review 与外部审计**落卡**的 Critical/Important findings 逐条核销——发现某条 finding 只存在于对话里、没有落卡，先补卡再核销。验收中判定「退回某节点/留待下一期」的缺口，逐条落 `docs/roadmap.md`（残余账本）。

## 4. 契约对照（有图项目）

分支视图对照闸门无 fail；接缝收窄了就提请调低预算（棘轮只减不增）。有新冻结物时核其版本及消费方证据；无新冻结物时查适用的既有契约和实际架构调用，不把“未进入 contract”判为缺证据。代码或环境变化使既有故事证据失效时补跑，并保留旧记录。

## 红旗

| 念头 | 事实 |
|---|---|
| 「测试全绿，直接归档」 | 全绿只证明「写下的假设被满足」，不证明假设对。行为假设逐条真机。 |
| 「变异删掉整段实现，测试红了」 | 若红的是编译错误，证据无效，重做保编译的变异。 |
| 「变异后行为一模一样，测试也不红」 | 先怀疑变异没打中（同名文本命中了别处），而不是先判「没人看着」。变异真生效则行为必变。 |
| 「真机麻烦，下次补」 | 事后补验 = 永不验。真机清单清空是归档的前置条件。 |
