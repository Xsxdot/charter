# Finish：收尾

**角色**：协调者。收尾是裁决密集节点，机械步骤可派，每个裁决归人。

## 顺序

1. **当前树新鲜全量**——「早些时候绿过」不算数。红了就地停住，不进入任何清理。

2. **集成方式是人的决定**：呈现三选项（本地合并 / PR / 保留分支）并等待，不自作主张，也不主动提议丢弃。丢弃工作需要用户显式确认。

3. **合并后**：结果树再跑全量；红了停在原地，不清理不收尾。

4. **基准回灌**（先合并、后回灌，锚点才指向主线提交）：
   - 有目标图：先确认图对账已过（走卡的流以「图对账」列裁决为准；无卡分支此刻人工核对 BASE..HEAD 与视图 diff 一致），再把本分支图 diff absorb 回基线；
   - 有原型基准：本分支的前端形态改动回流基准站；
   - 基准靠流程副产物保鲜，不靠专项重扫——跳过这步就是在给未来的自己埋一张腐烂的地图。
   - **基线不做文本合并**：主线在你干活期间也回灌过时，`baseline.json` 两侧改的是同一份图数据的不同增量。别逐行合——理由不是「合出来必然错」，而是**你无从判断这一次错没错**：2026-08-25 实测把一次真冲突还原成 union 缝合，其节点集、边集、容器集与正确 absorb 的结果**完全相同**，`check` 退出 0、fails 0、各类 warns 一条不差，与正确基线的输出**逐字节相同**。那次恰好全对，是因为两侧增量落在不相交的键区间（这份 JSON 一键一行、键有序，union 于是等价于集合并）——**那是那次 diff 的性质，不是机制保证**；两侧改到同一个节点时会留下重复键或互相矛盾的属性，而文件本身不会告诉你落在哪一种。**绿在这里不是证据。**
     唯一必然错的是 `meta.commit`：缝合出的基线会声称自己扫过一个它没扫过的提交。
     处置三步：取**主线**的基线 → 从工作分支取回本分支的视图 diff → 在新基线上**重跑 absorb**（absorb 顺带把 `meta` 刷到当前 HEAD，这正是文本合并做不到的那一半）。判据是 absorb 前后 `check` 的 fails 与各类 warns **逐项**比对，与在旧基线上跑的那轮相符——比对前先确认靶子一致，换靶子会让计数因无关原因漂移（实测：`budget-raised` 差 5 条，源头是靶子不是 git 仓、棘轮被跳过）。

5. **文档对齐**：受本分支影响的文档逐个过。**事实性修正自动做**（版本号、命令、路径）；**叙事改写、删除、涉安全的必问**——停/不停按这两类清单执法，不凭感觉。

6. **残余落账**：本分支凡标过「未验证」「退回裁决」「下一期」的条目，逐条核对已落 `docs/roadmap.md`（残余账本）；仍散在注释、验收清单或对话里的，此刻收进去——finish 是残余的最后一道收集网。

7. **归档收口**：远程任务先归档成功、再谈清理（顺序反了会留孤儿）。验收没过不归档。

## 红旗

| 念头 | 事实 |
|---|---|
| 「测试早上全绿过，直接合」 | 分支在动、基线在动。新鲜证据是收尾的入场券。 |
| 「先清理工作区再收口」 | 顺序反了。收口被拒时，已删的现场救不回来。 |
| 「基准回灌下次一起做」 | 下次的分支 diff 会叠在陈旧基线上，absorb 从此对不上。 |
| 「baseline.json 冲突了，逐行挑一下就好」 | 拼出来**可能刚好是对的**（实测有过），而你没有任何办法知道这一次是不是；且 `meta` 会声称它扫过一个它没扫过的提交。取主线基线 + 重跑 absorb。 |
