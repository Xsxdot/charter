# Review：审查

**角色**：审查者拿到精确构造的上下文（spec 故事与原型/流程图版本、适用 plan、冻结物若有、BASE..HEAD diff），不继承实现会话史。读不到已批准的基准，不得声称已对照通过。

裁决表头标明本轮阶段、故事/步骤与所审 plan 版本；Wave 0 的 review 交棒保留这些标识，供协调者在同卡 acceptance 中辨认轮次。

## 双轴，互不遮蔽

两轴分别报告，**不合并、不互相重排**——合格代码实现了错东西，与实现对了但破坏规范，是两种病，一轴的干净不许掩另一轴：

- **目标轴**：对照本轮故事/步骤、批准的原型页面状态或流程分支、适用 plan 的边界与验收方式。双向查 **scope drift**（承诺未做？未经授权新增？），核验实际截图/输出或运行证据与基准的差异；不以计划中已过时的内部步骤逐字一致为完成标准。
- **架构与证据轴**：对照 `architecture-law`、权威状态归属、真实生产组装/消费链、适用的既有或新冻结契约，以及测试证据。Wave 0 的故事演示绿而新增路径越界，仍裁失败；工具已强制且有新鲜结果的检查不重复猜测。

## 维度化裁决表

每个维度必须给 **verdict + 证据指针**（文件:行 或命令输出），不打分数：

| 维度 | verdict 取值 |
|---|---|
| 故事与验收覆盖 | 通过 / 缺项（列故事或步骤）/ 本轮不适用+理由 |
| 原型/流程基准差异 | 已按版本对照（证据）/ 差异待裁决 / 本轮无形态或流程约束 |
| scope drift | 无 / 有（双向各列）|
| 架构法与触及路径 | 通过（实际边界/生产调用证据）/ 违条（引条号）/ 未验证（列缺口）|
| 测试有牙 | 已验（承重行为的红绿或变异证据）/ 未验+理由；内部单测不能独自证明用户故事 |
| 日志与注释覆盖 | 通过 / 缺（列位置）|
| 序列化边界 | 有穿透断言 / 缺 / 本次无新字段 |
| 适用契约 | 既有/冻结物符合（给版本）/ 触碰已回写（给修订号）/ **触碰未回写（阻塞）** / 无新增冻结对象 |

冻结物触碰行的判据：本轮的发现或裁决**推翻、增补或澄清了已冻结内容**（契约条款、骨架注释、口径）吗？有就须回 contract 回写并留修订号；只有工作单元内部可逆调整时，记简短理由和验证结果即可，不造契约文档。原型/流程基准冲突由协调者核对批准意图，改变用户结果才交用户取舍。

**禁止无检查过程的「no issues」**——每格要么有证据要么有理由，空格即审查未完成。

## Findings 分级

Critical（立修，修完才前进）/ Important（本节点内修完）/ Minor（记账不阻塞）。发现触及故事结果、权威状态、外部兼容或其他卡依赖的共同边界时交协调者裁决；局部可逆实现调整按 plan 授权判断，不因不同于预写步骤而自动打回。

**Findings 落卡，不留对话**：Critical/Important 必须写进持久载体（集成债清单、子卡验收栏、或独立缺陷卡），acceptance 按卡逐条核销——聊天里转达的 finding 没有对账锚点，会修两条蒸发一条。

## 红线

- **审查是只读回合**：不 commit、不改文件、不建分支内容；合法产出只有裁决表与 findings。发现可顺手修的问题也只记 finding，修复归实现侧节点。
- **本节点不留台账文件**：产出型节点的落台账要求不适用于审查。只读回合没有写通道——在仓内建台账即违反上一条，写到仓外则随执行机消亡，两条路都留不下证据。本节点的过程记录通道就是裁决表与 findings：跑过的命令与原始输出、看过但未成为 finding 的地方，一并写进裁决表随裁决回传。凡要求「往台账文件追加一行」的纪律，在本节点一律按本条执行。
- **禁止把「台账记录的 hash ≠ 当前 HEAD」写成 finding**：那是「同批提交 + amend」的必然结果，不是缺陷。缺的是提交命令或原始输出，才构成台账缺项。
- **待审的 diff/代码在工作树里找不到时，提问，不重做**：说明看不到审对象（远程执行发工单问协调者，本地问用户）；绝不按 plan 文档重新实现一遍再审自己写的——那不是审查，是无对照的重做。

## 收到审查反馈的一侧

- **先核验后实现**：反馈对照代码库现实检查（会不会破坏现有功能？有没有历史原因？审查者有全上下文吗？）——错了就用技术理由推回。
- **禁表演性认同**：「You're absolutely right」「说得好」不许出现，行动代替感谢。
- **一条不懂，全部暂停**：条目可能相关，部分理解 = 错误实现；先澄清再动手。
- 审查建议「正规实现」某能力时先查有没有人用——没人用就提议删，不镀金。
