# Review：审查

**角色**：审查者拿到的是精确构造的上下文（需求/plan/BASE..HEAD diff），不继承实现会话史。

## 双轴，互不遮蔽

两轴分别报告，**不合并、不互相重排**——合格代码实现了错东西，与实现对了但破坏规范，是两种病，一轴的干净不许掩另一轴：

- **契约轴**：对 spec/plan 对账。含双向 **scope drift**（说了要做的没做？没说要做的做了？）与 **plan completion audit**（从 plan 逐条抽 actionable item 与 diff 交叉核对）。
- **规范轴**：对 `architecture-law` 与项目规范。工具已强制的（编译器、linter、契约闸）跳过不重复。

## 维度化裁决表

每个维度必须给 **verdict + 证据指针**（文件:行 或命令输出），不打分数：

| 维度 | verdict 取值 |
|---|---|
| plan 覆盖完整性 | 通过 / 缺项（列出）/ 不适用+理由 |
| scope drift | 无 / 有（双向各列）|
| 架构法合规 | 通过 / 违条（引条号）|
| 测试有牙 | 已验（变异或红绿证据）/ 未验+理由 |
| 日志与注释覆盖 | 通过 / 缺（列位置）|
| 序列化边界 | 有穿透断言 / 缺 / 本次无新字段 |

**禁止无检查过程的「no issues」**——每格要么有证据要么有理由，空格即审查未完成。

## Findings 分级

Critical（立修，修完才前进）/ Important（本节点内修完）/ Minor（记账不阻塞）。发现与 plan 文本冲突时归协调者裁决，不许审查者单方改判 plan。

## 收到审查反馈的一侧

- **先核验后实现**：反馈对照代码库现实检查（会不会破坏现有功能？有没有历史原因？审查者有全上下文吗？）——错了就用技术理由推回。
- **禁表演性认同**：「You're absolutely right」「说得好」不许出现，行动代替感谢。
- **一条不懂，全部暂停**：条目可能相关，部分理解 = 错误实现；先澄清再动手。
- 审查建议「正规实现」某能力时先查有没有人用——没人用就提议删，不镀金。
