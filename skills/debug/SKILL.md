# Debug：排查

**角色**：排查可派（适合快执行者跑轮次）；根因后的**分流决定归协调者**。

## 铁律

**无根因调查不许提修复。**没搞清为什么坏就改代码 = 修症状不修病根，补丁只会把缺陷换个位置复活。

## 第 0 步：钉死被验对象身份

动手前确认你跑的是你以为的那个东西——哪个二进制、哪个分支、哪个提交、哪个进程。版本戳、构建缓存、linked worktree 都会说谎。**身份没钉死之前，一切观察都不可归因。**

## 第 1 步：建红色反馈回路（这一步就是本 skill 的全部，其余是机械）

找到一条命令，同时满足四项才算有回路，**没有它不许进假设阶段**：

1. **能对这个 bug 变红**——「跑起来不报错」不算，要的是能失败给你看；
2. **确定性**——偶发红先二分收敛成必现，或先把触发条件找出来；
3. **快**——秒级到分钟级，回路慢一倍，排查慢十倍；
4. **agent 可跑**——不依赖人眼看屏幕。

## 第 2 步：边界取证（多组件系统）

在每个组件边界加诊断日志（统一前缀如 `[DEBUG-xxxx]`，便于最后一把 grep 清干净），完整跑一遍，先定位**断在哪一层**，再进那一层查。不许在没有取证的层里凭感觉翻代码。

## 第 3 步：假设纪律

- 列 **3~5 个可证伪的假设**并排序——只有一个假设 = 锚定了第一直觉；
- 一次实验只改**一个变量**；
- **归属判据看失败原文**：谁在报错、报的什么，比「我的改动碰没碰那里」可信——「不是我干的」≠「没有 bug」，摘清归属的实验证明不了性质。

## 常见形状（先认形状再动手）

- **偶发红**：判据大概率取了中途副产物（代理条件）；反面断言是稳定假绿的温床。
- **环境假红**：沙箱/权限/平台差异有固定形状（负向权限断言在 root 下全红、路径长度上限、HOME 不可写）；按形状认，认不出就在环境内外对跑同一命令。
- **测试全绿但功能不生效**：夹具编码了错误的行为假设——转 acceptance 的真机规则，不在机内空转。

## 熔断与出口

- **3 次修复失败 = 架构问题，禁止第 4 次尝试**：停下写清三次各改了什么、怎么失败的，上报。
- 修复必须先有**复现该 bug 的失败测试**（接 implement 的 TDD 铁律）；若代码里**不存在能写这条回归测试的接缝——这本身就是发现**，按架构债立卡，不硬塞测试。
- **根因后分流（协调者决定）**：一两行小修顺手修掉；架构级修复回 spec/contract 定性，不许在排查现场顺手动架构。
- 收尾：`[DEBUG-xxxx]` 日志一把清干净，排查结论（根因、证据、分流决定）落卡。
