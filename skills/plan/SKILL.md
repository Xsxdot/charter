# Plan：实现计划

**读者假设**：执行者对代码库零上下文、品味存疑。计划要让这样的人不猜也能做对。

**L3 重档的归属改变**：plan 编写权下放子系统执行者（依契约 + 子系统文档自写），审核权上收协调者——只审「是否越出契约、判据能否在基线跑通」，不审实现细节。

## 格式铁律

- 每个 task：精确文件路径、完整代码块、Interfaces（Consumes/Produces 带精确签名——执行者只看得见自己的 task，这是他知道邻居用什么名字的唯一途径）。
- 步骤粒度 2~5 分钟一动作。红绿模板（写失败测试 → 跑红 → 最小实现 → 跑绿 → 提交）**只套在锁缝断言的步骤上**——内部实现、日志、注释、纯映射步骤不配独立红绿周期（范围见 implement 铁律）。
- **无占位符**：TBD /「加适当的错误处理」/「同 Task N」/ 描述做什么却不给代码——都是 plan failure，同重于交白卷。正当出口一条：测试必须复用既有夹具/harness 而其形态因包而异时，允许以「断言逐条列全（每条可判 pass/fail）+ 指认要照抄的既有 harness（文件名）」代替完整测试代码；此例外必须在占位符扫描节自我声明，无声明的骨架测试仍是 plan failure。

## 每个实现类 task 必含的步骤

1. **判据先在基线跑**：验收命令与预期在动手前于基线复核过——判据错的代价大于实现错，且它写下时对、隔几天就不对。**绿地项目的基线 = 依赖库与契约对侧的源码**：计划中引用的每条库行为事实（读限、超时、默认配置）必须带出处（文件:行）或最小验证程序；凭记忆写「关键坑」即 plan failure——库会升级，记忆里的坑可能早已被库自己填平。现状签名与调用面的查证，项目有代码图时优先 `codegraph sym / who-calls`，未命中再 grep 并记覆盖债。

   **判据要钉住行为，不钉住计数。**写下一条计数型判据（「文件数 41→50」「覆盖率 ≥80%」
   「新增 ≥N 行」）之前先自问：**满足它的最省力方式是什么，那个方式达成目标了吗。**
   实测反例：判据写「cmd/ 图内文件数 41→50」，执行者补了 40 个**零边**节点，文件数精确
   达标，而 who-calls / chain 查这些命令依然一无所获——判据要代理的是「命令进图可查」，
   它钉住的却是「文件名出现过」。计数是可数的、可满足的，且与目标往往只有相关性没有因果性。

   **跨仓判据落笔前，先确认目标仓钉的依赖版本里真有这个能力。**尤其是自己刚在上游加、
   尚未发版的东西，最容易想当然。实测反例：判据写「anchor-off-\* warn = 14」，而目标仓
   钉的依赖版本里根本没有这个类型，执行者查证后如实标「未验证」——处置正确，错在判据。
2. **测试范围声明（最小化）**：写明本 task 跑什么测试、只跑触及包。全量测试不属于任何单个 task（见 implement 三段律）。
3. **加关键节点日志**步骤：入口带输入、外部调用前后、每条错误分支带上下文、成功路径不静默；用项目的结构化 logger，禁 print。
4. **加注释**步骤：新文件头写职责+边界；导出函数写参数/返回/注意事项；非显然逻辑写「为什么」。

缺 3、4 即 plan failure——可观测性是交付的一部分，不是事后项。

**最薄路径条**：本卡要锁的行为若今天从声明缝调用**还得不到断言的预期结果**（测试写下去会红，或缝调不到），task DAG 第一条必须是点亮该行为的最薄可跑路径；写下去就会绿的才免除。缝上存在旧响应/旧功能不构成免除；L3 重档直通竖切的写死结果也不构成后续子卡的「已有活路径」。

## 五项检查（实现类 plan 出稿后自审，缺一即 plan failure）

1. **缺陷族对抗审查**：按 `defect-families` 逐族设问，结论进验收栏。
2. **序列化边界设问**：新增数据字段从产生到消费之间**每一处手写序列化/投影**（手搭 map、DTO 转换、CLI 拼输出、跨语言另一侧）列进文件清单并加断言；「两端各自有测试」≠「这条链路有测试」——必须有一条穿过真实序列化边界的回归测试，用可空类型区分「字段缺失」与「值为零」。推荐武器：roundtrip 属性测试（随机构造输入，断言 encode∘decode 恒等）——一条属性顶一族手写用例，且自动覆盖缺失/零值分辨。
3. **上下文预算检查**：每个 task 圈得出有界文件集？圈不出先插竖切卡（架构法第三条）。
4. **类型标注**：边界型子系统 task 的行为验收写成显式真机清单。
5. **接缝覆盖（双向，对照 spec 测试决定的接缝清单）**：
   - **测试 → 缝**：每支测试的**入口调用符号**在清单某条缝上、或调用链穿过该缝——看入口不看标注；标注「属于某缝」而入口不符即 plan failure，不得降格为内部锁。
   - **缝 → 测试**：清单**每条缝至少被一支缝级断言锁住**；锁不住的要么提请删缝（缝清单修订走 review 冻结物触碰行留痕），要么 task 缺了。两个方向不互相代替。
   - **内部锁**（入口不在任何缝上的测试）**默认非法、只能附加、不能顶替**：每个实现类 task 至少一条缝级断言；合法理由的唯一形状是「**从声明缝构造不出这条断言** + 为什么构造不出」——「更短 / 更纯 / 无 IO / 好写表驱动」不构成理由；逐条在占位符扫描节自我声明，无声明即 plan failure。
   - **退路同闸**：步骤正文里的条件退路（「若意外先绿就改成直喂 X」）若会改变某支测试的入口符号，同样过本闸——未声明的退路即未声明的内部锁，要么当场按内部锁声明理由，要么删掉退路。

## 跨卡审计（L3 重档，扇出前法定步骤）

各子卡 plan 齐稿后、派发前，plan 集合必须过一次**独立上下文**的跨卡审计——本地=派 subagent 审，单上下文兜底=自审可以但结论一律「待拍板」；出稿者不得自批，与 breakdown 的出稿/拍板分离同款。审三样，都是单看任何一份 plan 看不见的：

1. **对照冻结物逐条**：每份 plan 引用的契约条目与冻结物原文核对（签名、口径、注释里的行为约定）——plan 与冻结物矛盾时执行者无从裁决，只会各按各的写；
2. **跨卡签名逐字比对**：A 卡 Produces 与 B 卡 Consumes 的每个签名逐字符对齐——结构化类型匹配不容参数类型别名的差异，「大致一样」集成期必编译失败；
3. **spec 故事逐条归属**：每个用户故事指到具体卡的具体 task，指不到的就是没人做——「每张卡各自过了 spec 覆盖」罩不住跨卡落空。

## 派发前自审

计划里凡有需要**驱动派发系统自身**的验收步骤，标注「本 task 由协调者执行，不派发」——它与执行者纪律的「不派发、不调派发 CLI」直接冲突，派出去等于没验。

## 红线

- **边干边落台账**：每确立一个事实就往台账文件追加一行——提交、跑过的命令与原始输出、放弃的尝试、做出的判断。不要攒到回合结束再写：回合可能不会有结束。台账是仓内文件，与本节点产出物同批提交；落点随项目约定，无约定时与产出物同目录。

- **本节点的产出物是计划文档，不是实现代码**：不写实现、不建脚手架、不「顺手把活干了」。同场 prompt 里出现实现级验收判据（真机清单、「没跑到结果不许写 pass」）时，那是 implement 节点的完成标准——plan 节点的完成标准只有一条：计划落盘且自检通过。两者冲突时以本条为准，不以判据为由越节点。
- **依赖的输入（spec、契约文档等）缺失或读不到时，提问，不自造**：远程执行发工单问协调者，本地执行问用户；绝不自写一份替代、不凭记忆补设内容——自写的输入会让后续所有节点建立在虚构之上。

## 自审三查

spec 覆盖（逐条能指到 task）；占位符扫描；跨 task 类型/签名一致性。
