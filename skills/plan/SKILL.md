# Plan：实现计划

**读者假设**：执行者对代码库零上下文、品味存疑。计划要让这样的人不猜也能做对。

**L3 重档的归属改变**：plan 编写权下放子系统执行者（依契约 + 子系统文档自写），审核权上收协调者——只审「是否越出契约、判据能否在基线跑通」，不审实现细节。

## 格式铁律

- 每个 task：精确文件路径、完整代码块、Interfaces（Consumes/Produces 带精确签名——执行者只看得见自己的 task，这是他知道邻居用什么名字的唯一途径）。
- 步骤粒度 2~5 分钟一动作：写失败测试 → 跑红 → 最小实现 → 跑绿 → 提交。
- **无占位符**：TBD /「加适当的错误处理」/「同 Task N」/ 描述做什么却不给代码——都是 plan failure，同重于交白卷。

## 每个实现类 task 必含的步骤

1. **判据先在基线跑**：验收命令与预期在动手前于基线复核过——判据错的代价大于实现错，且它写下时对、隔几天就不对。**绿地项目的基线 = 依赖库与契约对侧的源码**：计划中引用的每条库行为事实（读限、超时、默认配置）必须带出处（文件:行）或最小验证程序；凭记忆写「关键坑」即 plan failure——库会升级，记忆里的坑可能早已被库自己填平。
2. **测试范围声明（最小化）**：写明本 task 跑什么测试、只跑触及包。全量测试不属于任何单个 task（见 implement 三段律）。
3. **加关键节点日志**步骤：入口带输入、外部调用前后、每条错误分支带上下文、成功路径不静默；用项目的结构化 logger，禁 print。
4. **加注释**步骤：新文件头写职责+边界；导出函数写参数/返回/注意事项；非显然逻辑写「为什么」。

缺 3、4 即 plan failure——可观测性是交付的一部分，不是事后项。

## 四项检查（实现类 plan 出稿后自审，缺一即 plan failure）

1. **缺陷族对抗审查**：按 `defect-families` 逐族设问，结论进验收栏。
2. **序列化边界设问**：新增数据字段从产生到消费之间**每一处手写序列化/投影**（手搭 map、DTO 转换、CLI 拼输出、跨语言另一侧）列进文件清单并加断言；「两端各自有测试」≠「这条链路有测试」——必须有一条穿过真实序列化边界的回归测试，用可空类型区分「字段缺失」与「值为零」。
3. **上下文预算检查**：每个 task 圈得出有界文件集？圈不出先插竖切卡（架构法第三条）。
4. **类型标注**：边界型子系统 task 的行为验收写成显式真机清单。

## 跨卡审计（L3 重档，扇出前法定步骤）

各子卡 plan 齐稿后、派发前，plan 集合必须过一次**独立上下文**的跨卡审计——本地=派 subagent 审，单上下文兜底=自审可以但结论一律「待拍板」；出稿者不得自批，与 breakdown 的出稿/拍板分离同款。审三样，都是单看任何一份 plan 看不见的：

1. **对照冻结物逐条**：每份 plan 引用的契约条目与冻结物原文核对（签名、口径、注释里的行为约定）——plan 与冻结物矛盾时执行者无从裁决，只会各按各的写；
2. **跨卡签名逐字比对**：A 卡 Produces 与 B 卡 Consumes 的每个签名逐字符对齐——结构化类型匹配不容参数类型别名的差异，「大致一样」集成期必编译失败；
3. **spec 故事逐条归属**：每个用户故事指到具体卡的具体 task，指不到的就是没人做——「每张卡各自过了 spec 覆盖」罩不住跨卡落空。

## 派发前自审

计划里凡有需要**驱动派发系统自身**的验收步骤，标注「本 task 由协调者执行，不派发」——它与执行者纪律的「不派发、不调派发 CLI」直接冲突，派出去等于没验。

## 自审三查

spec 覆盖（逐条能指到 task）；占位符扫描；跨 task 类型/签名一致性。
