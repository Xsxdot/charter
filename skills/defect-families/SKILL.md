# 缺陷族法

对每个触及的模块/子系统**逐族正面设问**，结论写进验收栏。不许一句「无风险」带过；无风险的写「无，因为……」——把关者判的是审查够不够、漏没漏族，一句话结论没法判。

## 通用五族

| 族 | 对抗设问 |
|---|---|
| **生命周期 / 状态机中断** | 本操作中途宿主进程重启会怎样？谁负责收尾？孤儿资源（进程/工单/临时目录）由谁、何时回收？ |
| **静默失败 / 误导报错** | 每条错误路径的传播契约是什么？失败时用户看到的信息可行动吗？存在「报成功但没做」的窗口吗？ |
| **跨平台假设** | 本改动哪些假设在其他目标平台不成立（路径、进程组、权限模型、webview）？ |
| **假红 / 假绿测试** | 验收判据是不是中途副产物？有没有反面断言（稳定假绿的温床）？负载/并发下会不会翻红？夹具里的行为假设有没有真机项对应？这支测试锁的是**调用方依赖的行为**还是内部帮手——换实现、不改需求，它会不会无意义地红？ |
| **门禁绕过** | 新增的写路径/执行路径过没过权限门？门覆盖的是全部表面还是一部分？同一规则的所有入口共享同一道门吗？检查与动作之间有窗口吗——并发下门还关着吗（TOCTOU）？ |

## 追加设问（凡命中必答）

- **序列化边界**：新增数据字段从产生到消费之间，**每一处手写序列化/投影**（手搭 map、DTO 转换、CLI 拼输出、跨语言契约另一侧）都列进文件清单并加断言了吗？「两端各自有测试」≠「这条链路有测试」——必须有一条穿过真实序列化边界的回归测试，用可空类型区分「字段缺失」与「值为零」。推荐武器：roundtrip 属性测试（随机构造输入，断言 encode∘decode 恒等）——一条属性顶一族手写用例，且自动覆盖缺失/零值分辨。
- **枚举新值过既有白名单**：新引入的枚举取值（新状态名/事件类型/kind）流经的**每一处既有校验器/白名单/switch** 都确认登记了吗？两侧入口各自绿、中间一处白名单挡死，是「通道分裂」的标准形状。
- **承重安全属性有测试锁住**：一次性（token 用后作废）、唯一性、隔离这类安全属性，每条有没有一支**能变红的测试**锁着，还是只在实现里恰好为真？没测试锁住的属性，acceptance 的变异复验没有对应测试可红，会在后续「顺手优化」中无声失守。

## 使用规约

- 项目清单以本法为**下限**：项目清单只能加严、加族，不能屏蔽基线条目；基线新增的族与设问，自项目下一次进入拆解/plan 节点起自动并入。项目清单顶部标注「基线版本：charter@<commit>」，拆解时对不上就先对齐再答题——项目清单是基线的活分支，不是冻结拷贝。
- 各族设问答出的「行为事实」类结论（某事件走不走某通路），按 acceptance 的规则标「未验证，需真机」。
- 项目新踩的坑聚出新族时，回写项目清单；跨项目复现的族，回写本法。
