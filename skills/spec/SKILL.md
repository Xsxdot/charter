# Spec：需求成形

**角色**：协调者与用户的对话回路。**硬门：设计未获用户批准前，禁止写码、禁止建脚手架、禁止调实现类 skill。**「太简单不需要设计」是反模式——简单需求的设计可以只有几句话，但必须呈现并获批准。

## 消除承重歧义

spec 的职责不是穷举设计，而是消除**承重歧义**。先用需求自己的词试着说清：谁在什么条件下，通过什么关系或通道，使什么事实发生变化；谁能观察到什么结果。对每条关键陈述做**二解测试**：两个零上下文下游若能作出两种合理但不兼容的解释，且差异会改变可观察行为、事实归属、系统边界或不可逆成本，就是承重歧义，必须在本节点消除。

- 能从当前系统核实的是事实，自己查现存代码与契约，不拿用户当搜索引擎；属于用户意图或取舍的才上桌。
- 局部、可逆的实现选择不追问；写清由谁决定、不得越过什么边界、最终满足什么结果，即可交给下游。
- 拿不准是否承重时，只构造两种最小解释比较后果，不展开完整设计树。

**停止条件**：零上下文下游不需要替用户作出未授权的承重决定；不是把所有可能问题问完。

## 承诺清单

列出本期全部必交用户故事 S1…Sn：谁从什么真实入口触发、期望观察到什么、关键失败如何呈现、在哪个环境验证；未承诺的设想明确列入 Out of Scope。受形态或流程约束的故事引用已批准原型页面/状态或流程分支及其版本。故事 ID 与 spec 修订号贯穿 plan、子卡和验收；范围变化留痕，不把欠交改名为新需求。**承诺清单不能压成第一条演示。**

每条故事的验证入口要有**真实消费者**：存量符号给调用方与出处，新建符号写明由谁消费、从哪个边界进入，不写死签名。只为在本机走满分支而抽出的、无生产调用方的纯函数，不得占据验证入口名额（可做局部测试，不能代替故事验收）。缝的对面是外部格式/协议时，其解析/编码入口即缝上符号，表驱动测试视为穿过该缝。

## 对话纪律

- **一次只问一个问题**；话题需要展开就拆成多问。
- **事实归你查，决策归用户**。
- **只有确认存在承重岔口时才给方案**：给推荐与必要备选，不凑数量；上桌前对照已冻结契约与产品不变式，不相容的不上桌或标「需改契约」；YAGNI 无情地砍。
- 追问由未消除的承重歧义驱动，不按固定次数；只剩一种承重解释时立即停止。
- 用户的原方向是默认项。想改用户方向必须举证，且这个决定**永不自决**。

## L3 增段：架构形状与接缝语义

跨子系统需求在此定目标边界：子系统职责、权威状态归属、允许的依赖方向、公开面与生产组装关系（判据见 `architecture-law`）。**定语义，不抢写新签名**：跨子系统的规则在哪一层收口、允许新增哪些依赖方向、事件/数据从谁流向谁，是本节点的设计决定；本次新建内部接缝的精确签名/端点/类型是代码事实，在首故事实现中形成，只有被独立工作单元共同依赖或构成新的对外兼容承诺时，才由 plan 的「需冻结的外部承诺」节冻结。接缝缺陷不属于任何单个子系统，只有跨子系统视角能看见它——spec 的对话正是这个视角。

**选首故事**（L3）：从完整清单选一条高价值、能尽早暴露承重未知的最薄故事，说明它验证什么、哪些工作依赖这个结论。它沿已批准边界做真实生产竖切；故事跑通但新增路径穿透他方内部，不能作为后续子卡的共同基线。

## 定级（收尾法定步骤，只判一次）

按**定稿范围**判，判决写进 spec 头部，覆盖入口时的直觉预判。两问：改动跨几个子系统的契约面？动不动契约层——实现或对接一个已存在的跨仓/跨进程 wire 契约，即便本侧零修改，也按「动」计。

| 答案 | 级 | 路由 |
|---|---|---|
| 单子系统、不动契约，且 L1 两判据全中 | **L1** | implement → review → finish（spec 即 plan） |
| 单子系统，不动契约 | **L2** | plan → implement → review → finish |
| 跨子系统，或动（含对接）跨子系统契约 | **L3** | plan（含拆分与接缝）→ 单卡或子卡各走 implement → review → finish；扇出时父卡最后 review（全部故事）→ finish |

**L1 两判据**（都命中才是 L1）：①**plan 增量为零**——spec 末尾三行（改哪个文件、怎么验收）就是全部实现决定，三行写不完就不是 L1；此时同一份 spec 挂 `spec:` 与 `plan:` 双附件过 implement 门；②**验收一眼可核**。L1 省的是文档不是纪律：批准硬门与 implement 的测试纪律照走。只命中①的按 L2，可由用户在状态行裁决跳 plan。

**L3 是否扇出子卡**：单子系统工作量超过流程固定成本（实测约 70 分钟）才扇出，且只在既有边界上、一批不超过两张，新缝先由首故事串行长出；否则一张卡单轮交付。**判错了走跨流迁移**：带着已产出的东西显式迁移并留痕，不重建卡（重建丢事件流，审计链断裂）。

## 格式骨架

```
问题陈述 / 级别 / 方案（含弃选与理由）/ 落位三问（全级别）/ 全部必交用户故事（编号与验收依据）/
目标架构与接缝语义（L3）/ 首故事选择（L3 扇出时）/ 实现决定 / 测试决定（真实入口与风险）/
Out of Scope（必写）/ 备注
```

**落位三问（L1/L2/L3 全级别必答，各一行，判据见 `architecture-law`）**：
① **读写谁的权威数据**——归该领域；两个领域都要写 → 编排单元（第六条）；有独立责任/生命周期/消费者 → 新子系统（第一条、第五条）。
② **谁消费**——同子系统内领域 → 导出符号；另一子系统或另一进程 → 契约面 + client（第四条）。
③ **同步还是异步**——按第十二条三问作答。
答案的权威载体是项目仓的架构文档（数据归属表、允许的依赖方向、同步/异步表）；项目还没有这份文档时，本 spec 的三行答案即其第一版，交棒时提示建文档。

落点判据是**可见性**：实现决定段可写决策级落点（哪层收口、谁依赖谁）与用户可见的名字（命令名、配置键、错误文案）；内部符号名与文件路径禁写——这个名字改掉用户能察觉吗？不能的归 plan。存量项目用于消歧的现状事实必须带 `文件:行` 出处并标为现状读数，由执行节点复核；绿地项目不虚构。代码片段只保留承载决策的形态片段（状态机、schema、类型骨架）。

**边干边落台账**（纪律见网关「台账纪律」节）：裁决与结论回写 spec 正文，实验过程与原始读数进台账，正文只留一行指针。

## 收尾自检与交棒

1. **零上下文复读**：TBD/含糊需求清零；每条关键陈述至多一种承重解释；交给下游的事项写清决策者、边界与结果；
2. **骨架各段齐全**，落位三问三行齐全且条号引用正确，Out of Scope 不许空；全部故事与原型/流程版本可追溯，验证入口有真实消费者；
3. **按定稿范围复核定级**，判决已写进头部；
4. L3：职责、权威状态、依赖方向与组装关系可供首故事实现；内部新缝未抢写精确签名；
5. **残余落账**：Out of Scope 逐条分「永不做」与「本期不做、后续要做」，后者逐条落 `docs/roadmap.md`（仓库级残余账本：一行一条、注明来源；下一期开工 = 从 roadmap 取条目重走 spec 门）。推迟项只活在 OOS 一行里会话一断就成孤儿。

然后用户审文件；**批准即回写**——批准判决与日期写回 spec 头部状态行，不许只活在对话里。回写后交棒：L1 → implement；L2/L3 → plan。**批准前禁止任何实现动作**。
