# Spec：需求成形

**角色**：协调者与用户的对话回路。**硬门：设计未获用户批准前，禁止写码、禁止建脚手架、禁止调实现类 skill。**「太简单不需要设计」是反模式——简单项目的设计可以只有几句话，但必须呈现并获批准。

## 对话之前：事实调查

- **需求名词现状核查**：需求原话里的每个终端、执行主体、通道（「移动端」「客户端」「后台」……），动问之前先查现状代码确认它今天以什么形态存在。不存在的、或与既有契约冲突的，作为承重接缝**第一批上桌**——同一个名词在不同人脑中是不同的东西，这是 spec 阶段最贵的一类歧义。
- **对侧既有承诺盘点**：契约对侧已存在时（跨仓/跨进程），对侧的 README 配置示例、集成测试骨架、包注释就是**对侧单方面写好的验收清单**。发 spec 前逐条盘点；要砍掉其中任何一条承诺，必须显式写进 Out of Scope 并说明对侧哪些既有测试/文档会因此失效，不得默默砍。

## 对话纪律

- **一次只问一个问题**。话题需要展开就拆成多问。
- **事实归你查，决策归用户**：环境事实（现状代码怎么写的、依赖什么版本）自己查或派 agent 查，永远不要拿用户当搜索引擎；只有取舍才上桌。
- **提 2~3 个方案，带取舍，先给推荐**。上桌前每个方案先对照**已冻结契约与产品不变式**过一遍相容性：不相容的方案不上桌，或显式标注「需改契约」——推荐一个与产品承诺相悖的方案，比不推荐更糟。YAGNI 无情地砍每个方案。
- **第一个回答默认是修饰过的**：关键取舍追问两三次才是真话。
- 用户的原方向是默认项。你想改用户方向时必须举证，且这个决定**永不自决**。

## L3 增段：契约语义与接缝

跨子系统需求在 spec 阶段就要定契约——**定语义，不定签名**：

- **定得了的（设计决定）**：哪些规则跨子系统、在哪一层收口、允许新增哪些依赖方向、事件/数据从谁流向谁。
- **定不了的（代码事实）**：精确签名/端点/类型——那要查现状代码，归 contract 节点落地。硬在 spec 里写死签名会写出对不上现状的契约。

接缝缺陷不属于任何单个子系统，只有跨子系统视角能看见它——spec 的对话正是这个视角，用满它。

## 测试接缝对齐

发 spec 前勾勒测试将落在哪些接缝上。**接缝越少越好，理想是一个**（最高的可测缝）。这决定后续所有节点的测试预算落点。

## 定级与选档（收尾法定步骤）

定级在信息足够的时刻只发生一次——就是现在，按**定稿范围**判，判决写进 spec 头部（级别/档位），覆盖入口时的任何直觉预判。

**定级两问**：

1. **改动跨几个子系统的契约面？**（子系统判据见架构法第一条；绿地项目按 spec 定稿后将产出的子系统划分数，不按「仓库个数」）
2. **动不动契约层？**——**实现或对接一个已存在的跨仓/跨进程 wire 契约，即便本侧零修改，也按「动契约层」计**：单侧冻结的契约恰恰是查证纪律最不能省的地方。

| 答案 | 级 | 路由 |
|---|---|---|
| 单子系统，不动契约 | **L2** | plan → implement → review → acceptance → finish |
| 跨子系统，或动（含对接）跨子系统契约 | **L3** | contract → breakdown →（选档） |

**L3 选档，判据一条：单子系统工作量是否超过流程固定成本（实测约 70 分钟）。**超过 → 重档（各子系统并行子卡 + 集成）；不超过 → 轻档（拆解与契约冻结照做，实现归一轮）。「规模适中」是轻档的信号，不是重档的。**轻档不许跳契约冻结**——试点数据表明价值在契约那半段，不在扇出。

**判错了怎么办**：定级允许错，纠错动作是**跨流迁移**——带着已产出的东西显式迁移到正确的流并留痕，不是重建卡（重建丢事件流与关系边，审计链断裂）。跨子系统性藏不过拆解，判错通常在 breakdown 现形。

## 格式骨架

```
问题陈述 / 级别与档位 / 方案（含弃选与理由）/ 用户故事（编号列表）/
契约语义与接缝（L3）/ 实现决定 / 测试决定（接缝清单）/
Out of Scope（必写——显式的不做与做同样值钱）/ 备注
```

不写具体文件路径与代码片段（很快过时）；唯一例外：承载决策的形态片段（状态机、schema、类型骨架）。

## 收尾

spec 落盘 → 自审（占位符/矛盾/歧义/范围 + **按定稿范围复核定级与选档**）→ 用户审文件 → 批准后交棒：L2 → plan；L3 → contract。
