# Spec：需求成形

**角色**：协调者与用户的对话回路。**硬门：设计未获用户批准前，禁止写码、禁止建脚手架、禁止调实现类 skill。**「太简单不需要设计」是反模式——简单项目的设计可以只有几句话，但必须呈现并获批准。

## 对话之前：消除承重歧义

spec 的职责不是穷举设计，而是消除**承重歧义**。先用需求自己的词试着说清：

> 谁在什么条件下，通过什么关系或通道，使什么事实发生变化；谁能观察到什么结果？

这是一句试读，不是格式模板，也不预设终端、房间、消息、身份等固定栏目。对每条关键陈述做**二解测试**：

- 两个零上下文下游若能作出两种合理但不兼容的解释，且差异会改变可观察行为、事实归属、系统边界或不可逆成本，就是承重歧义，必须在 spec 阶段消除。
- 能从当前系统核实的是事实，自己查现存代码与现存契约；不存在的未来文档不查、不假定。属于用户意图或取舍的，一次只问一个问题。
- 局部、可逆的实现选择不追问；只有写清**由谁决定、不得越过什么边界、最终满足什么结果**，才可交给下游决定。
- 拿不准是否承重时，只构造两种最小解释比较后果，不展开完整设计树。

**停止条件**：零上下文下游不需要替用户作出未授权的承重决定；不是把所有可能问题问完。

**承诺清单不能压成第一条演示。**列出本期全部必交用户故事 S1…Sn：谁从什么真实入口触发、期望观察到什么、关键失败如何呈现、在哪个环境验证；未承诺的设想明确列入 Out of Scope。每条受形态或流程约束的承重步骤引用已批准原型页面/状态、流程分支及其版本，后续 review/acceptance 要拿实际运行证据与该版本对照，不能只看摘要。故事 ID 与 spec 修订号贯穿 plan、子卡和最终验收；范围变化留痕，不把欠交改名为新需求。

**选 Wave 0**：从完整清单选一条高价值、能尽早暴露承重未知的最薄故事，说明它验证什么、哪些工作依赖这个结论。身份、路由、恢复等若是该故事成立的必要条件，验证相应反例；未覆盖的独立未知另排窄实验或阻塞依赖它的扇出。已充分验证的存量路径可复跑复用，不为走流程重写。

- **有图先查图**：项目有 `codegraph/` 时先查图，未命中再 grep，未命中符号记「图覆盖债」。
  - 领域从哪下手 → `codegraph context <领域>`（`<领域>` 必须是 best 领域 id；现状 id 会被拒并报它在最优树里的分布——分布非单值，不代为改写。无 best 时降级为现状词表并在错误里注明。声明缺失不是错误，仍返回机械字段并以 warning 指向声明路径。响应 `actual` 披露实然归属与 `misplaced`/`misplacedSkipped`，应然≠实然。截断看 `truncated` / `fociTruncated`。）
  - 已经有名字 → `codegraph sym`
  - 这个方法怎么走 → `codegraph flow`（有序控制流：`call`/`branch`/`loop`/`return`。无数据则 `degraded` 且 `steps` 空，然后读源码。**禁止拿 `chain` 冒充。** 参数是方法名或节点 id，不带 `--with-source`；源码窗口用 `sym` / `chain --with-source`。）
  - 沿哪条路径下去 / 上来 → `codegraph tree` / `tree --up --through --from`（真树；菱形按路径重复。`--from` 必须搭配 `--through`。）
  - 碰过谁（切片）→ `codegraph chain` / `who-calls`（无次序、无分支。默认瘦身、外部领域折叠、共享内核收桩；旧形态显式 `--full`，`--full` 不关闭源码窗口或预算。）
- **调用链 ≠ 流程图。** `chain` / `context` 的主链是无序可达邻域。`flow` 的主语是对外契约方法（入缝 / 紫框目标 / 右栏实现），不是 CLI/HTTP/WS 通道。通道只说明怎么到达该主语；不要对 `GET /console` 这类通道跑 `flow`，先 `sym` / `who-calls` 找到它调进去的方法。
- **符号锚**：spec 引用现状代码时同 contract/breakdown 一样推荐 `file#Symbol` 符号锚（行号必漂，符号锚由 `codegraph resolve` 查询时决议）；出稿自检可跑 `codegraph resolve --doc <本文档>`。

## 对话纪律

- **一次只问一个问题**。话题需要展开就拆成多问。
- **事实归你查，决策归用户**：环境事实（现状代码怎么写的、依赖什么版本）自己查或派 agent 查，永远不要拿用户当搜索引擎；只有取舍才上桌。
- **只有确认存在承重岔口时才给方案**：给出推荐与必要的备选，不为凑数量制造方案。上桌前逐项对照已冻结契约与产品不变式；不相容的不上桌，或显式标注「需改契约」。YAGNI 无情地砍每个方案。
- **追问由未消除的承重歧义驱动**，不按固定次数追问；答案只剩一种承重解释时立即停止。
- 用户的原方向是默认项。你想改用户方向时必须举证，且这个决定**永不自决**。

## L3 增段：架构形状与接缝语义

跨子系统需求在 spec 阶段先定目标边界：子系统职责、权威状态归属、允许的依赖方向、公开面与生产组装关系。**定语义，不抢写新签名**：

- **定得了的（设计决定）**：哪些规则跨子系统、在哪一层收口、允许新增哪些依赖方向、事件/数据从谁流向谁。
- **定不了的（代码事实）**：本次新建内部接缝的精确签名/端点/类型——在 Wave 0 实现中形成，确有独立协作或新增对外承诺时再由 contract 冻结。既有公开契约从开始就约束 Wave 0；新的外部承诺若是 Wave 0 真实运行的前提，先进入 contract 只冻结那条缝。

接缝缺陷不属于任何单个子系统，只有跨子系统视角能看见它——spec 的对话正是这个视角。Wave 0 必须沿已批准边界做真实生产竖切；故事跑通但新增路径穿透他方内部，不能验收为共同基线。

## 测试接缝对齐

发 spec 前勾勒本期承重行为从哪些真实入口与接缝验证。保留最有解释力的少数入口，按故事风险选择断言；mock 可用于局部验证，但不能替代声明为真机的行为证据。新增字段经过手写序列化/投影时，明确至少一条穿过该边界的验证路径。

**接缝合法性三款**（清单成形时逐条核）：

1. **每条缝标明真实消费者**。存量符号：给调用方与可查出处；新建符号：写明由谁消费、从哪个边界进入，不写死签名。实现与 review 核对生产消费链；命中 contract 时再以源码符号与提交冻结精确形状。
2. **假缝禁令**：未导出、无生产调用方、只为在本机走满分支而抽出的纯函数，**不得占据接缝清单名额**。它可以用于局部测试（架构法第四条第 2 档测试缝），但不能代替真实消费者的故事验收。
3. **边界型例外**：缝的对面是外部现实的格式/协议时（wire 格式、外部工具输出、对端载荷），其**解析/编码入口即缝上符号**，即便未导出；此类表驱动测试视为穿过该缝，不占内部锁名额。

## 定级与选档（收尾法定步骤）

定级在信息足够的时刻只发生一次——就是现在，按**定稿范围**判，判决写进 spec 头部（级别/档位），覆盖入口时的任何直觉预判。

**定级两问**：

1. **改动跨几个子系统的契约面？**（子系统判据见架构法第一条；绿地项目按 spec 定稿后将产出的子系统划分数，不按「仓库个数」）
2. **动不动契约层？**——**实现或对接一个已存在的跨仓/跨进程 wire 契约，即便本侧零修改，也按「动契约层」计**：单侧冻结的契约恰恰是查证纪律最不能省的地方。

| 答案 | 级 | 路由 |
|---|---|---|
| 单子系统、不动契约，且 L1 两判据全中 | **L1** | implement → review → finish（快道） |
| 单子系统，不动契约 | **L2** | plan → implement → review → acceptance → finish |
| 跨子系统，或动（含对接）跨子系统契约 | **L3** | 轻档按冻结条件进 contract/breakdown；重档先走 Wave 0，必要的外部承诺先冻结 |

**L1 两判据（两个都命中才是 L1，缺一按 L2）**：

1. **plan 增量为零**：把 plan 写出来只会复述 spec——spec 末尾三行（改哪个文件、怎么验收）就是全部实现决定，三行写不完就不是 L1。此时同一份 spec 文件挂 `spec:` 与 `plan:` 双附件过 implement 门，不另写 plan 文档。
2. **验收一眼可核**：review + 真机一眼即可收口，acceptance 可跳（快道）。

**L1 省的是文档，不是纪律**：spec 与批准照走（本节硬门不豁免），implement 的 TDD 纪律照常适用——所以复用 implement 节点，不设「直接实现」节点（那是一份纪律更松的 implement 副本，复制即漂移）。只命中判据 1 的按 L2 定级，可由用户在 spec 状态行裁决跳过 plan 直接实现（先例：seam-budget、C9 载体法），review/acceptance 照走。

**L3 选档，判据一条：单子系统工作量是否超过流程固定成本（实测约 70 分钟）。**超过 → 重档（先 Wave 0，再按故事增量分批扇出与集成）；不超过 → 轻档（拆解后归一轮实现）。「规模适中」是轻档的信号，不是重档的。档位不决定是否冻结：只有本轮新增/变更的接缝被独立工作单元共同依赖，或涉及新的对外兼容承诺时才进 contract；复用既有契约不重复冻结。

**判错了怎么办**：定级允许错，纠错动作是**跨流迁移**——带着已产出的东西显式迁移到正确的流并留痕，不是重建卡（重建丢事件流与关系边，审计链断裂）。跨子系统性藏不过拆解，判错通常在 breakdown 现形。

## 格式骨架

```
问题陈述 / 级别与档位 / 方案（含弃选与理由）/ 全部必交用户故事（编号与验收依据）/
目标架构与接缝语义（L3）/ Wave 0 选择（重档）/ 实现决定 / 测试决定（真实入口与风险）/
Out of Scope（必写——显式的不做与做同样值钱）/ 备注
```

不写**未来落点**的文件路径与实现片段（很快过时）。**落点判据是可见性**：实现决定段可写决策级落点（哪层收口、谁依赖谁）与用户可见的名字（命令名、配置键、错误文案——它们是产品决策）；内部符号名与文件路径禁写——判据一句话：**这个名字改掉，用户能察觉吗？**不能察觉的都是落点，归后续 plan/实现，命中冻结时再交 contract。**现状事实引用相反：存量项目中用于消歧的现状事实必须带 `文件:行` 出处**，标注为现状读数，由执行节点在本轮工作树复核；绿地项目没有现状证据时不得虚构或寻找尚未产生的文档。代码片段的唯一例外仍是承载决策的形态片段（状态机、schema、类型骨架）。

**边干边落台账**：每确立一个事实就往台账文件追加一行——提交、跑过的命令与原始输出、放弃的尝试、做出的判断。不要攒到回合结束再写：回合可能不会有结束。台账是仓内文件，与本节点产出物同批提交；落点随项目约定，无约定时与产出物同目录。**提交事实的记法**：把提交当时的命令与原始输出追加进台账（历史读数），随后只 amend 一次收进同批提交。amend 会换 hash——这是 git 的事实，不是漏记。禁止把 amend 后的 HEAD 写回台账再 chase；收口判据是工作树干净，不是文件里的 hash 等于 HEAD。**裁决/过程分界**：裁决变更与结论回写 spec 正文（含修订留痕）；实验过程与原始读数（盲测、对照组、重测数据）进台账，spec 正文只留结论与一行台账指针——备注段不是实验账本。

## 收尾自检与交棒

spec 落盘后逐项自审，缺项就地补，补完不必重审：

1. **零上下文复读**：TBD/待定/含糊需求（「适当处理」「等等」）清零；每条关键陈述至多一种承重解释；交给下游决定的事项已写清决策者、边界与结果；
2. **骨架各段齐全**：尤其 Out of Scope 不许空；全部必交故事与原型/流程图版本可追溯，测试入口有真实消费者，假缝禁令核过；
3. **按定稿范围复核定级与选档**，判决已写进头部——入口时的直觉预判此刻作废；
4. L3：职责、权威状态、依赖方向与组装关系可供 Wave 0 实现；内部新缝未抢写精确签名，冻结理由与时点已按真实依赖说明；
5. **读数分界**：实验过程与原始读数已移台账、spec 正文只留结论与指针（分界见格式骨架节的「裁决/过程分界」）；
6. **残余落账**：Out of Scope 逐条分类——「永不做」与「本期不做、后续要做」；后者（尤其被裁掉的愿景主语）逐条落进 `docs/roadmap.md`（没有就建）。roadmap 是仓库级残余账本：一行一条的有序期队列，每条注明来源（哪份 spec/哪个缺口）；排序判据两行——先骨架后血肉、每期以可真机验收为界。下一期开工 = 从 roadmap 取条目重走 spec 门。推迟项只活在 OOS 行里，会话一断就成孤儿（实测：两轮绿地项目的「移动端」都死在 OOS 一行字里）。

然后用户审文件；**批准即回写**——批准判决与日期写回 spec 头部状态行，不许只活在对话里（实测：两轮项目的 spec 头部都停在「待用户批准」，而下游文档全按「已批准」跑完了全程）。回写后交棒：L2 → plan；L3 轻档 → breakdown（若需新增外部承诺，先 contract）；L3 重档 → Wave 0 plan（若所选故事依赖新外部承诺，先 contract）。**批准前禁止任何实现动作**（硬门在本节点开头，此处是最后一次执法点）。
