# Breakdown：拆解

**角色**：**跨子系统单 agent 出稿，协调者把关拍板。**拆解必须在一个上下文里跨所有触及子系统——接缝缺陷不属于任何单个子系统。输入为已批准 spec 的全部故事与目标架构、适用的既有契约、已验 Wave 0 基线（重档）和确曾命中的冻结物；没有新增冻结对象时，不要求空 contract。你的上下文是这些边界材料与各子系统文档，不是全量代码。

**你的全部产出都是提案。**凡「有两种做法、选哪种取决于偏好」的岔口，把方案与取舍都写出来标注「待拍板」，不要自己选一个往下写。

## 执行形态（出稿者与拍板者必须是不同上下文，三种载体各自成立）

1. **本地（Claude Code 主会话）**：主会话**派 subagent 出稿**（注入本 skill 正文），主会话只拍板。两个理由：拍板者不被出稿者的自我合理化污染；拆解要吞契约层与各子系统文档，别烧主会话的上下文。
2. **handoff 派发**：executor 出稿（本文即纪律块），本地协调者拍板。
3. **单上下文兜底**（无 subagent 机制的执行者）：允许自己出稿，但**一切岔口一律「待拍板」、禁止自批**——出稿完成即停，把提案完整交还拍板者。**援引本条前先核实 subagent 机制确实不存在**；因某条约束降级的，降级声明必须逐字引用该约束的出处（文件+行，或用户原话），引不出即约束不存在，按形态 1 执行。

## 产出四样

1. **触及子系统清单**：每个子系统标类型——逻辑型（接缝对面是自有代码，测试可闭环）/ 边界型（接缝对面是外部现实，机内只验契约形状，行为验收写真机清单）。有图时引用最优图 `codegraph/best.json`（`domains` 中 `parent` 为空者），无图时引用 spec 已批准的人工结构说明；按子系统独立派卡前核架构法第一条的**派卡资格四条**。

2. **边界与冻结核对**：对照 spec 架构方向、已有稳定契约和本轮实际冻结物；有冻结物则逐条核其生产者、消费者、版本及未越界，无冻结物则记录为何没有新增独立协作或对外承诺。确认 spec「已批准」、适用冻结物「已冻结」的状态可查。拆解若发现新增独立共享接缝/外部承诺，按 contract 判据回去冻结后才派发；只是同一工作单元内部可逆落点，则留给 plan/implement。澄清触及已冻结语义时回写冻结物；未触及时更新 spec/拆解的边界说明，不制造契约修订。

3. **故事映射 + 工作单元依赖**：逐条建立「故事/承重步骤 → 实现责任 → 真实消费者 → 集成与演示/回归负责人」。重档待实现部分列工程子卡及依赖 DAG；每条依赖标注是**契约/数据硬依赖**（前卡的产物或事实是后卡开工前提），还是**施工排序**（共享文件、机器、checkout 等资源冲突，解除冲突即可并行），不得把后者伪装成架构依赖。已由 Wave 0 完成的故事指向已验父卡基线与最终回归负责人，不造重复子卡。轻档写一个有界的单轮工作单元及其内部顺序，不强造子卡 DAG。每个待实现工作单元写清：①故事与适用边界/契约引用 ②意图与为什么 ③真实生产消费者及本批可演示的消费结果 ④可复核的技术验收 ⑤入口指针。共享基础工程也须指向将消费它的具体故事批次；没有真实消费者的接口/基础设施不单独派卡。纯测试卡和最终矩阵默认归故事卡或父卡最终验收；只有独立环境/数据准备构成真实硬依赖时，才说明理由另立卡。工程子卡可不单独产生用户可见结果，但不能因技术通过就宣布故事完成。
   待实现工作单元须能圈出**有界文件集**；重档子卡圈不出时先插竖切还债卡（架构法第三条），轻档圈不出时重评档位或先还债，不靠造空子卡掩盖范围。

   **行为闭环核对**：对 spec 承诺的每条跨子系统可观察行为写一行「触发者 → 权威事实/载体 → 消费者 → 可观察结果 → 实现责任」。实现责任可以是待实现工作单元，也可以是已验 Wave 0 基线；后一种仍写最终回归负责人。只核产品行为，不为内部方法单独造闭环。触发条件或结果说不清 → 退回 spec；缺载体/字段先查是否为已批准边界内的实现缺口，若需新增独立共享接缝或对外承诺才退 contract；没有实现或回归责任 → 不得推进。

4. **风险对抗审查**：用 `defect-families` 找本故事和接缝真正相关的失败族，结论写进对应子卡或父卡验收责任；「无风险」须说明依据，不为每张卡复制无关清单。

## 机内验不了的东西

凡结论依赖**行为事实**（某事件走不走某条通路、某字段实际由谁写入）而非可 grep 的 API 事实，必须显式标注「未验证，需真机」并写进真机清单，不许按推测写成结论——夹具可以编码一个不存在的世界，测试会全绿地验证它。

## 交稿自检（出稿者收尾逐项核对，缺一即稿未完成）

1. 产出四样齐全：子系统清单每个带类型、适用边界/冻结核对有结论、故事到工作单元或已验基线及集成/回归负责人映射完整、相关风险有可复核判据；
2. **「待拍板」岔口集中列成清单放稿首**——拍板者按这张清单裁决，散落在正文里的岔口等于没标；
3. 「未验证，需真机」条目已汇总成真机清单；
4. 待实现工作单元的有界文件集核过；重档子卡圈不出的已插竖切卡，轻档圈不出的已重评范围。
5. 行为闭环每行五格完整，实现与集成/回归责任确实存在；没有只活在接口、测试或无人认领格子里的承诺。依赖边已分清硬依赖和施工排序，每张工程卡有真实消费者及所属故事批次。重档后续按可集成故事增量分批，批间演示并回归已有故事。

## 拍板即提交（含回写）

协调者拍板后，拆解稿连同裁决结果随即提交入库。**拍板结果逐岔口回写进稿首待拍板清单（裁决 + 理由），头部状态行更新为「已拍板（日期）」，与裁决同批提交；状态行与裁决记录不一致视同未拍板。**产物不入库，会话一断就是孤儿（实测：一轮拆解稿以未跟踪文件形态死在工作区，`assignments` 为空，一张卡没派出去）；裁决不回写同样是孤儿（实测：两份拆解稿的裁决只活在会话、三份状态行停在「待拍板」，其中一份的实现已按无踪的裁决发生——2026-08-25 审计）。

## 红线

- **边干边落台账**：每确立一个事实就往台账文件追加一行——提交、跑过的命令与原始输出、放弃的尝试、做出的判断。不要攒到回合结束再写：回合可能不会有结束。台账是仓内文件，与本节点产出物同批提交；落点随项目约定，无约定时与产出物同目录。**提交事实的记法**：把提交当时的命令与原始输出追加进台账（历史读数），随后只 amend 一次收进同批提交。amend 会换 hash——这是 git 的事实，不是漏记。禁止把 amend 后的 HEAD 写回台账再 chase；收口判据是工作树干净，不是文件里的 hash 等于 HEAD。

不写实现代码；不建卡、不派发、不调派发工具——扇出归协调者。

**符号锚**：项目有代码图时，文档引用现状代码推荐 `file#Symbol` 符号锚（行号会漂，符号锚配 `codegraph resolve` 查询时决议）；出稿自检跑 `codegraph resolve --doc <本文档>`，坏锚即修。
