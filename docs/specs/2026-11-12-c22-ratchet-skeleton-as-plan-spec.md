## 一、问题陈述

2026-11-12 对 erp 与 pejam 两仓 11-01 19:00 之后的代码与过程审核（读数见末节）：

1. **子系统之间守住了，子系统内部在变差。**跨模块越界引用为零、组装点唯一；但 erp platform 的 `App` 方法数 11 天内 280 → 421，超 1000 行的文件 7 → 14；pejam `node/src/main.ts` 的 `startNode` 是 1395 行的单函数，窗口内被 50 个提交改过。
2. **管内部的条文没有执行点。**`architecture-law` 第三条（升格必答）、第六条（上帝对象）在 spec / plan / implement / review 正文里没有任何引用。
3. **现有检查都只看单张卡的增量。**plan 出稿者的原话是「已是大文件，本卡只加注册应答 1 处，不计；无命中」；楼层图的上帝对象判据要求「跨 > 1 层」，每模块一个 App 落在口子里；命中了也只是「标出来、裁决归人」，记成风险后照常推进。每次豁免在局部都成立，累计起来无人负责。
4. **第三条「超线拒发功能卡」无法执行。**两仓五个子系统全部超线，照做等于停掉功能开发，于是从未执行。
5. **L3 的骨架规则没被执行，L2 没有骨架。**17 张出了骨架的卡里 14 张是 plan 拍板之后才落盘，楼层图是 plan 里手画的；L2 往 App 上加方法时没有任何人决定新代码落在哪。
6. **测试与生产代码仍是 1:1。**两层测试的规则在（`implement/SKILL.md:12-13`），但分类权在实现者手里、边写边定，默认选择是多写。

7. **同一批测试被跑很多遍，并引发过载事故。**规则是卡级不跑全量、变异两处；记录在案的是 pejam 12 张抽样卡在卡级跑了 25 次 node 包全量（单次 23~35 分钟），变异最多的一张卡做了至少 91 处，审查者多数把实现者跑过的整套再跑一遍。多个会话同时跑全量导致机器过载、超时假红、再重跑。

8. **「卡只跑自己的测试、批次才跑全量」没有实现。**finish 写着「无父卡的单卡自己就是一批，两级一次做完」；11-05 之后 pejam 除一张父卡外全是单卡直进 main，于是每张卡都按批级跑了全量。攒批则要等——一批十张卡里的第一张等了约 22 小时才进 main。基线长期带着 14 条已知红，每次全量都要逐条比对新红旧红。

9. **「一律建卡」被大半的活绕开，而且没有边界。**erp 窗口内 155 个交付单元没有卡号。按个数多是小改动（生产改动中位 36 行，59% 在 50 行以内）——用户说明原因是清小 bug、调界面时走卡太重，光测试就要一小时。但按代码量，86% 来自 27 个超过 300 行的单元，最大的一个 7387 行；契约目录与迁移文件的改动大半也发生在卡外。

10. **进仓的文档九成是 agent 之间流转的。**pejam 窗口内进仓文档新增约 9.35 万行：证据 65268、plan 13622、交回物与审查报告 7737、台账 500，合计约 93%；给人批准的 spec 只有 5396 行；另有 1029 个截图与压缩包。它们进仓是因为 git 是唯一跨机器、跨会话的共享存储，不是因为有人要读。

**不是问题的**：层的选择（边缘层与持久层在两仓基本干净，第十三条不动）；跨子系统的判据。

### 2.1 超线容器只减不增

`architecture-law` 新增第十四条，把第三条、第六条已有的信号收成一个定义并给出处置：

- **超线容器**（任一命中）：单类型方法数 ≥ 20（第六条）；单包非测试源文件 ≥ 40 且无子包（第三条）；同一层目录内同前缀家族 ≥ 5 个源文件（第三条）；单文件 ≥ 1000 行（Q1）。
- **只减不增**：任何卡（含 L1 与 bug）合入后，超线容器的计数不得高于基线。新代码落在按概念命名的新类型、子包或文件里。
- **核对方式**：项目提供一条结构检查命令——读基线，输出每个超线容器的当前计数与增减，有净增即非零退出；没有命令时按 Q2。基线只许收紧，上调须用户批准并留痕。
- **例外出口**：基线里逐项豁免，每项一行理由，由人批（生成代码、纯数据表、名副其实只管一类数据的持久门面）。「本卡只加一点」不是理由。
- 第三条的处置句「答不出即先插竖切还债卡」「此时拒发功能卡」删除，改指第十四条；总则第 3 条「升格随卡走」的单位写明为「本卡要改的方法」。

### 2.2 随卡搬迁（用户定：范围不扩大）

L2 / L3 的卡要改超线容器里的方法时，**先搬后改**：

1. **范围**：本卡要改的方法，加上只被它们调用的私有方法。被别处共用的不搬，以接口注入（接口归使用方，第九条）。本卡不改的方法一律不搬。
2. **已有新家就搬进去**：同一概念已有子包或类型的，搬到那里，不另建。新家留一句包注释或文件头注释写它拥有什么。
3. **依赖单向**：老容器可以调新家，新家不得回调老容器。
4. **搬迁独立成提交，只搬不改**：既有测试不改断言即通过；先于功能改动合入。
5. L1 与 bug 不触发搬迁，只受 2.1 约束。

半迁移状态（一个家族一半在老容器、一半在新家）合法，没被卡碰到的部分不动——这是总则第 3 条「不溯及既往」的本意。

### 2.3 L2 骨架替代 plan（用户定）

- **L2 的 plan 节点产出物改为骨架提交**，不另写计划文档。骨架表达不了的三项——待拍板岔口及裁决、决策权限、真机清单（含首跑项）——由出稿者追加在 spec 末尾「实施备注」一节，仍作为交回物「偏离与自主决定」的对照基准。
- **骨架内容**：类型、接口签名、接线齐全，不写业务逻辑，每个桩一句话「做什么」（第四步原文）；另加 2.2 的搬迁提交（碰到超线容器时）与 2.4 的测试清单。L2 不出层表与楼层图，除非 spec 头部点名。
- **拍板对象就是骨架提交**（L2、L3 同）：拍板前骨架已提交、编译过、结构检查通过；「拍板后由首个工作单元落盘」不合格。出稿者与拍板者仍须是不同上下文。
- **按例外上交**：协调者审骨架 diff；交用户裁决的只有待拍板岔口与结构检查的命中项。
- 删去「L2 在 spec 头部点名『出骨架』时同样产出」；plan「五件事」表保留给 L3 子卡自写的 plan 与按需停 plan 的 bug 流。

### 2.4 测试清单进骨架（用户定）

两层测试的判据不变，决定权前移到骨架：

- **故事检查桩**：每条必交故事一个，从真实入口进，名字带故事编号。
- **不变式测试桩**：只给标注为承载规则的桩建（状态机、金额与时间计算、权限判定、序列化边界）。其余方法不写方法级测试。
- **implement 只填清单内的测试**。清单外新增测试文件须进「偏离与自主决定」，写明拦的是哪个实现中发现的真实缺陷，由 review 裁决。bug 流的复现测试不受此限。
- review 核「新增测试文件 ⊆ 清单 ∪ 已披露」。

### 2.5 搬迁方法的旧测试（用户定：有故事覆盖就删）

- 搬迁提交里旧测试跟着搬，只改引用、不改断言（它是「只搬不改」的验证手段）。
- 骨架同时给出**删除清单**：被搬方法的方法级测试里，不在不变式清单内、且其入口已有故事检查覆盖的。
- implement 在对应故事检查转绿后按清单删；没有故事覆盖的保留。
- review 核删除清单每一项对应的故事检查确实穿过该入口。

### 2.6 一次权威运行（用户定：并进 C22）

复跑的目的是拿到不由执行者书写的证据，不是把测试再跑一遍。

- **判据**：项目有按提交号可查、非执行者自述的运行记录时，审查者核对记录即为复跑——提交号与被审 diff 一致、范围覆盖触及包与本卡故事检查——不另跑。记录缺失、提交号不符或范围不足时，才由审查者自己跑。
- **implement**：完工时触发一次这样的运行（项目有此能力时），交回物引用记录指针，不抄输出。修复轮改了代码就重新触发，旧记录作废。
- **变异不变**：仍由审查者做，两层各一处；变异本身需要的运行不在此列。
- **批级全量不变**：每批一次，同样以运行记录为证据。
- **交回物末节**：有运行记录的条目只写指针（记录在哪、哪个提交），不贴原始输出。
- 没有运行记录能力的项目，现行「审查者复跑」照旧。

运行由谁触发、在哪台机器、是否排队，属项目层。

### 2.7 常设集成分支，全量只属于它（用户定：main 快进等用户点头）

批次不再事先规划：一批就是「上次全绿之后落进集成分支的所有卡」。

- **一个仓一条常设集成分支**，从 main 拉出、长期存在。所有卡过了自己的测试（触及包 + 故事级检查 + 全量编译）就落到它上面，不等别的卡。删「无父卡的单卡自己就是一批」，删「每张集成父卡一条集成分支」。
- **全量只在这条分支上跑**：按提交触发、同一时间只跑一个、结果按提交号留档（即 2.6 的运行记录）。卡不跑全量，父卡也不跑。
- **判定只有全绿与红**，不与已知红名单逐条对照。基线里现存的红先归零：修好，或显式删除并落 roadmap。
- **卡落集成分支不逐张等用户**（用户定）：review 通过即由协调者落入。现行「单卡与父卡呈现三选项并等待」只保留给 main 快进与丢弃分支两种情形；丢弃仍须用户显式确认。
- **main 只能快进到集成分支上一个全量全绿的提交，由用户点头后执行**（用户定）。用户的关口只有这一处；热修同路。
- **红了定归属**：从上次全绿以来落入的卡里找，修复作为一张卡落入；main 停在原地。
- **父卡**：扇出 L3 的父卡分支只承载自己的子卡，父卡验收通过后整体落入集成分支。父卡验收做故事核销、生产闭环核对、整体走查、回旋镖对账，不自带全量。跨子系统各改内部的多张 L2 各自直接落集成分支，父卡在集成分支头上做验收。
- 第四步与 C21 为批级全量写的「运行期间冻结被测树」「基线按 main 提交复用」随之删除：按提交跑不存在树被改动，全绿基线不需要对照。

分支叫什么、全量多久触发一次、在哪台机器跑，属项目层。

### 2.8 轻档：小改动不建卡，边界由判据守（用户定：不建卡）

「一律建卡」改为「进流程的请求一律建卡，轻档除外」。当初立这条是因为「小活可无卡」会让一切都滑成无卡；现在把口子的边界写成可机械核对的判据。

- **判据（全中才是轻档）**：①生产代码改动不超过上限（Q5），按一次落入集成分支的整体 diff 计；②不动契约面所在目录、不动迁移与持久化结构；③只在一个子系统内；④不使超线容器净增（2.1）。
- **流程**：不建卡、不出 spec、不出骨架、不做变异、不写裁决表与交回物。提交信息标明轻档并用一句话说清改了什么。
- **验收**：界面与文案类由用户看结果；bug 类保留排查节的出口——先有复现该 bug 的失败测试，「无根因不许修」不变。
- **落入集成分支时核对**：触及包测试、全量编译、结构检查，加上面四条判据。项目没有自动核对时，由协调者落入前按 diff 人工核四条。
- **超出任何一条即不是轻档**：转正常卡，按跨流迁移带产出走，不重做。
- 用户的关口不变：轻档同样只落集成分支，main 快进仍等用户点头（2.7）。

### 2.9 给人的、跨卡存活的、随卡走的（用户定）

用户定的原则：先分清哪些要人看和知道、哪些只在 agent 之间流转，再据此定进不进仓。对每样产出问三句：

1. 人要对它做决定，或需要知道它吗？——**给人的**。
2. 以后做别的卡的 agent 需要它吗？——**跨卡存活的**，进仓，尽量以代码形态存在。
3. 只是本卡内 agent 之间交接用的吗？——**随卡走的**，不进仓，挂在卡上。

| 类别 | 包括 | 放哪 |
|---|---|---|
| 给人的 | 下列六类 | 经协调者一个口子给人；其中的决定留一份进仓（spec 头部、决策记录） |
| 跨卡存活的 | 代码、测试、骨架里的注释、已批准的 spec、决策记录、roadmap、架构文档 | 进仓 |
| 随卡走的 | 交回物、审查裁决表、测试输出与运行记录、截图、L3 的 plan 文档 | 挂在卡上；项目没有随卡存储时才进仓，且只留指针与一行读数，不贴原始输出 |

**人要看和知道的只有六类**：①批准方向（spec 的故事、范围、待拍板岔口）；②确认形态（原型与界面）；③裁决偏离（越权、范围变化、与原话对不上）；④批准例外与不可逆的事（上调超线基线、豁免、部署、删除）；⑤放行进主线（2.7，附带里面有什么、哪些未验）；⑥验收结果（一个功能做完后的现状与未验证项）。其余在 agent 之间解决，除非升级成③或④。

**给人的每一条都要自成一体**：不打开仓库里任何文档就能决定；一条只问一件事，带选项、推荐与后果；用户原话逐字带着走，转述单独标明。

协调者用什么界面、消息怎么分类排版、随卡存储怎么实现，属项目层。

### 2.10 领域说明：L3 人审多一项「数据归属」（用户定：只展开改动部分）

楼层图回答「一个故事怎么流过去」，不回答「谁拥有什么」。审核里最硬的几条问题都是后一类：同一概念在两个模块各有一套写法、一个模块把另一个模块的类型存进自己的表、同一规则在四个模块各写一份。

- **骨架多带两种注释**（L2、L3 的骨架都带，它们留在代码里给以后的 agent 用）：每个类型一句话写职责与拥有的数据；本卡新增或改动的字段各一句话写「是什么、谁写它」。连同第四步已有的「每个桩方法一句话」与 2.2 的包注释，构成领域说明的全部来源。
- **领域说明从骨架抽取，不另写文档**：每个触及的领域一张——职责、拥有的数据、对外方法。方法只列领域对外的，私有的不列。
- **只展开本卡新增与改动的部分**：新领域完整展示；已有领域只展开本次新增或改动的字段与方法，其余折成一行计数，可点开。
- **L3 的人审从两件事变三件**：产品逻辑与流程对不对（按故事走楼层图）；分层与架构对不对（第十三条）；**数据归属对不对**（第五条：规则归数据所有者）。
- **一项自动标记**：新类型的「拥有的数据」为空即标出（第六条：名字说不出拥有什么数据），裁决归人。
- L2 不出领域说明给人看，除非 spec 头部点名或结构检查命中。

领域说明怎么渲染、挂在楼层图的哪里，属项目层（生成器）。

## 六、Out of Scope

**永不做（本仓）**：

- 结构检查脚本、基线文件格式、在合并处挂闸——项目层。
- 运行记录由谁触发、在哪台机器跑、是否排队，以及某个包的全量为什么慢——项目层。
- 集成分支的名字、全量的触发频率、现存已知红的清零——项目层。
- 随卡存储怎么实现、协调者（项目经理）向人发消息的界面与排版——项目层（pejam PJ81.3 第④⑤步）。
- 架构师熟练工的模板与模型选择——项目层（pejam PJ41）。
- 存量债的专项重构——由各项目自行立卡决定，本仓只规定随卡搬迁。

**本期不做、后续要做（逐条落 roadmap）**：

- L3 的 plan 文档是否同样收缩成骨架 + 备注（Q3=A 时）：L2 跑几张后回看。
- 第十三条上帝对象判据「跨 > 1 层」是否保留：有了第十四条的计数后看它是否还有独立命中。
- 手画楼层图存废：等楼层图生成器（PJ41）落地后再议。
- 不随卡触及的旧测试是否专项清理：先看随卡删除的效果。
- 架构师在写业务逻辑之前判断「哪些桩承载规则」的漏判率：靠「清单外已披露」的条数回看。
- 轻档是否被拆着用（一个功能切成多次线内落入）：按同一文件在短期内的轻档落入次数回看；边看边调的界面微调本来就会重复落入，先观察再定是否要加累计判据。
- 卡级审查漏到后面的缺陷（用户定：不改规则，只观察）：改版后看集成分支全量与父卡验收阶段发现的缺陷里，还有多少本该在卡级拦下。基线读数是一张父卡批级阶段 11 个缺陷中约 7 个在卡级范围内。
- 修复熔断是否被执行（用户定：不改规则，只观察）：同一问题修复超过三轮的卡还有几张。基线读数是一张子卡同一问题修到第四轮后改回 plan 原方案。
