# charter 自举：安装可复现 + 变异/判据纪律补缺

- **卡**：C4（变异纪律）、C6（三样东西的可复现落点）——合批
- **级别与档位**：**L3 轻档**（判据见下「定级判决」）
- **状态**：**已批准（用户，2026-08-24）**
- **日期**：2026-08-24（出稿与批准同日）

## 问题陈述

charter 这套方法论今天**装不回去，也测不出它有没有漂**。

现役执行流的三样东西只活在一台机器的 SQLite 里：工作流定义、派发模板、纪律块。
仓里对前两样零记录——换机、重装、新人接入全靠记忆手搓 12 列 4 门。

漂移不是假设，已在读数上：C6 立卡时账本是 `charter v7`，今天（不到一天后）是 **v9**，
仓里没有任何一行记录这两次改了什么。同族的 B229（handoff 卡，高优先）已实测到纪律块
跨机 md5 不同。

同时，charter 自己的纪律有三处空洞，都属同一族——**一个通过了的检查，不等于它想证明的
事情为真**。C4 记录了四种形态，其中三种在仓里 grep 零命中。第四种（变异必须编译得过）
虽有正文，却落在一个现场够不着的地方（详见「现状读数」）。

两张卡合批的理由不是凑数：C4 改的是 `skills/*/SKILL.md`，改完必须跑
`scripts/regen_discipline.py` 才能生效；C6 建的正是这套安装的可复现落点。**C4 是 C6 那条
管道的第一个真实 payload**，落地后跑一次 C6 的比对，就同时验证了两件事。

## 现状读数

均为 2026-08-24 本工作树读数，由 contract 节点在其工作树复核。

### C4 四种形态的覆盖

| 形态 | 内容 | 现状 |
|---|---|---|
| ① | 变异必须编译得过（否则 `--- FAIL` 计数为 0 = 假绿） | **已有正文**：`skills/acceptance/SKILL.md:22`，红旗表 `skills/acceptance/SKILL.md:43` |
| ② | 变异必须打中唯一；变异后行为没变先怀疑没打中 | **零覆盖** |
| ③ | 判据要钉住行为，不钉住计数（代理指标型假达标） | **零覆盖** |
| ④ | 跨仓判据落笔前先确认目标仓钉的依赖版本里有这个能力 | **零覆盖** |

两条结构事实：

1. **`skills/implement/SKILL.md` 全文没有「变异」二字**——C4 卡文点名的落点之一是空的。
2. **形态①落在了现场够不着的地方。**`scripts/regen_discipline.py` 的 compose 映射只含
   contract / breakdown / plan / implement / review / integrate / recon **七个节点**
   （`scripts/regen_discipline.py:29-37`），**没有 acceptance**——acceptance 是人工列、
   不派发，故无纪律块。于是「变异必须编译得过」只有协调者在本地会话读 skill 时能看到，
   **派发出去的执行者永远读不到**；而 C4 记录的两次踩坑正发生在 implement 的变异自验环节。

形态③④ 与 ①② 不同族：卡文自陈「两条都是协调者写判据时的错，不是执行者的错」。
①② 是**执行者做变异时**的坑，③④ 是**协调者写判据时**的坑，受众不同。

`skills/plan/SKILL.md:20` 已有「判据先在基线跑」，对形态④是**部分覆盖**（真跑了就会发现
那个类型不存在），对形态③**无效**——「cmd/ 图内文件数 41→50」这类判据在基线上跑得通，
它坏在代理错了目标，不坏在跑不通。

### C6 三样东西的缺口

| 东西 | 仓内真源 | 缺口 |
|---|---|---|
| 工作流定义 `charter` | **无** | 从零。账本现为 v9 |
| 派发模板 `charter-default` | **无** | 从零。账本现为 v4 |
| 7 个纪律块 | **已同源**（`scripts/regen_discipline.py`） | 只缺版本与跨机分发 = B229，本期不做 |

三条约束性事实：

1. 仓根 `install.sh` 是 **codegraph 二进制**的下载安装脚本（见其头部职责注释），与方法论
   安装无关——C6 没有现成载体。
2. `handoff workflow put <name> --file <def.json>` 与 `handoff template put <name> --file <def.json>`
   均已存在且接受文件入参，安装机制现成，**handoff 侧零修改**。
3. `.github/workflows/ci.yml` 的 paths 过滤只含 `graph/**`，`skills/` 与 `scripts/` 无任何
   CI 门。该文件里的「Reject stale committed dist」是仓内现成的防漂移门形态（rebuild → diff
   → 拒绝），但它跑在 GitHub runner 上，**那里没有 handoff 账本**——这决定了「账本 vs 仓」
   的比对只能是本机运维动作，不能进 CI。

### 顺带发现的一颗雷（纳入本期）

> **contract 节点更正（2026-08-24）**：本节初稿断言缺省 `discipline: "implement"` 会
> 「解析到一个不存在的纪律块」，**该断言经查证不成立**，性质恰好相反，已按代码事实改写如下。
> 更正依据见契约文档 `docs/contracts/2026-08-24-charter-provisioning-contract.md` 条 C-9。

模板 `charter-default` v4 的缺省 `discipline` 字段值为 `"implement"`。它是一个**合法的
内置角色名**（handoff 内置五个：implement / review / spec-draft / plan-writing / finishing），
解析时先找 `~/.handoff/discipline/implement.md`（不存在），再落到**内置 implement 块**——
按执行器能力选 subagent 或 single-context 档。所以它既不报错，也不悬空。

真正的风险是它**不报错**：charter 的七个纪律块是以覆盖文件形态存在的
（`~/.handoff/discipline/charter-*.md`），必须由节点的 `override.discipline` 点名才会被用上。
将来新增一个忘写 override 的派发节点，会**静默拿到通用内置 implement 块**，不报错、不告警——
执行者以为自己在跑 charter 纪律，实际跑的是通用实现纪律。handoff 自己在
`internal/ledger/templates.go:27-30` 记过同形态的教训（「审阅模板悄悄拿到实现块」）。

导出模板到仓内时必然要面对这个字段，顺手处置，不留给下一个人。

## 定级判决

按定稿范围判，覆盖入口直觉。

**定级两问**：

1. 改动跨几个子系统的契约面？——charter 仓内 `skills/` 与 `scripts/` 是同仓两目录，无独立
   契约面与部署单元，**不构成两个子系统**。真正的跨越在 charter → handoff。
2. 动不动契约层？——**命中**。本期要生产 `handoff workflow put` / `template put` 消费的
   JSON，那是一个**已存在的跨仓/跨进程 wire 契约**。spec 纪律明写：实现或对接已存在的
   跨仓 wire 契约，即便本侧零修改，也按动契约层计。

**→ L3。**

这不是形式主义，风险是具体的：`handoff workflow show` 的输出形状是
`{"Name":…,"Version":…,"Def":{…}}`（外层带 Name/Version），而 `put --file` 吃的是完整对象
还是只吃 `Def` 子树，**今天未经查证**。猜错的后果是装出一个坏流程或静默丢字段。
这正是 contract 节点该干的活——去 handoff 源码里查证结构定义，而不是从 CLI 输出反推。

**选档：轻档。** 判据是「单子系统工作量是否超过流程固定成本」——本期 handoff 侧零修改，
实质只有 charter 一侧在动，**并行没有对象**，重档的扇出对本批无意义。契约冻结与拆解照做
（价值恰在契约那半段），实现归一轮。

## 方案

### 选定：仓内单向真源 + 一条安装命令

- **仓是唯一真源，账本是安装目标。**工作流定义与模板以 JSON 落进 charter 仓；纪律块沿用
  既有的 `scripts/regen_discipline.py`（本就同源）。
- **一条安装命令**把三样东西装进本机账本：workflow put + template put + regen 三连。
- **一条比对命令**回答「账本和仓漂了没有」，本机运维动作，不进 CI。
- **单向纪律**：此后改流程必须改仓再装，不许直接 `handoff workflow put` 改账本。
  这条纪律是方案成立的前提——两个真源必漂，v7→v9 已是先例。

### 弃选

- **只存快照不建安装**（仓里放两份 JSON + README 记手工命令）。只解决「无记录」，
  不解决「不可复现」；换机照样手搓，且没有任何防漂移防线。成本省得有限，价值少一大半。
- **连跨机同步一起做**（并入 B229）。体量最大，且 B229 是 handoff 项目的卡，会把本批变成
  跨两仓改动。跨机分发是独立的一层，不该压在「先有仓内真源」这件事上——没有真源，
  同步无从谈起。留 B229。
- **做成 handoff 出厂种子**。**永不做**，B230 已论证否决：那会把私人方法论焊进通用引擎，
  且纪律正文会出现第三份副本。本期方案的方向与之相反——handoff 装完仍是零流零模板，
  charter 自己带着自己的三样东西。
- **做成 codegraph 子命令**（`codegraph charter install`）。把方法论焊进图工具，且 codegraph
  的契约里有「不发网络」这类不变式，塞进账本操作会污染它的职责。

## 用户故事

1. 作为换机或重装的 charter 使用者，我在新机器上跑一条命令，就把 charter 的工作流、模板、
   纪律块装齐，不必凭记忆手搓 12 列 4 门。
2. 作为 charter 维护者，我改完流程定义后仓内记录与账本一致；怀疑漂了时，一条命令告诉我
   漂在哪一样、哪个字段，而不是让我肉眼比对两份 JSON。
3. 作为 implement 节点的执行者，我做变异自验时能从纪律块里读到「变异必须编译得过」与
   「变异必须打中唯一」，不再把编译失败的 0 计数当成「变异存活 = 测试是摆设」。
4. 作为写验收判据的协调者，我能从 plan 纪律里读到「判据钉行为不钉计数」与「跨仓判据先验
   能力存在」，不再写出可被最省力方式满足的代理指标。

## 契约语义与接缝（L3）

**定得了的（本 spec 的设计决定）**：

- **方向单向**：charter 仓 → handoff 账本。charter 生产，handoff 消费。
  handoff 不需要知道 charter 存在，本期对 handoff 零修改。
- **消费面**：只用两条既有 CLI（`workflow put`、`template put`）与既有磁盘约定
  （纪律块目录）。不新增任何 handoff 侧接口，不要求 handoff 为 charter 让路。
- **真源归属**：三样东西的权威副本在 charter 仓。账本里的版本号由 handoff 自增，
  **不由仓管理**——比对时它是需要被规范化掉的噪声字段，不是不一致的证据。
- **等价判定的语义**：「一致」指**语义等价**而非字节相同——字段顺序、账本自增的版本号、
  时间戳不构成差异；states/gates/nodes 的实质内容构成差异。

**定不了的（代码事实，归 contract 节点查证落地）**：

- `workflow put --file` 与 `template put --file` 吃的精确 JSON 结构：完整对象
  （含 `Name`/`Version`/`Def`）还是仅 `Def` 子树。
- `workflow show` 的输出能否原样 roundtrip 回 `put`；不能则转换规则是什么。
- put 时 `Version` 字段是被忽略、被拒绝，还是必须省略。
- 模板定义里 `discipline` 缺省值的合法取值域（决定那颗雷该改成 `charter-implement`
  还是整个字段留空）。

以上四条严禁在本 spec 里猜写成签名——写死会写出对不上现状的契约。

## 实现决定

- **纪律落点按受众分两处**（受 compose 映射约束，只有进了映射的七个节点，正文才会变成
  执行者读得到的纪律块）：
  - 形态①②（变异台）→ **implement** 新增变异自验段。做变异的是执行者，implement 有纪律块。
  - `acceptance` 现有的形态①正文**改为引用式，不重写**——避免同一条纪律出现第二份副本
    （C6 卡文点名忌讳的形态）。协调者复验侧保留入口。
  - 形态③④（判据撰写）→ **plan** 判据段扩写，作为 `skills/plan/SKILL.md:20`「判据先在基线
    跑」的两个具体化，不另起炉灶。
- **安装与比对同一个脚本的两个模式**（装 / 验），不拆成两个文件——比对逻辑与安装逻辑共享
  同一套规范化规则，拆开必漂。
- **`regen_discipline.py` 的输出目录需参数化**（今日为模块级常量 `OUT`，
  `scripts/regen_discipline.py:9`），否则比对逻辑无法在不污染本机 `~/.handoff/` 的前提下被
  测试驱动。这是可测性启用点，不是接缝（见下）。
- **纪律块内容改动后必须重跑 regen**——既有约定，本期不改，但安装命令要把它含进三连，
  免得又变成一条靠记忆执行的步骤。

## 测试决定（接缝清单）

**缝（唯一一条）：仓内产物与账本定义的语义等价比对函数。**

- **符号与调用方**：新建符号，落在安装/比对脚本的模块级；生产调用方是该脚本的 `--check`
  模式主流程，测试是第二调用方。签名归 contract 节点落地，此处只声明导出面：模块级可导入，
  不藏在 `main` 里。
- **合法性**：该函数是 **handoff JSON wire 格式的解析/判定入口**，命中接缝合法性第三款
  （边界型例外）——缝的对面是外部工具的输出格式，其解析入口即缝上符号。此类表驱动测试
  视为穿过该缝。
- **缝级断言（至少）**：
  1. 一对「语义等价但字段序不同 / 版本号不同」的输入 → 判等价（防止把噪声报成漂移，
     那会让比对命令变成狼来了）。
  2. 一对「states 或 gates 实质不同」的输入 → 判不等价，且指出差异在哪一样、哪个字段
     （不指路的比对等于没有，B229 与 C6 都吃过「知道漂了但不知道漂在哪」的亏）。

**内部锁候选（不占缝名额）**：`regen_discipline.py` 的输出目录参数化——它是为让上述缝可被
测试驱动而做的可测性启用点，是手段不是缝，按假缝禁令不入清单。

**不走单测、走真机验收的部分**：三连安装真的把定义装进账本这一路径。它的验收是真机
清单——装完后 `workflow show` 与 `template show` 的读数与仓内真源语义等价，且卡能在新装的
流上正常 move。这条写进 acceptance，不硬凑成单测。

**C4 的验证路径**：C4 是纯正文改动，自身无代码接缝。它的落地证据是——改完 `skills/` 正文并
跑 regen 后，对应纪律块含新段；这恰好由 C6 的比对能力覆盖。这是本批合并的技术兑现点。

## Out of Scope

**永不做**：

1. **把 charter 做成 handoff 的出厂种子**。B230 已论证否决，本期方向与之相反。
2. **为 charter 修改 handoff**。本期 handoff 侧零修改；若实施中发现非改 handoff 不可，
   那是契约分歧，退回 spec 重议，不许顺手改对侧。

**本期不做、后续要做**（已逐条落进 `docs/roadmap.md`）：

3. **纪律块版本化与跨机分发**——归 B229（handoff 项目，高优先，已实测跨机 md5 漂移）。
   本期只保证仓内真源与本机安装，不碰多机同步。
4. **CI 门**。「账本 vs 仓」的比对需要 handoff 账本，GitHub runner 上没有，进不了 CI。
   仓内自洽性检查（`skills/` 正文 → regen 输出是否已提交同步）技术上可进 CI，但那要求把
   纪律块产物提交进仓，是另一个决定，本期不开。
5. **`skills/` 与 `scripts/` 的 CI 覆盖**。今日 `ci.yml` 的 paths 只含 `graph/**`，本期新增的
   脚本不进 CI 门；其测试靠本地跑。
6. **acceptance 节点纪律块化**。形态①落点问题的另一种解法是给 acceptance 也发纪律块，
   但 acceptance 是人工列、不派发，为它建纪律块等于改流程形状，超出本批。本期用「正文移到
   implement + acceptance 改引用」绕过它。

**明确不改**：

7. 其余 5 个纪律块（contract / breakdown / review / integrate / recon）的正文不动。
8. codegraph 与 `graph/` 模块零改动；仓根 `install.sh` 不动（它是 codegraph 二进制的安装
   脚本，与本批无关，不要因为名字像就去改它）。
