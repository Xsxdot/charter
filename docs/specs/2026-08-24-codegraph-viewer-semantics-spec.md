## 问题陈述

一期把理想树与执法读数上了墙，二期把下钻、迁移视角与欠账读数上了墙。**两期回答的都是「架构差在哪」，没有一期回答「这一组到底是干什么的」。**
点进任何一个领域，今天看到的是容器分组树与节点计数——它告诉你这里有 193 个符号，不告诉你它们合起来在做什么、有哪些不能破的规矩、一个请求进来怎么流。

A 组当初被顺延，理由是「消费职责/生命周期数据，B231 完成前做是空壳」。B231 已完成：
`packages` 段入库（66 个目录 / 35 个有包 doc 摘要）、`summary` 覆盖率 48%→82.5%、`modelKind` 分种完成（实体 53 / dto 642 / config 13）、`lifecycle` 127 条。**数据到位了，欠的是消费。**

但本轮事实调查同时挖出两件必须在 spec 里处置的事，否则三期会做成一个漂亮的空壳：

1. **「泳道 = 入口」在真数据上不成立。**`entry` 节点只集中在 2 个最优域（控制门面 74 / 协调者命令面 83），**其余 21 个域全是 0**。照订单样例那套「每个入口一条泳道」画，21 个域打开是空白页。
2. **领域声明的词表与查看器的画布不是同一套。**声明（`codegraph/domains/*.json`）以**视图领域 id** 为键，覆盖 2/20；而一期起画布就是**最优树**（12 顶层 + 11 子域）。两套 id 只交集 11 个，其中 `d_coordination_task` 的容器实测散落在 **7 个**最优域里——机械映射会把一份职责声明贴到七个域上。

## 方案（含弃选与理由）

### 一、领域页双 tab：语义（应然 + 机械）/ 结构（行为）

**语义 tab** 分两层，视觉上分开，来源标清楚：

- **应然层（人写声明）**：职责一句话、不变式（每条带测试锚）、状态机迁移表、生命周期锚。
- **机械层（扫描事实）**：实体表（只列 `modelKind=entity`，带创建/写状态徽标，来自 `lifecycle` 段）、包职责表（`packages` 段，只转录不概括）。

**空态即催稿位（本刀的核心裁决）**：18/20 个域没有声明。空态不写「暂无数据」，写清楚
「声明是人写的应然承诺、扫描器不生成」+ 全仓覆盖读数 + 该写在哪个文件路径。
**弃选**：让扫描器生成职责文案——`Package.Summary` 的注释已经把这条钉死为配方红线（「生成式概括是配方红线」），
生成出来的是正确但空洞的话，会被人和 agent 当成真实承诺读。

**结构 tab** 见第二条。

### 二、结构 tab = 三段带（调进来 / 本域编排 / 调出去），泳道锚在**入缝**而不是 entry

**裁决：一条泳道 = 一条跨域入缝（被域外调用的符号），不是一个 `entry`。**
理由是硬数据：`entry` 只在 2 个域非零，而入缝在 17/23 个域非零。入缝才是「外部世界怎么进到这个域」的通用答案；
`entry`（CLI 命令 / HTTP 路由）只是入缝在最外两层的特例——那两个域的泳道自然还是它们的 entry，形态不用特判。

带的三段：**左端口**＝入边来源域（一域一节点，带边数）、**中段**＝入缝泳道（每条向右展开 3 级域内骨架，高扇入工具收桩不展开）、**右端口**＝出边去向域。
三条视图语法（只画行为、外部领域一域一节点、高扇入收桩）与一期二期逐字一致，不新造语法。

**入缝为 0 的域不画流程图**（实测 `d_web_cards` 48 节点 / `d_web_admin` 113 节点 / `d_cli` 323 节点都是 0）：
空态直说「本域没有跨域入边，它的读法是包职责与实体表」。**不给它编一条假主链**——这是走查早就否决过的「DFS 长墙」的近亲。

**弃选：**
- **照订单样例做函数级泳道**：那份样例是手工策划的干净架构，机械派生到真图上 21/23 个域退化。样例作为**视觉语法**的基准保留（步骤卡、端口列、徽标），作为**数据派生规则**的基准作废。
- **把域内全部调用边画成流程图**：即 DFS 长墙，一期走查已否决。
- **按 `container` 分泳道**：容器粒度制造假读数（handoff 卡 B232 的实测结论），不引进查看器。

### 三、级联调用链面板：抽屉式列级联，深度到 3 级为止

点一条泳道或一个步骤，右侧抽屉按「入缝 → 第 1 级被调 → 第 2 级 …」逐列级联，点某一列的项目继续下钻；
每列显示符号名、摘要、高扇入收桩标记；底部固定源码窗口入口（沿用一期详情面板的 `/codegraph/source`）。

**深度上限 3 级，且到顶时显式说明「再深是 CLI 的活」**（指向 C1.5 的 `chain --with-source`）——
查看器负责「看懂一个域」，不负责替代 agent 的上下文装配。**弃选**：无限下钻（长墙的另一种壳）。

### 四、组织切换：最优树 / 现状领域；**声明迁到最优词表（用户裁决 A，2026-08-24）**

顶栏一个二选一开关：**按最优树**（默认，一期二期的画布）/ **按现状领域**（`baseline.json#domains` 的 20 个视图域，也是一期已有的无 best 回退路径）。切换只换画布，不换语义 tab 的数据来源。

**裁决（用户 2026-08-24）：`DomainDecl.Domain` 的取值域从视图领域 id 改为最优图领域 id。**
理由是用户认可的那条：职责/不变式/状态机都是**应然陈述**，而 `best.json` 就是应然结构，两者本就该对齐；
把应然文本挂在现状机械归属上是 C1.8 之前的遗留。迁完之后语义 tab 直接落在画布上，组织切换回归纯粹的观察开关。

**落地口径（三条，contract 节点按此冻结）：**

1. **同刀做完，不留中间态**——`ValidateDecls` 改校 best 的 domains 与两份声明文件重写必须在同一刀里，
   分开做中间态 validate 必红（与 C1.6「换 best 词表必须同刀重写 target.contracts」是同一条教训）。
2. **`d_workspace.json` 直接改名/改键**：它的 7 个容器在 best 侧 1:1 全落 `d_workspace`，文本一字不改即成立。
3. **`d_coordination_task.json` 重写为 `d_orchestration.json`，不机械拆成 7 份。**
   它的 25 个容器散在 7 个最优域（`d_orchestration` 10 / `d_maintenance` 5 / 未认领 3 / `d_policy` 3 / `d_workspace` 2 / `d_gateway` 1 / `d_web_shell` 1）。
   **声明是承诺，不能靠复制变出 7 份**——机械拆写会造出六份没人负责的假承诺，比空着更坏。
   做法：按 `d_orchestration`（任务编排）的**实际边界**重写职责句；四条不变式逐条核对它守的代码是否落在 `d_orchestration` 内，
   落在内的保留（testRef 必须仍指向真实存在的测试函数，`ValidateDecls` 会核），落在外的**删掉并落 roadmap**，
   留给那几个域各自写声明的那一刀。生命周期锚同法核。
   **结果是声明覆盖仍是 2/23，不是 8/23**——这个数字诚实下降/横盘是预期的，不是回退。

**弃选：按容器交集把声明机械映射到最优域**——实测 `d_coordination_task` 会被贴到 7 个域上，等于让七个域共享一句不属于它们的职责，比空着更坏。

### 五、数据面：宿主响应新增 `decls` 段

viewer 是纯前端，声明必须上 wire。宿主已经在加载 decls（为了算 report），把它放进响应是加一个键。
**additive-only**，缺席合法（无声明目录的项目就没有这个键），旧 viewer 忽略未知键——与 `lifecycle`(v0.3.0)、`packages`(v0.6.0) 同款先例。

## 用户故事

1. 作为架构维护者，我点进一个领域，第一屏读到的是「它负责什么、有哪些不能破的规矩、规矩由哪个测试守」，而不是符号计数。
2. 作为架构维护者，我在同一页切到「结构」，看到外部世界从哪几条缝进来、进来之后本域怎么编排、又调出去到哪几个域——三段一屏读完。
3. 作为架构维护者，我点一条缝可以逐级级联往下看，看到 3 级为止，并被明确告知再深该用哪个 CLI 命令。
4. 作为架构维护者，我打开一个**没有声明**的域时，页面告诉我「这里空着是因为还没人写、该写在哪个文件」，而不是假装没有这回事。
5. 作为架构维护者，我打开一个**没有入缝**的域时，页面直说它没有外部调用方、该用另一种方式读它，而不是给我一张编出来的流程图。
6. 作为架构维护者，我能在最优树与现状领域两种组织之间切换，并清楚知道两者的差别是「应然」与「现状」。

## 契约语义与接缝（L3）

**动的契约面一处**：宿主只读 API `GET /api/projects/{name}/codegraph` 的响应体新增 `decls` 段。

- **语义**：领域 id → 该领域的人工声明（职责/不变式/生命周期锚/状态机），内容与 `codegraph/domains/<id>.json` **逐字段等同**，宿主不做加工、不做映射、不补默认值。
- **additive-only**：缺席合法；旧 viewer 必须能忽略它（Go/TS 双侧都是忽略未知键的既成行为）。
- **加载失败不拖垮整页**：与既有 `best`/`target` 的处置一致——告警并跳过该段，其余照常返回。
- **不上 wire 的**：声明的校验结论（`ValidateDecls` 的 issues）——那是 `check` 的产物，已在 `report` 里，不重复上。
- **已裁决 A（2026-08-24），另动一处契约**：`DomainDecl.Domain` 的取值域从视图领域 id 改为最优图领域 id，`ValidateDecls` 的「领域存在」校验改校 best；这是 charter graph 库的行为变更，需 handoff 同刀重写两份声明文件（**同刀，不分开做**——分开做中间态 validate 必红，与 C1.6「换词表必须同刀重写 contracts」是同一条教训）。

**接缝清单（四条，全部符号 + 调用方）：**

1. `handoff/internal/agentd/codegraph.go#handleProjectCodegraph`（调用方：路由注册 `server.go:509`）——响应装配缝，`codegraph_test.go` 既有 harness 直测。
2. `charter/graph/webui/src/api/types.ts#CodegraphResp`（调用方：`client.ts#fetchCodegraph`）——wire 边界型缝，解析入口即缝上符号（表驱动测试视为穿过该缝）。
3. **新建纯函数模块**（暂名「领域页派生」，签名归 contract）：输入 baseline + best + decls，输出 ①语义视图模型（应然层 + 机械层 + 空态标记）②结构视图模型（入/出端口聚合、入缝泳道、3 级骨架、收桩标记）。**导出到组件层**，调用方是下面第 4 条的两个组件。这是本刀的**主缝**，测试预算落这里。
4. 领域页组件（语义 tab / 结构 tab / 级联抽屉），调用方是二期已有的下钻页——组件只做渲染与选中态，不在组件里聚合（沿用一期二期的分层纪律）。

**假缝禁令自检**：第 3 条是真导出、有生产调用方（组件层），不是为了测覆盖抽出来的；第 1、2 条是既有符号。

## 实现决定

- 派生全部落纯函数层，组件薄壳；沿用 `besttree.ts` 的既有分层，不在组件里就地聚合。
- 骨架派生的三个常量（深度 3、每级取节点上限、高扇入收桩阈值）**写死在纯函数模块里**，不进配置——与 fitness 阈值同款理由：可配置的阈值会被调到「不碍事为止」。
- 不加路由库；tab 与抽屉沿用组件内状态 + 二期的面包屑。
- 宿主侧只加一个键，两条 API 的路径参数、错误文案、状态码零改动。
- 不动 `codegraph/diffs` 视图叠加语义；分支视图下语义 tab 显示的仍是主线声明（声明不随分支 diff 变）。

## 测试决定（接缝清单落点）

- **主缝（派生纯函数）**：vitest 表驱动——①有声明/无声明两条路径的语义模型；②入缝为 0、入缝为 1、入缝为 150（大域）三档的结构模型；③收桩阈值命中与否；④骨架深度上限；⑤端口聚合计数与 `report` 同口径。**含变异复验**：把「入缝为 0 时不产泳道」的判据反转，测试必须转红。
- **wire 缝**：`decls` 缺席 / 存在 / 含未知字段三态的解析用例（沿用 `client.test.ts` 既有形态）；宿主侧 Go 用例断言 `decls` 缺席时响应无该键、存在时逐字段等同。
- **组件缝**：testing-library 断言四类空态文案确实出现（无声明 / 无不变式 / 无实体 / 无入缝）——**空态是本刀的产品承诺，必须有断言守着**，否则它会在某次重构里悄悄变成「暂无数据」。
- 一期二期用例不红 = 回退与下钻语义未破。
- **真机**：在 handoff 真基线上逐个打开四种形态的域（`d_ledger` 顺利 / `d_orchestration` 大域 / `d_workspace` 满配声明 / `d_web_cards` 退化），核对读数与 CLI 同口径，并与原型副本逐屏对照。

## Out of Scope

**永不做：**
- 让扫描器生成职责/不变式文案（配方红线，见 `types.go#Package` 注释）。
- 在查看器里编辑声明或 best.json（查看器只读，编辑归 CLI 与 contract 节点——一期二期既有裁决延续）。
- 无限深度下钻（长墙）。

**本期不做、后续要做（落 roadmap）：**
- **补写其余最优域的声明**（本刀迁完后覆盖 2/23）：这是 roadmap 1a 的内容、且是 handoff 侧的写作工作，不是 charter 的代码工作。三期交付的是「空着会催你」的位置，不是内容本身。**含本刀从 `d_coordination_task` 删掉的那几条不变式**——它们守的代码落在 `d_maintenance`/`d_policy`/`d_gateway`/`d_web_shell` 等域内，随那些域各自的声明重新落位。
- **不变式测试锚的执行态**（点一下跑那支测试 / 显示它上次是绿是红）：需要测试结果数据源，图里没有。
- **状态机与结构 tab 的互相印证**（每条迁移边高亮到那个 ✎ 步骤）：依赖 `lifecycle.field` 的准确性，而 `lifecycle.field` 今天不校验（roadmap 9a）。
- **订单样例那种手工策划的干净流程图**：作为视觉语法基准保留在原型站，不作为数据派生目标。
- **跨域调用链**（级联走出本域）：本期级联止于域边界，跨域看的是端口列。
