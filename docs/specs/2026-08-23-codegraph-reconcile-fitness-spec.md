> 级别与档位：**L3 轻档**（动 wire 契约：target.json 新增字段 + check 报告新增 finding kind）→ contract → breakdown → 单轮 implement → review → acceptance → finish
> 来源：`docs/roadmap.md` 第 1 条；上游 `handoff/docs/2026-08-22-codegraph-batch-handover.md`（四刀批次交接文档）待拍板第 6 条

## 问题陈述

两个缺口，共用一个落点（`check`），故一批交付：

**缺口一（刀 3）：`check` 只拦违法边，不查漏建。**
现有语义是「实际跨子系统边 ⊆ target.json 声明的契约面，违规即非零退出」——它回答「不许建的缝建了没有」，不回答**「说好要建的缝建成没有」**。contract 节点冻结的目标图增量（新子系统／新缝／新入口）实现后无人逐条核对成真，漏建可以一路合进主线。

注意与既有 `charter:recon` 节点的分工：recon 对的是「本分支**代码改动** vs **视图 diff**」（防漏记图），本刀对的是「**target.json 契约声明** vs **实测图**」（防漏建缝）。两者互补、无重叠。

**缺口二（刀 4）：架构法的可机械化判据全靠人工。**
第三条的判据数字（前缀家族 ≥5、单包 ≥40 无子包）与 `legacyBudget` 棘轮都写在法条里，靠拆解节点人工核对——既漏又贵。`legacyBudget` 字段已存在但**只执法「实际 ≤ 预算」，不执法「预算不得增长」**，涨预算是绕过一切约束的现成后门。

## 方案（含弃选与理由）

**两刀共用一个落点：`check` 命令。** 刀 3 成为新的 finding 类型，刀 4 成为新的 fitness finding 类型 + 一条棘轮判据。

### 刀 3：常驻全量对账（不新增子命令）

每次 `check` 核对 target.json 声明的**全部**契约面是否在实测图中存在，缺一即报：

- **入口漏建**：`entries` 里的容器 label 在图中不存在；
- **接口漏建**：`interfaces` 里的接口名在图中不存在；
- **缝漏建**：声明的契约方向零实际跨子系统边（死契约）。
- 子系统漏建已由既有 `dead-rule` warn 覆盖，不重复造。

**弃选：**
- **增量比对（BASE vs HEAD 的 target.json）**：严格贴合「contract 冻结的增量」原意，但需要 git 与 BASE 语义、detached HEAD 要降级，且**抓不到「历史声明从未建成」的存量漏建**。全量对账是它的超集且更简单。
- **`reconcile` 独立子命令**：全量对账与 `check` 的输入完全相同（target + 视图），独立命令等于把同一份加载与归域逻辑复制一遍，还多一处要在流程里记得调用的地方。语义选定为常驻后，形态问题自动消解（交接文档待拍板第 6 条随之定案）。
- **全量 warn + 增量 fail 双档**：实现量翻倍且要背 git 依赖，而实测显示存量本就零缺失、warn 档当前无货可装。

### 刀 4：fitness 判据 + 预算棘轮

- **判据 1**（前缀家族）：同一目录内、文件名共享**前 4 字符**且成员 ≥5 个源文件即命中；报文给出该组**真实最长公共前缀**而非截断值。
- **判据 2**（大包）：单目录源文件 ≥40 且无子目录即命中。
- **判据 3**（预算棘轮）：逐契约比对主线版 target.json，`legacyBudget` 上涨即命中。

**弃选：**
- **切分式前缀家族定义**（按 `-_` 与驼峰边界取首段）：实测两头不讨好——Go 全小写连写下失灵，且仍误报惯例前缀。字符前缀规则反而同时覆盖下划线、驼峰、Go 连写三种风格，**恰因惯例前缀（use/get/set/new/is）几乎都 ≤3 字符，要求共享 4 字符自动把它们滤掉**。
- **阈值可配（写进 target.json）**：可调阈值最可能的用法是「调高到不报为止」，反而弱化 fitness 函数；异常命名风格的项目出现时再议，不预付。
- **判据 1 不机械化**：实测表明它可以准确机械化（4 组命中零误报），放弃等于白扔一条法条。
- **baseline.json 快照当棘轮参照**：零 git 依赖很诱人，但 baseline 是**可整体重建的实测文件**——一次全量重扫就把棘轮基准重置成当前 target 值，历史涨幅静默洗白；而重扫恰是最需要棘轮盯住的时刻（`27→192` 那笔就是重扫场景）。次生成本：快照字段要么让扫描配方手抄 target 数字（违反「能派生的绝不手抄」），要么把 absorb 从「合并实测差异」变成「兼管契约快照」。
- **硬 fail 无逃生舱**：图重扫导致的正当上涨每次都撞门，会迫使人绕过整条判据。
- **统一 warn 不 fail**：与现有 20 条 warn 混在一起容易被忽略，fitness 函数退化成报表。

## 用户故事

1. 作为契约冻结后的实现者，我在 `check` 里看到「声明了但没建成」的入口/接口/缝，逐条清零后才算实现完毕——而不是等到 absorb 或永不暴露。
2. 作为拆解者，我不必人工数文件：`check` 直接告诉我哪些前缀家族 ≥5、哪些包 ≥40 无子包，我只需回答「还能圈出有界文件集吗」（命中不等于必须拆，但必须回答）。
3. 作为审查者，我看到任何人调高 `legacyBudget` 都会被 `check` 拦下，除非他在 target.json 里写明理由——理由留在冻结物里可审计，不是聊天记录。
4. 作为图重扫的执行者，重扫导致的预算上涨我写一句「图重扫补全」即可放行为 warn，不被硬门卡死。
5. 作为无 git 环境（CI 容器、未 fetch 主线）的使用者，棘轮判据会明示「因取不到主线版本已跳过」，而不是静默放过让我误以为通过。

## 契约语义与接缝（L3）

**定语义，不定签名**（精确字段名/kind 字符串/函数签名归 contract 节点）：

1. **target.json 新增逐契约的「上涨理由」语义**：一个可选的自由文本字段，语义 = 「本契约的预算上涨是有意为之」；填了则棘轮判据由 fail 降为 warn，不填即 fail。它**只影响棘轮一条判据**，不影响 `over-budget`（实际 > 预算）的既有执法。
2. **check 报告新增 finding 类型**：漏建三类（缝/入口/接口）与 fitness 三类（前缀家族/大包/预算棘轮）各自独立成 kind，**不复用既有 kind**——消费方（handoff agentd 两条只读 API、Web 控制台）按 kind 分流，复用会让旧消费方把新语义误显示成旧语义。
3. **judgement 分档语义**：漏建三类 = fail（交接文档原文「漏建即非零退出」）；fitness 判据 1/2 = warn（架构法第三条原文「命中判据不等于必须拆，但必须回答；沉默即违法」——它要求的是回答，不是修复）；棘轮 = fail，有理由字段时降 warn。
4. **依赖方向不变式：`codegraph` 包不得直接调 git。** 旧版 target 由 CLI 层取出后**注入**核心包（既有 `os/exec` 调 git 只在 `graph/cli` 层）。这既保住包的 stdlib-only 冻结条款与可测性，也让棘轮逻辑成为纯函数。
5. **降级语义**：取不到主线版 target（无 git / 未 fetch / detached HEAD / 首次提交）时，棘轮判据跳过并**明示提示**；静默跳过是被禁的——「判据失效」与「判据通过」不可区分是本条存在的理由。
6. **比对基准语义**：棘轮比的是「本分支相对主线」，缺省取与默认分支的 merge-base，可显式指定。与 `charter:recon` 的 BASE 语义保持一致，不另立一套。

## 实现决定

- 判据 1 阈值（前 4 字符、成员 ≥5）**写死**，不进配置。
- 判据 2 的「包」= 目录；「无子包」= 该目录下无更深层目录出现在图文件集中。
- 三类漏建判据的判定对象取自**视图**（`Merge` 后），与既有 check 判据同源，不另读 baseline。
- 顺带修 `check.go#sortFindings` 的比较器：补 From/To（及 Edge）作为 tiebreak，消除撞键时的排序抖动（roadmap 第 5 条，本刀落点同文件，一并了结）。

## 测试决定（接缝清单）

**主缝一个：`Check()` 返回的 Report。** 六类新 finding 全部在此汇合，红绿都在这一个接缝上验——包括「零噪声上线」的正面断言（拿真仓形态的夹具跑出零新增 fail）。

**次缝一个：CLI 层的旧 target 注入点。** 只验两件事：注入值正确传达、取不到时走明示降级路径。git 本身不进测试（不造 git 仓夹具），注入点用假值驱动。

## Out of Scope

**本期不做、后续要做**（逐条落 roadmap）：
1. **charter 修法配套**：integrate/acceptance 引用漏建对账、architecture-law 标注哪几条判据已机械化。法条引用不存在的能力是反模式，必须工具落地后再改。
2. **「预算必须紧贴现实」判据**（`legacyBudget` 远高于实际命中数时报「松弛过大，应调低」）：与棘轮互补的另一半，本期只做「不许涨」，不做「必须贴」。
3. **各仓命中判据后的实际整改**（`internal/agentd` 61 文件、`cmd` 41 文件的竖切）：判据交付后按卡另行排期，本期只交付判据。
4. **dead-rule 与新增 dead-* 的档位对齐**：既有 `dead-rule` 是 warn，新增漏建三类是 fail，档位不一致但语义确有差别（规则没命中文件 vs 声明的东西没建成）；本期不动既有行为，是否统一另议。

**永不做**：
5. **架构法第三条判据 3（单个可派发上下文单元 >2~3 万行）机械化**：它的裁决对象是「派卡资格」而非代码形态，`check` 不掌握派卡上下文，机械化会得出与实际派发无关的数字。
6. **阈值可配置化**：见弃选理由。
