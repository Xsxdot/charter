## 问题陈述

查看器现在的形态，用户看不懂。

C12 原本立的案是「实现跑偏了，照原型补回来」——已核实的偏差分三层：C1.10 的形态没做（流程视图三态只做了一个）、形态做反（级联调用链原型是横向 Miller columns，实现是竖排抽屉）、约 38 处零 className；C1.9 基本忠实，只有四条点状偏差。

但 2026-08-25 的 spec 对话推翻了这个立案的前提：**原型本身也不是用户要的形态**。用户能看懂的只有「首层有哪些子系统、点进去有哪些领域」，再往下的东西——迁移清单长墙、级联调用链、焦点链——都看不懂。所以要修的不是「实现与原型的差」，是**目标形态本身**。

对话中查出四条事实，把「看不懂」的根因从样式层挪到了信息架构层：

1. **入缝排行是坏的，坏因是容器粒度**。领域页取入缝用 `inboundEdges.slice(0, DOMAIN_FOCUS_QUOTA)`（现状读数：`graph/webui/src/app/codegraph/domainpage.ts:283`，配额 5 定义在同文件 `:16`），按边序取前五条、不排序不过滤。于是「任务编排」子系统画出的五条泳道，头号入缝是 `writeJSON`（102 条跨域入边）、`truncateRunes`（9 条）、`ledgerErr`（8 条）——全是工具函数，3 层内可达符号数为 1，链是死的。根因是 `k_agentd_fn` 把 213 个包级函数糊成一个容器归一个域（同 B232）。
2. **契约面的官方粒度已经是容器，查看器没用上**。契约图 37 条契约中 11 条声明了 `entries`，15 个 entry 全部精确匹配容器 label（`ledger.Store` / `proto 实体` / `discipline（包级函数）`）。而入缝收敛比很高：任务编排 336 条入边 / 152 个被调符号只落在 6 个容器，协议契约 257 / 81 落在 4 个容器。
3. **骨架漏了一整根轴**。对话前半程推出的四层骨架（子系统→领域→容器→符号）里，程序入口无处安放：162 个入口全挤在 5 个入口容器中，归属 `d_cli` / `d_gateway` / `d_web_shell`，作为普通容器沉在结构树底部。用户由此指出「看不到整个系统的任何入口和顶层流程图」。
4. **形态基准指错是流程缺陷，不是笔误**。C1.10 的 spec 把形态基准指向了一份从未走查的临时页（327 行，无 git 历史，其自身 README 状态标着「走查中」），真正经用户四轮走查的基准页是入库基准站里的那一版。没有任何闸门验证「被引用的基准页是否已确认」，所以「零样式细节」在源头上就没有对照物能拦住。

## 级别与档位

**L3 · 重档。**跨三个子系统的契约面：扫描侧（配方与扫描器）、graph 子系统（图 schema 与
`check`）、查看器（消费）。`flows` 段与状态机 `anchor` 约定是三方共用的 wire 契约，必须先冻结。

**仍然成立的两条现状读数**（它们决定了查看器那一半不需要动后端）：

- `CodegraphResp`（`graph/webui/src/api/types.ts:87`）已同时提供 `best`、`target`（含
  `contracts.entries` 与 `legacyBudget`）、`report` 与 `decls`——**两轴四层的现有数据一次全给**，
  查看器侧零 API 改动。
- 宿主内嵌走单向传参 `?project=<name>`（`handoff/web/src/app/codegraph/CodegraphFrame.tsx:19`），
  查看器内部的轴与层级状态不经过该契约，**handoff 侧零改动**。

所以本卡的跨子系统性**全部来自新增的 `flows` 段与状态机约定**，不来自查看器重设计本身。
拆解时这两半是可分离的（见「实现决定 · 分两半」）。

## 方案

**选定：结构是主干，行为从入口进入。首层即子系统连线图。**

> **方案修订（2026-08-25，走查原型后）**：初稿设计「首层二选一进入某根轴」。用户走查后指出
> ——**没有任何入口指向「整个系统」**，CLI / HTTP / WS 逻辑上都指向某个子系统，形式不同而已。
> 首层选轴因此是个假选择。改为：首层就是子系统连线图，入口挂在子系统上，行为轴由「点入口」进入。
> 原「首层选轴」页作废，此处留痕。

> **导航修订二（2026-08-25，同日走查）**：初版把导航切成三个页面（子系统全景 / 子系统内部 /
> 领域页）。用户问「领域到底是什么，从哪儿进」时暴露了这个切法是错的——**子系统就是顶层领域**，
> 对 12 个子系统里那 9 个叶子子系统，「内部页」和「领域页」画的是同一批容器，纯重复。
> 改为**一个页面按 scope 变**：`scope` 空 = 根（12 个子系统），否则 = 某个领域。
> 「进领域」不是一个单独动作，双击一路下去就是。三页合一，原两页作废。

```
一个页面，变的只有 scope：

  scope = 根        →  12 个顶层领域（= 子系统）
  scope = 任务执行   →  它的 3 个下层领域
  scope = 卡片账本   →  它的 12 个容器（叶子领域，到此为止）

  单击 ─▶ 右栏三个 tab：基本信息 · 对外面 · 状态机
  双击 ─▶ 领域则换 scope；容器则进容器详情
  右栏「程序入口」点进去 ─▶ 流程图（另一条线，递归下钻）
```

**领域树的事实**（核过，无一例外）：`best.json` 的 `domains` 是一棵树，树上每个节点都是领域；
子系统 = 顶层领域（12 个）；容器只挂叶子领域。12 个子系统里 **9 个本身就是叶子领域**
（双击进去直接是容器），只有任务执行（3）、跨机连接（2）、Web 控制台（6）有下一层领域。

**递归同构**：每一层是同一个页面、同一套形态——节点 + 有向边 + 对外部的端口 + 单击右栏 + 双击下钻。
层数不固定，到**容器**为止——容器是原子节点。

**首层连线图与契约图一一对应**（现状读数）：顶层 37 条跨子系统边，**37 条全部在
`target.json` 里已声明**。线宽 = 调用量，线色 = 直调债预算四档。

行为轴的递归性有数据支撑（现状读数）：`GET /api/tasks/{id}/branches` 可达 37 个符号、碰到 17 个下层域入口、横跨 5 个域。入口本身天然带业务分组——CLI 86 个入口聚成 15 个命令族，HTTP 72 个端点聚成 17 个资源族，族名即业务名。

**三个弃选方案与理由**：

- **弃选「入口层加在结构轴最上面」（单一下钻五层）**：入口族与子系统是两种切法，硬排成上下级会骗人——`CLI card` 族触达 5 个域，它不是任何一个子系统的下级。
- **弃选「入口归位到子系统卡上」**：需先按服务的领域拆分入口容器（改扫描配方 + 全量重扫），会把本卡压在 B228「代码图基线落后于 main」上；且跨域业务流程（`/tasks` 触达 7 个域）仍无归属地。
- **弃选「照原型补齐」（C12 原立案）**：原型的形态基准本身已被用户否定；且原型的流程图数据是手写假数据（281 行页面里的 `LANES` 常量），其头部注释自陈是在等后续扫描期产出真数据。

**同期确立的三条形态裁决**：

1. **容器层如实报，不遮**。22 个容器超 40 个符号（7 个超 100），容器卡正面直接显示符号数、文件数与「无声明职责」，标成债务色，不做视图层折叠圆场。整改归 B232 / B233 / roadmap 1f，查看器不替架构债打圆场。
2. **人看流程图，agent 看调用链**。人面向的界面不再出现调用链视图；调用链能力保留在 CLI 与 agent 取数路径上。
3. **流程图这一格先占位、内容降级**。格位现在定下来，内容用现有边能算出的浅形态；扫描侧产出真流程数据后只换内容不改结构。

## 用户故事

1. 作为看图的人，我打开查看器就看到子系统之间的连线图，一眼看出这个系统由哪几块组成、谁调用谁、哪条依赖欠债最多。
2. 作为看图的人，我单击一个子系统就在右栏看到它的契约、它对外的入口、以及它和谁协作；我不需要先做任何选择。
3. 作为看图的人，我双击一个子系统进入它内部，看到的是**和外层一模一样的形态**——盒子、连线、对外部的虚线端口；我不用学第二套交互。
4. 作为看图的人，我在任何一层的右栏都能切三个 tab：基本信息（职责 / 选中项 / 不变式 / 对外面读数 / 程序入口）、对外面（这一层的契约面）、状态机；右栏宽度我能拖，状态机那种宽内容拖开看。
5. 作为看图的人，我在图上就能看到每个容器的职责，不用点开；如果它没有可说清的职责（函数组、实体这类没有主体的容器），卡面直接写「无职责主体」。
6. 作为看图的人，我在子系统的右栏看到它对外的入口（CLI / HTTP / WS 分组）；如果这些入口是被一个上帝文件集中注册的而不是它自己注册的，界面直接这么告诉我。
7. 作为看图的人，我点一个入口就进入它的流程图：分支画成菱形、调用画成节点、提前返回甩到一侧；流程里本身也是下层入口的那一步我能点进去，看它自己的流程——递归下钻。
8. 作为看图的人，我能看出复用与抽象的债：哪些跨域契约入口只服务一个入口、哪些没有任何入口能到达、哪些是真共享内核、哪些是被到处调的工具函数假复用。
9. 作为看图的人，凡是界面上因数据缺失而降级或空缺的地方，界面明确告诉我缺什么，而不是显示一个看起来完整的假读数。
10. 作为看图的人，「对外面」给我看真正的契约入口，而不是 `writeJSON` 这类被到处调的工具函数；被折叠的噪声我能展开看，但它不占名额。
11. 作为看图的人，我一眼分得清「对外面」和「程序入口」是两件事——界面不把它们混成一个词。
12. 作为看图的人，图里的方向靠**箭头**表达，不靠我数节点排在第几层；一屏就能看见全部节点，画布不留大片空白，连线不乱缠。
13. 作为看图的人，流程图太长时它折成下一列而不是让我一路往下滚；两列之间是一条**看得见的蛇形连线**（从本列末尾往下、拐进列间走廊往上、再拐进下一列开头），不是一句「接上列」的文字。
14. 作为看图的人，流程走到接口调用时，图上给我看的是**接口**；右栏列出它的全部实现，每个实现的入口就是那个实现的流程图起点，我点进去换一张图看。

## 实现决定

**四类债读数**（全部可由现有数据算出，现状读数已验证）：

- **兜底桶占比**：子系统的跨域入边中，落在「函数组」类容器的比例。安装与换版 35/35（100%）、任务编排 242/336（72%）、卡片账本 4/114（3%）、协议契约 1/257（0%）。这是「离理想图多远」最锋利的一条——占比 100% 意味着该子系统没有契约面，直接不满足架构法第一条身份判据第 1 款。
- **复用度**：每个跨域入缝符号能被多少个程序入口可达。438 个入缝符号中，21 个复用度为 0（死契约）、230 个为 1（只服务一个入口）、9 个在 60 以上。
- **真假共享内核判据**：高复用度落在实体/类型方法容器 = 正当共享内核（`Config` 123、`Target` 76、`ExecutorConfig` 68）；落在兜底桶 = 假复用（`writeJSON` 73、`Redact` 69、`isForwarded` 47）。与兜底桶占比同一个信号，一处判据两处用。
- **接口实现骨架重复（走查第 5 屏新增）**：一个接口有 N 个实现、这 N 张流程图骨架相同细节不同，
  就是模板方法没抽出来的债。实测：`executor.Adapter` 四个实现（claudecode / codex / grok /
  opencode）的 `Start` 都是「① 裁决 socket ② 写任务物料 ③ 起进程 ④ 起事件循环 ⑤ 投首轮」，
  抄了四遍。这个对比只有把四张流程图并排才看得出来，调用边上看不出来。
- **触达域散度**：入口族触达的领域数。`HTTP /workbench` 3 个（干净）、`HTTP /machines` 8 个、`HTTP /pty` 8 个（散）。

**流程图的形态（走查第 5 屏定稿 2026-08-26，替换初版的「泳道降级形态」）**：

- **一条主干竖着走**。矩形 = 一次调用（左侧色条 = 所属领域），菱形 = 分支。
- **卫语句甩到一侧**：`if err != nil { return }` 这种画成菱形 + 右侧一个返回终点，不占主干。
- **分支体缩进成子干**，左侧留一条「否」旁路绕回主干。这就落实了「switch/if 通过流程图展示，
  调用方法展示在不同节点」。
- **装不下就折列，不让人一路往下滚**——折几列由画布宽度算出（拖分隔条会重排），
  列与列之间画一条**蛇形连线**走列间走廊，不用文字标签代替线。
- **紫框 ▸ = 该节点本身是下层入口**，点进去是它自己的流程图（递归下钻）。
- **双线框 = 接口调用**，见下条。

**契约面（L3 的 wire 契约，schema 草案 §2/§2b/§8 已收齐）**：本卡触碰的 wire 是
`baseline.json` + `best.json` + `codegraph/domains/*.json` 三份，扫描侧 / graph 库 / webui
三方共用。逐条落点见 schema 草案的 §8.6 一张表。本轮**新增**：`baseline.flows`、调用点
`iface` 标记、entry `channel` 字段、`stateMachine.anchor`、`best` 的「容器只挂叶子领域」
不变式、容器 `kind` 受控词表。本轮**不新增**：容器职责字段、`best` 的节点级入口映射
（那条改扫描配方，不改 schema）。**双写漂移已裁（2026-08-26，用户：走甲）**：`responsibility` 今天在
`best.json` 与领域声明文件里双写且两处文本不一致（viewer 三个组件里两个读 best、
一个读 decl）。裁决是 `best.json` **去掉该字段**，职责正文归领域声明文件唯一所有
（架构法第五条）；无声明的领域界面显示「未声明」并给出该写哪个文件，**不回退到任何
兜底文本**——23 个领域里 21 个会立刻空出来，那是真实债务的显形。现有 21 段正文
逐条搬进声明文件作初稿。落地细则见 schema 草案 §8.1。

**容器是原子节点，没有详情页（用户裁决 2026-08-26）**：结构轴到容器为止。容器的职责已经
画在图上、也在右栏「基本信息」；再往下只剩符号清单，而按早先定下的「真正的调用链给 agent 看，
不给人看」，那份清单对人没有价值。**双击容器无动作**，界面直接说明它没有下一层。
原型的 `pages/struct-container.html` 已删除。

**接口 → 实现（用户裁决 2026-08-26）**：流程图节点展示**接口**——代码里写的就是接口，
走到哪个实现是运行期由注册表/装配决定的；图上替它猜一个具体实现，等于把运行期事实
伪装成静态事实。右栏列出全部实现，**每个实现的入口就是那个实现的流程图起点**。
数据侧只在调用点加一个 `iface` 标记，实现清单从已有的 `implements` 段 join 出来，
不在 `flows` 里复制（见 schema 草案 §2b）。这条同时把 schema §7 第 1 项收窄了：
流程图侧要的就是接口本身，`callgraph` 那一档不必为解析实现集买单。

**这一轴今天没有数据**：现有边是无序无条件的二元组，`baseline` 里既没有步骤次序也没有
分支。原型的三条流程是**手抽自真实源码**的（每步带行号可逐行核对），用来定形态；数据由
扫描侧补（roadmap 27/32）。原型里凡是没手抽的入口一律显示空态，**不拿机械可达序列冒充
流程图**——那份序列改放右栏「调用链（给 agent）」tab，如实标注它没有次序也没有分支。

**入口归属判据（新增，原型已验证）**：入口挂到「它服务的子系统」上，判据是**从入口出发第一次遇到的跨域调用目标所在的子系统**（排除兜底桶噪声）。现状读数：162 个入口中 **122 个（75%）判出单值**，24 个多值 2、2 个多值 3，14 个判不出——判不出的**全部是 Cobra 分组命令**（`handoff card` / `handoff service` 之类），它们本来就没有行为。多值的显示全部候选并标注，判不出的标「无行为」。

这条判据同时暴露今天的建模是错的：这 122 个入口的**容器归属**全是 `d_cli` / `d_gateway`（因为 `c_cli`、`c_http` 各是一个整体容器），而**逻辑归属**散在各业务子系统。声明式修复见 Out of Scope-2。

**入口注册散度（新增债读数）**：入口应当由它所属的子系统自己注册。判据 = 该子系统的入口分布在几个文件；集中在 1 个文件且入口数 > 3 即判「集中注册」并标红。现状读数——任务编排 43 个入口全在 1 个文件、协议契约 24 个全在 1 个文件（`internal/agentd/server.go` 79 处 `HandleFunc` 集中注册）；而卡片账本 36 个入口分布在 12 个文件、跨机连接 32 个分布在 27 个文件（`cmd/` 下 52 处 `AddCommand` 分布在 43 个文件），这两个是健康的。

**噪声折叠判据（新增，原型已验证）**：泳道名额不给工具函数。判据可机械判定，与真假共享内核同源——被调符号落在兜底桶容器（`函数组` / `TypeScript 函数组`）**且**复用度 ≥ 10 即折叠为可展开块，不占名额。原型实测：`d_orchestration` 不套判据时前五条泳道全是 `writeJSON`(73) / `isForwarded`(47) / `forwardURL`(45) / `truncateRunes`(33)；套上后变成 `Store.GetTask`(23) / `Store.MirrorTaskTarget`(16) / `Store.ListProjectLocations`(16) 这些真契约入口。**这条判据同时替换掉今天那个坏掉的 `slice(0, 5)` 取法。**

**行为轴的债读数（原型三条手抽流程实测，每条对着源码可核）**：用户提出的洞见——「入口 →
流程图 → 节点即下层入口，递归展开能看出复用和抽象的债」——已验证成立，且这些读数**平铺的
调用边给不出**：

| 读数 | 实测 |
|---|---|
| 真复用 | `ledgerstep.PreflightDiscipline` 被 3 处调用（`cmd/card_dispatch.go:263`、`internal/agentd/cardstep.go:133`、`ViaTemplate` 内部），三条派发通道共用同一个裁决顺序。 |
| 抽象债 · 同一裁决跑两遍 | `handoff card dispatch` 主干 `:263` 先算一次「（角色名，目标机）」，`:286` 的 `ViaTemplate` 内部再算一次。源码注释自己写着「必须与这里完全同序」——**靠注释维持的同序就是债**，该抽一个已裁决的派发意图值对象往下传。 |
| 抽象债 · 一个入口两条抵达通道 | `--step` 分支与主干最终都落在同一个 `ViaTemplate`：一条本地进程直调，一条 CLI → HTTP → StepRunner 绕一整圈网络。 |
| 次序债 | `Manager.Dispatch` 在接口调用点 `ad.Start` 之前已建工作树、落库、写分支名，全是不可回滚副作用，只能靠一个 defer 补偿清理覆盖**全部**错误返回（源码注释：漏补一处 worktree 就永久残留）。次序造成的债，只有流程图看得见。 |

**状态机**：领域右栏展示 `CgDomainDecl.stateMachine`（格位今天已在 `graph/webui/src/api/types.ts:17`，全项目 0 条数据）。它**只能人工声明**——`lifecycle` 只记「谁写了哪个字段」，记不了状态值（全项目写 `state` 的只有 1 条）。schema 草案给它加一条 `anchor` 约定（`file#Symbol` 符号锚，指向写这次迁移的符号），使原型早就定下的互证关系可机械执法：**每条迁移边的 anchor 必须出现在该域某条 flow 的 call 步骤里，且在 `lifecycle` 中是对应实体的 writer**。三处对不上即声明与代码不符。该闸随数据齐备后开启，本轮只落格位与空态。

**术语正名（走查中发现的混淆，必须写死）**：

| 词 | 定义 | 现状读数 | 落在哪 |
|---|---|---|---|
| **程序入口** | CLI 命令 / HTTP 端点 / WS —— 系统的外部入口 | 162 个，全在 5 个入口容器里 | 右栏「基本信息」tab 底部；点它进流程图 |
| **对外入缝** | 跨这一层边界被调进来的符号 —— 这一层的**契约面** | 跨顶层域 438 条 | 右栏「对外面」tab |
| **泳道** | 流程图的一条：一条**程序入口**一条泳道 | 数据未就绪 | 流程图页，不在 scope 页 |

初版把「对外入缝」画成「泳道」并放在 scope 页中间，**名字叫错、位置也放错**。界面上两个词不得混用，
「对外面」tab 内必须有一句显式区分。

**布局判据（用户裁决 2026-08-25，替换初版的强制分层）**：

- **方向靠箭头表达，不靠位置**。边贴到节点边框（不是圆心）、箭头放大、画在群组框之上节点之下；
  跨包调用深色、包内浅色、双向边红色虚线。
- **摆放判据两条**：能看见全部节点时**空白画布面积最少**、**连线交叉最少**。做法：①按连接权重贪心
  排序（强连的相邻）②货架装箱，**目标长宽比 = 实际画布长宽比**（不是拍脑袋的固定比例）③相邻交换
  若干轮，代价函数 = Σ(边两端距离 × 调用量)。缩放同时看宽高取小者并居中。
- **分层只用于节点本身就是聚合单位的层**（根层的子系统、中间层的领域）：按调用方向做拓扑分层，
  SCC 缩点，环内同层并用红色标出（架构法派卡资格第 3 条要求依赖可排 DAG；本图实测 **2 个环、
  3 条双向边**）。**孤立节点不进分层图**——入度为 0 就排进 L0 等于谎称它们是最外层调用方，
  单列一行并写明原因。
- **容器层用包群组**：容器按包聚成群组，边接到**具体容器**不是群组。实测收益：40 容器 → 6 包、
  25 → 7 包、22 → 7 包；包的数量是个位数，容器数是几十。
- **画布可平移缩放**：空白处拖动、⌘/Ctrl + 滚轮缩放、双击空白复位。

**选中态**：单击一个节点时，**相连的节点一起高亮**（描边加重），不相连的压暗，连线只留它的进出边。
只压暗不高亮读不出「谁连着谁」。

**容器职责的来源（走查中核出）**：容器在 schema 里**没有职责字段**（`CgContainer` 只有
`label`/`kind`/`entry`/`domain`）。今天可推导的只有一类——「类型方法」容器 = 同名类型节点的
doc 注释，**覆盖 100/100**（须按包匹配，全局取首个同名会张冠李戴：`opencode.Adapter` 一度拿到了
claudecode 的注释）。「函数组」「实体」类容器**没有职责主体**，卡面直接写「无职责主体（函数组）」，
不硬凑。实测：执行器适配 40 个容器中 28 个有职责、12 个没有（6 函数组 + 6 实体）——**没有职责的
那 12 个，正好就是「说不出职责」的那一批**。容器职责格位的缺失见 schema 草案。

**wire 类型关联（走查中补的盲区）**：跨语言（TS↔Go）**禁止建调用边**（扫描配方硬约束：前端调后端
走 HTTP，不是函数调用），所以 Web 控制台在调用图上孤立是**正确的，不是漏建**。但两侧的真实关联走
`projections`：`协议契约 ↔ Web 控制台` **77 条 twin**，另有 294 条 `typed` 指向协议契约。
本轮把它画成**紫色虚线的第二类边**并明确标注「不是调用边」，孤立子系统旁写明原因。
顺带补上的盲区：协议契约不只是 257 条入边，它还被 294 条 typed 投影引用——它是真正的枢纽。

**右栏形态**：三个 tab（基本信息 / 对外面 / 状态机）+ 可拖动分隔条（宽度持久化）。中间区域全给图。

**分两半**（供 breakdown 参考）：本卡的跨子系统性只来自 `flows` 段与状态机约定。查看器重设计那一半（两轴四层、四类债读数、噪声折叠、C1.9 四条点状修、组件退场、防漂判据）**不依赖新 schema**，用现有数据即可完整落地；扫描侧那一半（工具化机械层、`flows` 产出）是另一条并行线。两半在「流程图那一格」交汇。

**组织切换的归属**：「按最优树 / 按现状领域」是结构轴内部的一个正交维度（两者之差即放错位读数），不与轴选择混排在同一组控件里。C12 已核出的 a11y 缺陷（两组控件塞进同一个 `tablist`）由此机械消解。

**C1.9 四条点状偏差并入本轮**：结构轴首层就是被这四条影响的那张画布，本轮要重画，分开做会让同一块画布在两张卡上打架。四条为——迁移清单从常驻左栏改为按需抽屉并带计数徽标、补四档债务色板图例、读数按层分档并带三态配色、嵌套层补虚线 frame。

**退场**：面向人的调用链视图（级联抽屉、调用树、焦点图）本轮从界面移除；焦点链按用户裁决不再保留。

**形态基准与走查（硬门）**：本轮先出原型、由用户逐屏走查、走查结论回写基准站 README，**之后才允许开始实现**。

**载体已定案（用户裁决 2026-08-25）**：原型跟着源码走，落 charter 仓。charter 此前无原型站，本轮已建 `prototypes/base/`（形态镜像：查看器单页无路由）与 `prototypes/.gitignore`（只 `base/` 入库），分支副本 `prototypes/codegraph-two-axis/` 承载本轮新形态。这同时销掉 roadmap 第 21 条的根因——charter 侧的 review 执行者从此结构上看得见原型，C1.10 白费两轮的事不会重演。

**原型用真数据**：分支副本的 `shared/mock.js` 抽自 handoff 仓入库代码图（`baseline`/`best`/`target`），不是编造的占位内容。这是这轮走查能作数的前提——形态好不好看，要在真实的难看数据上看。

**防漂判据**：本轮补一条机械检查，拦住「结构对、样式无」这一族——新增交互控件必须有非空 className。禁止断言具体 class 值的原有纪律不变（那条初衷没错），只断言非空。更重的视觉对照（截图或 DOM 结构比对）不在本轮。

## Out of Scope

**本期不做、后续要做**（逐条已落 roadmap）：

1. **扫描器的实现**。本轮产出 schema 草案与冻结契约，**不实现 Go 工具链扫描器**（`go/ast` + `go/types` + `x/tools/go/ssa`）、不做工具与 AI 的并行对照轮、不重扫基线。schema 草案 §6 的四步迁移路径归后续卡。
2. **入口容器按服务的领域拆分（声明式修复）**。本轮用派生判据顶上（见实现决定「入口归属判据」，75% 单值），派生结果与将来的声明结果不一致时正好是对账判据。声明式修复仍在本轮之外。现状 `c_http` 的 72 个端点横跨至少 6 个领域（`/api/tasks`、`/api/projects`、`/api/pty`、`/api/machines`、`/api/discipline`、`/api/update`），全部记在 `d_gateway` 名下。这是扫描配方内部规则打架的产物（一条规定入口只分 CLI/HTTP/WS 三容器、另一条要求入口容器挂到它服务的领域），改配方即可修，代码零改动。本轮行为轴的入口族从入口节点名分组算出，不依赖此项。
3. **容器粒度整改与架构物理化**（B232 / B233 / roadmap 1f）。本轮只如实报，不整改。
4. **领域声明铺满**（roadmap 1a）。23 个领域现只有 2 份声明，本轮其余 21 个域的职责/边界/不变式右栏按空态如实显示。
5. **视觉对照闸门**（截图或 DOM 结构比对）。本轮只补「非空 className」这条轻判据。
6. ~~原型站与查看器源码跨仓~~ **本轮已解**：用户裁决原型跟着源码走，charter 建站完成。roadmap 第 21、30 条随本卡销账。handoff 仓那份 `prototypes/codegraph-*` 是否清理，归 handoff 卡。
7. **代码图基线落后于 main**（B228）。本轮不依赖重扫，不解此项。

**永不做**：

8. 面向人的调用链视图（级联抽屉、调用树、焦点图）。按用户裁决，调用链是给 agent 的数据，不是给人的界面。焦点链一并退场。
9. 视图层为大容器做折叠圆场。与「容器层如实报」裁决直接冲突。
