## 一、问题陈述

2026-10-29~11-01 对 pejam 仓 PJ24（账号实例，L3）与同期 PJ 卡的会话复盘（读数见末节）：

1. **定级把「跨子系统各改内部」判成 L3**。spec 定级表写「跨子系统，或动其契约 → L3」，`architecture-law` 术语节写「L3 即改动跨越 ≥2 个子系统的**契约面**」，两处不一致；实际按前者执行，PJ24 这类不动接缝的多子系统改动走了全套 L3（拆分、接缝、冻结节、首故事串行、父卡终验），一张卡做了数天。
2. **冻结节退化成实现规格书**。「≤ 12 条」上限没有解决问题，只是把规格书截断；用户看不懂这个上限要防什么。冻结物是文本条目，靠人读、靠人核，编译核不了。
3. **首故事串行是慢的主因之一**。新缝必须先由一张子卡长出来，其余子卡等它合入才能开工；而「缝」本来可以在动手前以可编译骨架一次立好。
4. **测试与代码 1:1 却没抓到真 bug**。PJ24 测试文件与实现文件一一对应，真问题全在真机才暴露；基线里长期有红文件没人管。
5. **finish 反复跑全量**。每张卡 review 一次全量、finish 合并前后各一次、父卡再来一次；多张子卡时全量跑了十几遍。
6. **产品/UI 的审核没有固定位置**。页面形态在 spec 阶段用原型定过，卡末对照过，但一批卡合起来的整体体验没人走一遍。
7. **handoff 已于 2026-11-01 退役**（用户定：只删不加替代）。本仓 README、网关、plan、`flows/`、`scripts/` 仍以 handoff 为流定义与纪律块的安装目标。

**不是问题的**：plan / review 节点本身的耗时（PJ24 里两者合计不到两成）；skill 正文长度。

**原则**：七条问题各对应一处判据改动；凡是「谁来做、用什么工具」的都不写进本仓。

### 2.1 定级只认契约面（用户定）

- spec 定级表第三行改为：**L3 = 新增或变更跨子系统的契约面，或对接既有跨仓/跨进程 wire 契约（本侧零修改也算）**。
- 新增一行：**跨子系统、但各子系统只改内部、不动任何契约面 → 每个子系统一张 L2 卡**，挂同一张集成父卡（见 2.4）并行；父卡不做拆分与接缝，只做批级 finish。这不是 L3。
- `architecture-law` 术语节那句与之对齐（措辞统一为「契约面」）。
- L3 内不再分档：只有「扇出 / 不扇出」，判据照旧（单子系统工作量超流程固定成本）。

### 2.2 plan 产出物：层表 + 可编译骨架 + 楼层图（用户定）

plan 节点的产出物从「文字计划 + 冻结节文本条目」改为三件：

1. **层表**：每个触及子系统列出层（泳道=子系统、楼层=层，边缘层是契约面所在层）、每层的职责一句话、允许的依赖方向。
2. **可编译骨架**：类型、接口签名、接线（组装点）齐全，**不写业务逻辑**；每个 stub 方法只做两件事——打一行结构化 flow 日志（谁在哪层调了谁，可带「用户看到」），和返回零值/固定值；**每个 stub 方法头一行注释写「做什么」**（用户定：只看方法名不知道它干什么）。骨架必须编译过、能按故事跑通一遍产生日志。
3. **楼层图**：**结构从骨架 diff 的静态调用图抽取**（用户定：不能从日志推结构）；日志只提供调用顺序与「用户看到」标注。主会话只审这张图。五项自动判据（命中即标，裁决归人）：
   - **空层**：层表声明的层在该泳道无任何 actor；
   - **上帝对象嫌疑**：单 actor 承担该泳道 ≥ 60% 的步骤、步骤 ≥ 5、且跨 > 1 层；
   - **跳层**：一条调用跨过 ≥ 2 个非边缘层；
   - **越过契约面**：跨泳道的调用不从本泳道边缘层出发或不落在对方边缘层；
   - **过度设计嫌疑**：≥ 4 个非边缘、非 ui 的 actor 各只承担 1 步。
   人审两件事：产品逻辑与流程对不对（按故事走图），分层与架构对不对（对照 `architecture-law`）。

**冻结节随之改形**：冻结物 = 骨架里跨子系统契约面的类型与接口签名，**由编译核对**；文本条目与「≤ 12 条」上限删除。仍需文字的只剩两类：对外 wire 承诺（跨仓/跨进程）与「反着写也没测试变红」的拍板记录。

**首故事串行删除**：骨架合入集成分支即共同基线；implement 的「首故事（L3）边界」段改为「骨架边界」：子卡只在骨架留的位置填业务，不得新增跨泳道穿透、临时协调对象、硬编码成功或测试专用入口；发现骨架错了停下回 plan 改骨架，不就地绕。

楼层图怎么生成、谁生成，是项目层的事（pejam PJ41）；charter 只规定图的四要素（泳道/楼层/actor/调用）与五项判据，手画也合法。

### 2.3 两层测试（用户定）

implement 测试纪律改为两层，删「竖切测试」与「纯映射须被断言覆盖」：

1. **故事级检查**：每条必交故事一条检查，从真实入口到可观察结果，在项目的测试环境里跑（后端经接口、前端经自动化脚本）。它是验收的主证据，写在 plan 验收方式里、implement 跑、review 复跑。项目须提供环境的起/跑/收三条命令与种子数据——这是项目层的事（pejam PJ28），charter 只要求「命令存在且可由 agent 跑」；无环境时按 Q2。
2. **不变式单测**：只为承重规则与不变式写（状态机、金额/时间计算、权限判定、序列化边界），先红后绿。**不为文件、不为层、不为映射写测试**；与实现 1:1 的测试是删除对象。

review 变异复验的对象限于不变式单测与故事级检查各一处。基线里的红文件在卡级 finish 前必须归零或显式落 roadmap（不得作为「已知抖动」跳过）。

### 2.4 集成分支：卡级 finish 与批级 finish（用户定）

现行「子卡 → 父卡分支」推广为所有卡的统一模型：

- **集成父卡**：一批卡共用一张父卡，父卡分支 `cards/<父卡号>-charter` 从 main HEAD 拉出；**一个仓同一时间只有一个活跃集成分支**；无父卡的单卡自己就是一批（卡级与批级一次做完，即现行 finish）。
- **卡级 finish**（每张卡）：触及包测试绿 + 全量编译过 + 故事级检查绿 + 首跑项真机证据 → `git merge --no-ff` 合入集成分支 → 在卡上记「怎么验证」（命令与入口）。**不跑全量**。
- **批级 finish**（父卡）：集成分支上**跑一次全量** + 整体产品走查（2.5）→ 回旋镖对账 → `git merge --ff-only` 进 main。**main 只从集成分支 ff 进，合入后不再全量**。
- 热修也经集成分支（拉新的集成父卡），不直推 main。
- 三段律改为「编译全量、测试局部、**批级**全量」；review 的「父卡最终验收四件事」并入批级 finish 前的父卡 review，不再在子卡 review 跑全量。

### 2.5 产品与 UI 审核的三个固定位置（用户定）

- **spec 阶段**：页面形态以原型定稿（现行 `prototyping-in-brainstorm`，不变）。
- **卡末**：review「原型/流程基准差异」格对照指定版本（现行，不变）。
- **批末**：批级 finish 前增加**整体走查**——按本批全部必交故事从真实入口走一遍，核 UX 连贯性与 UI 一致性，产出走查记录（故事 → 观察 → 通过/缺陷）并入父卡 review 裁决表一行「整体走查」。谁走查是项目层角色（产品/UI 熟练工或人），charter 只定这一步与证据形状。

### 2.6 分层判据入架构法

`architecture-law` 新增**第十三条（层的职责与楼层判据）**：接口/边缘层只做解包、鉴权、调用、封包；规则归领域层（第五条）；持久层只读写；2.2 的五项判据数字作为先例写入（空层、60%/5 步/>1 层、跨 ≥ 2 非边缘层、边缘层出入、≥ 4 单步 actor）。第十二条之后、附录之前。
