## 一、问题与证据

现行流程在接触真实运行反馈前，先固定精确契约，再通过 plan 预写大量实现。它能核对静态结构，却未必暴露身份、时序、生命周期和真实组装中的未知。

- contract 同时负责精确签名、Ticket 0 和硬编码结果的“直通竖切”；见 skills/contract/SKILL.md「冻结」。接线通过不能单独证明用户获得目标结果。
- plan 强制完整代码块、精确签名、2～5 分钟动作，并把“描述做什么却不给代码”判为失败；见 skills/plan/SKILL.md:23。实现尚未运行就已出现两份待维护的代码，运行中的合理调整还会被当作偏离计划。
- 原型对照曾退化成核 README 摘要，真实页面缺口因此漏过；见 docs/roadmap.md 第 49⑤ 条。单加故事 ID 不能消除这一类意图压缩。
- workflow 当前为 acceptance → integrate → 图对账，integrate 正文却要求交棒 acceptance；见 flows/charter.workflow.json:113 与 skills/integrate/SKILL.md「交棒」。重档父卡缺集成后的最终验收位。

B358 的历史读数与补契约过程见台账 §3，只作为机制样本，不作为整月效率结论。本文要验证的是：更早获得真实反馈、减少重复规定实现，是否降低从批准需求到完整交付的成本。

## 二、本次改造要实现的用户故事

| ID | 使用者与目标 | 可验收结果 |
|---|---|---|
| C1 | 用户希望整个开发过程保留最初承诺 | 批准的每项必交结果都有故事 ID、验收依据和收口责任；不能只交第一条演示就结束 |
| C2 | 执行者希望有清楚边界，并能处理实现中的发现 | 不提供完整实现代码的 plan 也能合格；局部可逆调整可自主完成，承重变化才升级 |
| C3 | 协调者希望在多人并行前暴露关键未知 | Wave 0 按已声明的子系统边界跑通生产路径；只在独立协作或新增对外兼容承诺需要时冻结接缝，必需的外部承诺提前确定；未验证假设只阻塞受其影响的工作 |
| C4 | 用户希望看懂进度与需要拍板的事 | 进度按用户故事说明已看到什么、还缺什么；决策说明产品后果，不只堆技术术语 |
| C5 | 维护者希望改法实际生效且成本可比较 | 节点转换、失败续接和版本边界经隔离试跑；真实卡记录首个演示、最终交付、人工介入与返工成本 |

## 三、spec 保留完整目标，选择第一条竖切

### 3.1 完整故事清单

spec 必须列出本期所有已承诺的用户结果 S1…Sn，而非只列第一条演示。每条说明：谁从什么真实入口做什么、期望观察到什么、关键失败如何呈现、需要什么环境验证。需求尚未承诺的设想放 OOS，不混入必交集合。

后续文档引用故事 ID 与 spec 修订号。breakdown 分解既有承诺，不自行新增、删除或弱化故事；发现新需求先回写 spec 按已有决策权限处置。批准范围的变化必须留痕，不能用新措辞覆盖旧承诺。

### 3.2 选择 Wave 0

优先选用户价值高、且能暴露关键未知的一条最薄完整故事。选择说明只需回答：本次会验证哪些承重假设，为什么这些假设值得先跑。

不规定恰好一个失败用例。身份归属、跨机器路由、恢复或隔离若是该故事成立的必要条件，就验证相应反例；不为凑数量遍历全产品。若一条故事覆盖不了另一个独立的承重未知，安排下一次窄实验，或把依赖它的工作留在后续批次。

承重未知记录在 plan 的待验证项中：假设、验证动作、受影响的工作、通过/失败后的去向。未验证的部分不得被描述为已证实，也不得按该假设已成立去扇出；无关工作可以继续。已充分验证的存量路径允许复跑并复用，不要求为走流程重写代码。

### 3.3 原型与流程图是可追溯的验收依据

故事清单负责索引意图，已批准的原型和流程图负责承载对应的形态与行为细节。两者以版本绑定，不把原型压成几句摘要后丢弃。

每个受形态/流程约束的承重步骤，指向具体原型页面及状态、流程分支和可访问的版本（提交或内容快照）。review 与 acceptance 记录实际截图、输出或运行证据及差异结论；视觉项目在同数据、同视口对照指定原型，不以 README 概述代替页面。

执行者读不到基准时不得宣称对照通过。基准冲突由协调者核对已批准意图；涉及用户结果的取舍才交用户裁决。没有 UI 的故事可用 CLI 输出或其他真实消费面的证据，不强加原型。

## 四、plan 改为轻量、可执行的交接

所有使用 plan 的路径一并瘦身；Wave 0 复用修改后的 plan，不在重型正文后追加一条含糊豁免。

### 4.1 交接只需回答五件事

| 内容 | 必须明确的决定 |
|---|---|
| 交付目标 | 本轮对应哪些故事/步骤，做到哪里，哪些不在本轮 |
| 改动边界 | 有界模块或文件集、代码入口、必须遵守的架构与契约引用及版本 |
| 工作顺序 | 先验证哪个假设，再产生哪些可验证结果；真实依赖关系 |
| 验收方式 | 成功与关键反例的断言、测试入口、运行环境和应保存的证据 |
| 决策权限 | 执行者能自行调整什么，触及何种边界必须升级 |

零上下文执行者必须能找到输入、知道下一步和完成标准；不要求他机械照抄预写实现。

### 4.2 删除与保留

- 删除“每个 task 必含完整代码块”“没给代码即失败”“统一 2～5 分钟一动作”。
- 已冻结的签名引用源码符号与版本，跨卡共同使用同一契约；编译与契约测试核对类型兼容，不再要求各份 plan 复制签名后逐字符比较。
- “无占位符”约束交付承诺与处置责任：“适当处理错误”不合格；“该行为待实验，先跑何种验证、失败后阻塞哪部分”是合法计划。
- 保留事实查证、有界改动范围、故事归属、风险对应的断言、关键诊断信号和真实验收条件。测试允许 mock 做局部验证，但不能拿它替代声明为真机的行为证据。
- 日志、注释与基础 TDD 纪律由 implement 统一承载；plan 只额外指出本任务特有的观测点或约束，不逐 task 重抄通用步骤。
- 完整代码或详细序列可用于已明确的协议、不可逆迁移、关键算法等高风险处，但须说明为什么提前定细节有价值，不扩大为统一模板。
- 测试范围按行为风险选择；保留高层接缝证据，允许复杂内部规则有补充单测，不要求为每支内部测试证明“从高层绝对无法构造”。内部单测不得顶替用户故事验收。

### 4.3 滚动细化与自主权限

只详细计划下一段可验证工作，后续保留目标、依赖和风险；进入下一段前再补齐可执行信息。跨卡审计检查共同边界、故事覆盖和验收责任，不能以各卡尚未预写完整实现为由拒绝。

私有函数拆分、内部算法、局部实现顺序等在授权边界内可调整；保留简短理由与验证结果即可，无需逐项请示。改变用户结果、权威状态归属、外部兼容面或其他任务所依赖的契约，先由协调者判断影响，涉及产品取舍再上报用户。

review 对照目标、边界、行为证据与调整理由，不把遵循过时步骤当作完成标准。同步修改 implement「与 plan 签名一致」和 review 的逐步骤对账口径，避免旧规则从下游重新引入。

## 五、真实竖切与流程承载

### 5.1 Wave 0 的完成条件

从真实产品入口，经生产组装点与实际状态读写，到用户可观察结果；通过真实运行验证所选承重假设。不得用测试专用入口、硬编码成功或绕开组装点来替代。

Wave 0 的代码从开始就遵守 spec 声明的子系统职责、权威状态归属、允许依赖和组装关系；只建设所选故事触及的部分，不预铺全部子系统。接缝的精确形状可在实现中形成，但不得新增跨子系统穿透、把业务规则塞进临时协调对象，或以单机捷径冒充目标边界。review 与 acceptance 要分别核对可观察结果和触及路径的物理边界；已有遗留绕行可登记，不能因此把尚未实现的整体隔离宣称完成。故事演示成功而新增路径越界，Wave 0 仍不通过。

保留四种责任：轻量计划、实现、独立审查、协调者验收。已满足批准基准时由协调者验收；只有新增或冲突的产品取舍才再次请用户决定，不要求每次界面变化重复批准。

通过行为与架构两轴审查和验收的代码进入后续共同基线。失败的实验允许废弃或重写，并记录学到的事实；若真实反馈推翻了承重归属或依赖方向，先修订 spec 的目标边界，再重验受影响的故事，不能为了“代码必须保留”固化错误边界。外部 sandbox/替身明确标出保真范围，未验证外部行为继续作为待验证项管理。

### 5.2 先复用既有节点试点，不新增四列

撤回 r1 强制增加“脊柱计划 / 故事脊柱 / 脊柱审查 / 脊柱验收”四个状态的决定。试点优先在同一父卡上复用现有节点：

~~~text
L3 重档父卡：
spec → [contract：仅 Wave 0 必需的新外部承诺]        [命中才前置]
     → plan → implement → review → acceptance       [Wave 0]
     → 协作分工草案 → [contract：仅需新增冻结时] → breakdown
     → 分批子卡 + integrate → acceptance             [集成后验收]
     → 图对账（有图改动时）→ finish

L3 轻档：
spec → [contract：仅需新增冻结时] → breakdown
     → plan → implement → review → acceptance → finish

L2：
spec → plan → implement → review → acceptance → finish

L1：
保留现有微改快道，不强制增加 Wave 0 或独立 plan 文档。
~~~

方括号表示条件节点，不代表现役 workflow 已支持自动跳转。已有稳定外部契约是 Wave 0 的前置约束，无须为了重新冻结而进 contract；新的外部承诺若是 Wave 0 成立的前提，只提前冻结该缝。L3 轻档无独立扇出且无新增对外兼容承诺时，直接从 spec 进入 breakdown。是否命中 contract 的判据见 §6.2，不能为了满足附件门禁制造空 contract。

Wave 0 是执行阶段标记，不是第五种定级；计划头部注明阶段与选定故事，审查/验收引用同一计划版本。已有卡状态显示当前动作，交棒记录显示阶段、故事与下一去向，不依赖会话记忆。卡附件沿用现役 produces 的路径/kind，不自行发明引擎字段。

试点由驾驶手册显式选边：Wave 0 验收后依冻结判据进入 contract 或 breakdown；轻档从 spec 依同一判据选择 contract 或 breakdown。最终验收进入图对账/finish。缺少阶段或证据不默认按最终验收处理。workflow 的普通成功边改为 integrate → acceptance → 图对账；breakdown 现有的 `require_attachment: contract` 和失败回 contract 也须按是否确有冻结对象改造，不能用空附件占位或把未冻结的新缝直接派发。其余失败边按失败责任复核，不能沿用“integrate 失败就进 acceptance”。

**这是待隔离试跑证明的承载方案，不宣称现役引擎已经支持全部条件跳转与重复进入语义。** 先验证命中/跳过 contract、必要时在 Wave 0 前后两次进入 contract、失败重试、同卡二次 acceptance、附件版本与任务结果不会串轮。若既有能力无法正确表达，记录具体阻塞后再设计最小状态或引擎增量；不静默绕过门，也不预先扩成四列。

### 5.3 基线与证据衔接

Wave 0 验收记录绑定故事/原型版本、被测提交、运行构建/环境、实际结果和审查记录，并指明触及的架构边界核对结论。后续子卡共同基线首先是该已验提交，其中已包含 Wave 0 前必须冻结的外部承诺；若 Wave 0 后再进入 contract，则叠加其冻结提交；若跳过，沿用已验提交和适用的既有契约。取不到对应基线不得从旧 main 重新猜实现。

contract 做接口搬移等调整后，对受影响的故事补跑验证；影响证据有效性的代码或环境变化会使对应证据失效。重新运行可以更新证据，不能覆盖旧记录冒充从未失败。若外部承诺必须在 Wave 0 前冻结，Wave 0 直接遵守该版本，后续未经变更审批不得改写。

阶段入口由协调者核对交棒证据与冻结判据，contract 命中时也核对上游引用。当前不能证明引擎会验证故事语义或条件跳转：附件存在与验收通过必须分开报告；纪律拒绝与机器 gate 拒绝不能混称。隔离测试须分别核实由谁执法。

## 六、契约冻结与拆解职责

### 6.1 冻结前识别独立消费者，避免循环

Wave 0 验收后，协调者在同一 plan 的交棒区形成简短协作分工草案：下一批有哪些工作单元、各自责任、哪些接缝被共同依赖、哪些仍待验证。它不生成完整子卡 DAG，不预写实现。

协调者据此判断有无新增冻结对象：有则先进入 contract，再由 breakdown 形成正式子卡与依赖关系；没有则直接进入 breakdown，并记明已复用的契约或无新协作接缝。若拆解改变了消费者、责任或所需接缝，重新按 §6.2 判断；命中时回 contract 冻结，不能把未经冻结的新缝混入派发。分工确定后更新同一记录，避免另造一份长期维护的拆解文档。

### 6.2 冻结理由与证据分开

独立 contract 节点只为本轮**新增或变更**两类承诺：独立工作单元之间共同依赖的接缝，或对外兼容面。每条写清生产者、消费者、依赖的语义及兼容边界。子系统边界本身在 spec 定语义、Wave 0 触及处由代码与审查证明，不以进入 contract 作为架构合格的替代条件。

| 情形 | 路由与责任 |
|---|---|
| 新的对外承诺是 Wave 0 真实运行的前提 | 在 Wave 0 前进入 contract，仅冻结这条必需的外部缝；不能先用自定协议跑通再要求对侧兼容 |
| Wave 0 后新建/变更独立工作单元共同依赖的接缝，或后续新增对外承诺 | 在相应子卡派发或对外消费前进入 contract；只冻结受影响的缝 |
| 复用已有稳定契约 | 从一开始遵守并引用其版本，由 plan/review/acceptance 查证；不为重复冻结进入 contract |
| 同一工作单元内继续演化、没有新增对外承诺 | 不进独立 contract 节点；breakdown/plan 仍写清责任与架构边界，review 仍检查实际调用 |

“已在 Wave 0 跑过”是证据状态，不单独构成冻结理由；撤回 r1 的 O 类入口。无独立协作/兼容需要的内部方法留在工作单元内演化。尚未被竖切覆盖的接缝，若确需并行，必须有两侧约束、可编译的消费关系与必要契约断言；其未验证行为仍不能标为真机通过。

已有仓内签名以源码为真源，文档引用提交与符号并说明语义；新建接缝先产生可编译骨架或协议金样本，再以其提交/版本为共同依据。外部 wire/存储格式按其规范与金样本表达。契约不复制全部实现，也不靠“有接口”证明架构成立。

contract 删除硬编码直通竖切；Ticket 0 只保留确有协作/兼容价值的声明与协调骨架。业务首轮实现归 implement；契约整理不得顺手扩出新用户能力。

### 6.3 轻档与存量兼容

只有按 Wave 0 路径工作的重档才要求对应前置证据。L3 轻档没有独立扇出、也没有新增或变更的外部兼容承诺时，跳过 contract；命中对外承诺时按其真实前置关系冻结，不要求提供不存在的 Wave 0 验收记录。轻档若遇到承重未知，可先安排窄验证再继续，不能因为档位轻就猜定行为。

既有稳定公开契约不会因“契约后移”自动解冻；Wave 0 必须遵守它们。只有本次新增且尚未承诺的内部边界可以在授权范围内演化。

### 6.4 故事是交付单位，子系统是代码责任单位

一个故事允许由多张工程子卡共同实现。重档 breakdown 对待实现部分建立“故事/步骤 → 工程子卡 → 集成与演示负责人”的映射；Wave 0 已完成的故事指向已验父卡基线与最终回归负责人，不重复造卡。轻档只映射到有界单轮工作单元及验收责任，不强造子卡 DAG。每张实际创建的工程子卡有有界代码范围和独立技术验收，但不必单独产生用户可见结果。

共享基础设施、迁移和还债卡允许存在，需说明服务于哪个已批准目标。不能仅因卡名含接口/DTO 就拒绝，也不能因所有子卡通过就宣布故事完成。

后续按可集成的故事增量分批推进；每批将代码集成、演示、回归已有故事，再推进依赖该结果的下一批。最终 acceptance 对全部必交故事和原型基准逐项核销，Wave 0 旧绿、子卡技术验收或“后续修复卡已创建”都不抵最终完成。

## 七、架构与用户沟通

架构形状在 spec 中描述责任、权威状态、允许依赖、公开面与组装关系；存量物理位置给现状指针，新的内部文件/符号落点由 plan/实现细化。目标边界允许在事实反馈后修订，涉及承重归属按决策权限升级。

Wave 0 的架构验收仅覆盖所选故事实际触及的生产路径：既要查本次新增调用是否遵守目标方向，也要查该路径的权威状态、组装与消费者是否真的落在声明边界上。局部合规可以如实报告；不能据此称尚未覆盖的子系统或整体迁移已完成。contract 的冻结结论也不能替代这项审查。

| 结论 | 必须具备的证据 |
|---|---|
| 目标结构已声明 | 最优图/契约图或人工结构说明 |
| 本次变更契约合规 | 修改触及的实际调用满足约束，无新增违约 |
| 指定边界已实现 | 物理代码边界、权威状态归属、真实组装与生产消费链均成立；该范围内没有绕过公开面的路径 |

遗留直调可明确登记，但有绕行的边界不能称为完整隔离；可以报告“本次新增路径合规、整体迁移未完成”。同包内任意调用、未被生产使用的接口、测试替身或宽预算下的 graph 绿均不足以证明边界实现。

协调者交接或遇到阻塞时，用故事语言说明：现在能观察到什么、还缺什么、发现的新事实影响哪项承诺。需要用户裁决时，先给可观察差别、成本/风险、推荐和需要改变的承诺；局部技术选型由获授权的责任者处理。

## 八、实施范围与生效边界

下列是完整实施与验收范围。仓内 skill 正文已先行修改；其余动作仍须按隔离验证与版本决策推进。

1. Charter 正文：spec 的故事、目标架构与依据绑定；plan 的通用瘦身；Wave 0 的生产路径架构验收；contract 的条件进入与窄冻结；breakdown 的两层分工；implement/review 的自主调整与证据口径；integrate/acceptance/finish 的故事闭环；using-charter 与 architecture-law 的对应路由和判据。
2. 共用规则优先放已有合法载体；只有多节点确需共享的故事约束才抽短的 story-spine 横切正文，不复制 plan/implement/review，不预建三份专用纪律块。
3. workflow 先修集成后验收及失败路由；还要支持 L3 轻档从 spec、L3 重档从 Wave 0 验收直接进 breakdown 的免冻结路径，并使 breakdown 的附件门与失败回退按实际冻结对象处理。新外部承诺前置时也要验证 spec → contract → Wave 0 的路径；同卡前后都命中 contract 时验证重复进入。新阶段与条件分流先在隔离账本证明，再写入 product-backlog 驾驶手册。本文不预设 handoff 新字段、节点别名或版本选择能力。
4. 生成与检查：沿用 regen_discipline 的 compose_map/regen 与 charter_provision 的 install/check 真通道。regen 写出的文件只是产物；实际纪律以账本 discipline get/put 为准，不能把本地文件更新当成安装成功。
5. 分发生效清单覆盖本机与 mac-02 上实际使用的协调者/执行者 harness，至少核查用户使用的 Grok、Claude Code、OpenCode；同时核对 Codex 安装入口。查清实际目录、软链接/插件来源与加载方式后，按同一修订同步。未访问或未验证的端明确记未生效。
6. workflow 的卡钉版本与纪律块/本地 skill 的加载版本分别查证。旧卡可否继续旧法取决于能否保持配套版本，不能仅因 workflow 钉旧版就假设规则全旧。先隔离试点；正式替换前明确活动卡清单、适用版本及恢复办法。不自动迁移在飞卡、不把已过节点的历史证据伪造为新法证据。

测试接缝为现存生成器被 provision 消费的正文、provision 与 handoff 账本的边界、以及卡节点派发与结果处理。使用现有脚本测试和隔离账本验收，不为本次文字改造新造通用管理平台。

## 九、验证与效果观察

### 9.1 实施验收

- 语义对账：spec、plan、implement、review、网关和驾驶手册不再互相要求复制签名/预写实现；轻档不被 Wave 0 前置条件误拦，也不因无新增冻结对象被迫生成空 contract。
- 生成与安装：生成到临时目录并运行现有相关测试；隔离目标实际安装后读取 workflow/template/discipline 比对。只做关键词匹配不算行为验证。
- 正向流程：分别跑通 Wave 0 → contract → breakdown 与 Wave 0 → breakdown 两条重档路径、轻档有/无 contract 两条路径，以及外部承诺前置时的 spec → contract → Wave 0；再跑子卡 → integrate → 最终 acceptance，验证共同基线、阶段分支、必要的重复进入和恢复。
- 反向流程：构造一个故事功能通过但新增路径穿透他方内部的 Wave 0，确认审查或验收拒绝共同基线；分别验证缺 Wave 0 证据、引用旧提交证据、无冻结对象却被附件门卡住、真实冻结对象被绕过、breakdown 失败误退 contract、验收失败和节点重试。记录是协调者纪律拦截、执行者拒绝还是机器 gate 拒绝，不混称自动保证。
- 基准传递：让实现/审查从其真实上下文取得故事与原型版本；构造一个故事遗漏和一个原型差异，确认它们会被指出，不能仅验附件存在。
- plan 验证：用无需完整代码块的真实任务检验交接是否足够；局部可逆调整允许通过，改变承重承诺仍会升级。
- 若节点复用或旧卡兼容验证失败，明确阻止推广并回写最小必要变更，不能在完成声明中藏成“后续补验”。

### 9.2 真实卡效果观察

先跑一张适合的 L3 重档试点，确认流程可驾驶，再观察累计三张；没有真实样本就只报告规则/机制验证，不宣布提速。观察任务见 docs/roadmap.md 第 65 条。

| 指标 | 口径 |
|---|---|
| 首次可演示时间 | spec 批准到首个符合选定故事的真实演示，保留时间戳 |
| 总交付时间 | spec 批准到全部必交故事最终验收，包含中途返工 |
| 人工介入 | 用户被要求作决定的次数与原因；可取得时另记投入时间 |
| 返工 | 因原承诺遗漏、假设错误或边界变动产生的工作与耗时；新需求另列 |
| 流程成本 | 文档/审查/派发轮次，活跃处理与排队/等待分别记录 |
| 质量与覆盖 | 必交故事证据、已知未验证项、集成后缺陷与原型偏差 |

历史对照记录项目规模、承诺变化、模型/harness 与环境差异；只作可解释的描述性比较，不把三张卡当因果证明。token/费用仅在真实记录可得时补充。契约行数、卡数只作诊断，不作为优化目标或删除必要工作的理由。

负优化信号：脊柱持续扩大却迟迟无演示；轻量 plan 把关键选择留空而引发反复询问；故事仅贴 ID 无证据；临时探索代码固化错误架构；无冻结对象仍派 contract 或该冻的缝直接扇出；等待/人工裁决增加而返工未减少；为让指标漂亮把欠交移成新卡。出现时收窄或修订相应规则，不继续叠加统一检查表。

## 十、范围外与修订边界

- r3 设计修订轮未修改 skill、运行时 workflow、卡状态或任一机器的安装；后续经用户授权的第一阶段已修改仓内 skill，但仍未修改运行时 workflow、卡状态或任一机器的安装，也未 commit/push。
- 不重新实现 B158/B358，也不补做过去一个半月的完整效率统计。
- 四个新增状态暂不进入本期承诺。若隔离试跑证明既有节点不能表达，再以具体失败证据设计必要增量；跟踪见 roadmap 第 66 条。
- 自动定级、通用架构 linter、原型自动生成故事均不在本期；没有另行承诺后续建设。
- 不用代码量、接口数、固定时间粒度或固定失败用例数定义计划质量。
- 不因精简 plan 放弃架构、真实验收、独立审查或对用户承诺的变更控制。

## 十一、r3 对审查意见的处置

| 问题 | 本版处置 |
|---|---|
| 过早精确化被转移到 plan | §四删除预写实现义务，同步 implement/review；明确自主权限 |
| 一条故事掩盖全目标与其他未知 | §三完整承诺清单、风险选切与待验证项；§六分批交付 |
| 原型继续被摘要替代 | §3.3 绑定版本/状态/实际证据；§七用产品后果沟通 |
| 轻档前置死锁、contract/breakdown 循环 | §6.1 冻结前分工草案；§6.2 按新增冻结对象选路；§6.3 轻档无冻结对象时跳过 contract |
| 故事与子系统混作拆卡单位 | §6.4 工程验收与故事验收分开，明确收口人 |
| 只查文本、安装与门禁口径失真 | §五隔离验证节点复用；§八真实安装和版本；§九正反向流程验收 |
| 强制四列、未测流程成本 | §5.2 撤回新增列承诺；§9.2 加时间、人工与返工口径 |
| Wave 0 为赶演示固化错误边界 | §5.1 增行为与架构双轴验收；§七只对已触及生产路径宣称物理边界成立 |
| contract 后移后仍强制空转，或外部前提被拖到 Wave 0 后 | §5.2 与 §6.2 改为条件节点；外部必需承诺前置，复用既有契约时不重新冻结；§九验证跳过与前置路径 |

r3 记录的是修订后的设计与验证要求，不是这些效果已经实现的结论。
