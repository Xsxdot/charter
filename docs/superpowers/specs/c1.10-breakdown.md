## 三、同一轮 implement 工作项与依赖 DAG

本节的 T1～T4 是 implement 轮内的工作项，不是子卡。每项都有有界文件集和行为化判据；协调者拍板 P1 后在 T3/T4 选对应文件方案。

    T1（Go 校验与 fixture） ───────────────┐
                                          ├─→ T4（页面装配、wire 缺席回归、全量回归）
    T2（纯函数语义/结构模型） ─→ T3（双 tab/级联抽屉组件） ─┘

T1 与 T2 可并行；T3 依赖 T2 的模型；T4 依赖 T2/T3 的导出模型和组件入口。C1.11 的宿主生产半边不作为本轮工作项，真机联调由协调者在两卡合并后执行。

### T1｜best 词表校验切换与 charter 测试夹具适配（S1·逻辑型）

#### ①契约引用

contract §2.3 条 22～28、条 36 的跨卡版本钉语义；现状入口 graph/codegraph/decls.go#ValidateDecls、graph/cli/cli.go#graphValidateCmd、graph/codegraph/decl_test.go#TestValidateDecls。

#### ②意图与为什么

让声明存在性校验与查看器使用的最优组织共享同一主词表，同时保留锚点和 testRef 的原有保鲜规则。best == nil 是合法存量形态，必须显式产出可行动 issue 而不是崩溃或把声明当作已校验。测试 fixture 的声明文件只用于把“声明 key 来自 best、容器仍可落在 baseline 另一套域名”这条本地回归固定下来，不代表 C1.11 的真实声明迁移。

有界文件集：

    graph/codegraph/decls.go
    graph/codegraph/decl_test.go
    graph/cli/cli.go
    graph/cli/cli_test.go
    graph/codegraph/testdata/repo/codegraph/domains/d_cmd.json（由现有 d_cli fixture 改为 best 词表）
    graph/codegraph/testdata/repo/codegraph/domains/d_cli.json（仅保留/生成坏声明测试所需的临时路径，不作为有效迁移数据）

#### ③验收

1. cd graph && go test ./codegraph -run 'Test(LoadDomainDecls|ValidateDecls)$' -count=1 退出码为 0；完整声明在 best.Domains 存在而 v.Domains 不存在时返回空 issues，声明只在 v.Domains 存在而不在 best.Domains 时返回包含领域 id 的 issue。
2. cd graph && go test ./cli -run 'TestGraphValidate(|ReportsDomainCount|DomainDeclIssuePrefix)$' -count=1 退出码为 0；validate fixture 使用 best 词表并继续输出声明计数，坏声明仍以 [decl <id>] 前缀返回非零，不把坏声明静默当成无声明。
3. best 缺失场景的测试构造 best == nil，执行 ValidateDecls 不 panic，返回明确“无法在 best 词表校验”的 issue；命令退出非零时输出包含声明 id，而不是成功报告。
4. 锚点回归保持可行为化验证：moved anchor 仍不报错，vanished/file-missing anchor 仍各自产出对应 issue；注释中出现同名函数不满足 TestRef。
5. cd graph && go test ./... -count=1 退出码为 0；graph/codegraph/testdata 的本地 fixture 适配只为该测试闭环，不声称 handoff 的声明迁移已完成。

缺陷族对抗审查：

| 族 | T1 验收结论 |
|---|---|
| 生命周期 / 状态机中断 | 无，因为 T1 是纯内存校验加只读声明加载；进程中断不启动子进程、不创建工单或临时目录。文件读取由现有 LoadDomainDecls 负责，半次命令不会留下业务资源。 |
