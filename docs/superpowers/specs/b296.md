# B296 台账提交事实不得自引用最终 HEAD

## 问题陈述

谁：产出型节点的执行者（写台账、同批提交）；审查者（读台账对账）；协调者（决定打不打回）。

条件：节点纪律要求「提交事实进台账」且「台账与产出同批提交」。同批的法定动作是一次 `git commit --amend --no-edit`。

要变的事实：执行者不再把「台账里的 hash 等于最终 HEAD」当成必须达成的状态；审查者不再把不相等写成 finding。可观察结果：像 B266 那样的功能已经做完的卡，不会再因追 hash 空转三轮、撞封顶。

今日（B266 实测）：执行者按字面记 `git commit` 原始输出（含 hash）→ 为同批而 amend → hash 变了 → 审查以「台账 ≠ HEAD」major fail → 协调者接受 → 再派 implement 追新 HEAD → amend 再换 → 永远对不上。review skill 正文里没有这条检查；是审查发明、协调者批准的伪规则。

根因不是「amend 用错了」，是 **git 提交写不进自己的最终 hash**。任何「台账文件里的本提交 hash == 该提交 HEAD」都不可满足。继续教执行者「再 amend 对齐」是在追一个数学上不存在的不动点。

## 方案

**记法（产出节点）**：提交当时的命令与原始输出照旧进台账（那是历史读数）。随后 **只 amend 一次** 把这条收进同批提交。amend 会换 hash——这是 git 的事实，不是漏记。**禁止**把 amend 后的 HEAD 写回台账再 chase。收口判据是工作树干净，不是「文件里的 hash 等于 HEAD」。

**禁令（审查节点）**：**禁止**把「台账记录的 hash ≠ 当前 HEAD」写成 finding。缺的是提交命令或原始输出，才构成台账缺项。

**落地范围**：五份「边干边落台账」段各补同一记法（implement / plan / contract / breakdown / spec，避免只补 implement、plan 轮照样追）；review 红线另补禁令（审查节点没有台账段，不能靠改那五份让审查者读到）。条款落盘后 regen + provision install，执行者读到的是账本里的块。

弃选：

- **只改审查、不改记法**：B266 的执行者会继续 chase，审查即使不 fail，implement 自审仍可能把自己打回。病在两边。
- **记父提交并让审查核 `HEAD^`**：新的可检查字段，多一套对账，收益仍只是「别追自引用」。YAGNI。
- **取消同批、改成第二次 ledger-only commit**：hash 写的是第一次提交，文件仍不等于 HEAD；还拆掉 handoff 已放行的法定 amend。不动这条通道。
- **handoff 侧加机械闸拦「hash≠HEAD」finding**：审查产出是 LLM 文本，解析不到稳定字段。机械执法归 C8 族，本卡不并。
- **把五份台账段抽成单一真源**：现存重复，本卡不借机重构。

## 用户故事

1. 产出节点执行者提交后把命令原文写入台账、amend 一次、工作树干净即收口；不得再开一轮「把 HEAD 写进台账」。
2. 审查者看到台账里的 hash 与 `git rev-parse HEAD` 不同，不写 finding、不因此 fail。
3. 台账完全没记提交命令或原始输出，审查仍可报缺项。
4. 改完 skill 并 install 之后，派发注入的 `charter-implement` / `charter-plan` / `charter-contract` / `charter-breakdown` 含记法句，`charter-review` 含禁令句。
